# Helodrace 1.7 전용 전환 계획

작성일: 2026-10-30. 상태: 실제 1.7 설치·빌드 및 저장 회귀 기반 전환 진행 중. 세부 증거와 미완료 항목은 [전환 실행 기록](1.7%20전환%20실행%20기록.md)에 기록한다. 0~3단계 전체 완료 상태는 아니다.

목표는 **Main을 RimWorld 1.7 / .NET 10 / Harmony 3 전용으로 전환하고, 모드가 소유한 계산·리소스·그리기 코드를 가능한 한 Waylith native API로 옮기는 것**이다. Main의 1.6 실행, 이전 저장 파일, 구형 DefName과 모드 API의 호환성은 유지하지 않는다. **이미 배포된 Blancas Drugs에는 이 폐기 정책을 적용하지 않으며, 기존 버전과 저장 데이터의 호환성을 보존한다.** Lobos Arsenal은 Vehicle Framework의 1.7 대응을 전제로 함께 검증한다.

기술 근거는 [1.7 엔진 구조 및 최적화 검토](1.7%20엔진%20구조%20및%20최적화%20검토.md)와 `1.7.4990-unstable` 참조 DLL 조사다. 이후 승인된 Steam 전환으로 실제 1.7.4990 rev1069를 설치했다. 2026-11-01에는 Steam 설치가 1.7.4995 rev309로 갱신된 것을 확인했고 새 엔진에서 빌드·기하/런타임·시작/저장 검증을 다시 수행했다. 참조 DLL만으로 호출 의미나 성능을 판정하지 않는다. 사용자가 정한 native 우선 방침을 이번 전환의 기준으로 삼는다.

## 전환 원칙

1. Main은 단일 1.7 코드와 빌드 산출물을 사용한다. Main의 1.6 분기, 다중 타깃 빌드, 구버전용 어셈블리와 저장 데이터 이행 코드는 남기지 않는다. Blancas Drugs는 별도 버전 로딩·빌드와 필요한 저장 호환 경로를 보존한다.
2. 모드 내부는 Waylith 또는 엔진이 사용하는 .NET 타입을 사용한다. Unity 타입으로 계산한 뒤 마지막 호출 이름만 native로 바꾸는 전환은 완료로 계산하지 않는다.
3. RimWorld 1.7 자체의 public API·override·Harmony 대상이 요구하는 Unity 타입은 경계에서 주고받는다. 이것은 구버전 지원과 구분한다. 변환은 입력과 출력 지점에 모으고 반복문 내부 왕복 변환을 없앤다.
4. 모드가 직접 사용하는 Unity API는 항목별로 native 대응을 검토한다. 남기는 사용처는 파일·심볼·게임 계약·직접 전환할 수 없는 이유를 기록한다. UI 전체를 일괄 제외하지 않는다.
5. native 전환으로 기대하는 효과와 실제 측정 결과를 구분한다. 정확도·외형·입력 동작은 기존 의도와 맞추고, 성능 개선 여부는 1.7 안에서 비교한다.
6. 기능 단위로 검증 후 main에 커밋한다. 브랜치와 PR은 만들지 않는다. 작업 시작 전부터 존재한 다른 변경은 각 커밋에서 제외한다.

확인한 packageId:

- Main: `BlueBackedFish.Helodrace.Main`
- Blancas Drugs: `BlueBackedFish.Helod.BlancasDrugs`

- Lobos Arsenal: `Arsenal.Helod.LobosArsenal`

종속성 방향은 `Main → Blancas Drugs`, `Lobos Arsenal → Main + Vehicle Framework`다. Blancas Drugs가 Main을 필수로 요구하는 역방향 의존성을 만들지 않는다. VF와 Lobos Arsenal은 Main의 필수 종속성으로 넣지 않는다.

Main의 About.xml에는 Blancas Drugs를 modDependencies로 추가했고 기존 loadAfter도 유지한다. 실제 1.7 빌드·시작 검증 후 supportedVersions를 1.7 전용으로 전환했다. 이는 native 전환 전체 완료를 뜻하지 않는다. 연구·레시피 패치, MayRequire로 감싼 유전자와 TCCC 약물 선택은 필수 구성 기준으로 후속 정리한다. 이 과정에서 Blancas 자체의 기존 DefName·독립 실행 계약은 바꾸지 않는다.

## 0단계 — 실제 1.7 실행 환경과 기준 확보

작업:

- Steam 1.7 unstable의 실제 설치 버전과 빌드 ID를 기록하고 엔진 DLL·호스트 구조를 확인한다. 참조 패키지와 실행 버전을 맞춘다.
- 별도 저장 경로와 `-mod=`로 Harmony·Core·Biotech·Blancas Drugs·Helodrace 최소 구성을 만든다. 기존 테스트 실행기의 ModsConfig·명령행에도 필수 packageId를 넣는다. 현재 사용자 플레이 환경과 시험 환경을 구분한다.
- native API 연결 및 리소스 수명을 판단하는 데 필요한 함수 본문을 로컬에서 확인한다. 함수 본문을 참조 DLL로 추정하지 않는다.
- Main 기능 기준 화면·동작과 성능은 새 게임·새 저장으로 기록한다. Blancas Drugs는 Main 없는 기존 배포 환경의 저장도 별도 확보해 이전 저장 호환성을 시험한다. 새 Main을 과거 저장에 추가하는 작업을 Blancas 호환성 시험과 섞지 않는다.

완료 기준: 정확한 버전·실행 명령·모드 목록·로그 위치·기준 맵이 재현 가능하다. Headless는 계산 시험, NoWindow/일반 창은 렌더링 시험에 사용한다.

## Blancas Drugs — 선행 구조 감사·1.7 대응·기존 배포 호환성

Main의 필수 종속성이므로 **Main 1.7 통합 시험 전에 Blancas 1.7 기반과 저장 회귀 기준을 마련한다.** 구조 개선은 호환되는 작은 단위로 나눠 진행하고, 단순 재빌드만으로 이 작업을 완료 처리하지 않는다.

### B0. 배포 계약과 기존 동작 고정

- 실제 배포 버전의 DLL·Defs·패치·번역·빌드 설정과 기존 저장 fixture를 고정한다. 현재 저장소 소스와 배포물이 같은지 먼저 비교한다.
- packageId, `BD_*` DefName, `HelodBlancasDrug` 내 저장된 Hediff/Comp 타입과 Scribe 키를 목록화한다. `HediffComp_SleepLogic.hasTransitioned`처럼 이미 저장하는 상태는 유지하거나 명시적 이행으로 읽는다.
- 기존 1.6 배포 경로를 보존하고, 1.7용 net10.0 산출물을 별도 버전 폴더와 LoadFolders로 분리한다. 공통 루트의 Assemblies에 두 버전 DLL이 동시에 로드되지 않게 한다. 기존 버전의 Defs도 의도치 않게 바뀌지 않도록 범위를 분리한다.
- Main 없이도 기존 기능을 유지한다. Main 전용 연구 배치·유전자·TCCC 연동은 Main에서 관리해 순환 의존과 기존 사용자에게 Main 설치를 강제하는 변경을 피한다.

### B1. 비효율적인 구조부터 측정·개편

확인한 우선 감사 대상:

| 대상 | 현재 코드에서 확인한 구조 | 개선 방향과 보존할 의미 |
|---|---|---|
| `HediffComp_ExclusiveGroup` | Comp마다 60틱 검사, Pawn의 전체 Hediff를 LINQ·익명 객체·ToList로 반복 검색 | 폰/그룹 단위 중복 평가·할당 제거 검토. stage/Severity 변경·추가/제거 시 갱신하고 offsetStages·동률 처리·기존 검사 시점·OnRemoval 억제 의미 보존 |
| `HediffComp_SleepLogic` | 전환 전까지 매 틱 Awake/InBed 판정 | 실제 비용을 측정하고 상태 전이/interval 구조 검토. 침대 수면만 허용하는 조건과 hasTransitioned의 일회성·재로드 동작 보존 |
| Compare*AndRemove Comp | 임시 Hediff 추가 → 다른 Hediff 검색/비교 → 즉시 자기 제거 | 공통 판정 로직·조회 중복 정리. 외부 DefName·Comp 타입·복용 효과 순서를 유지하고 제거 콜백 재진입 방지 |
| OnRemoval·MKultra | 효과 제거·추가와 수술/섭취 분기가 연결됨 | 재진입·중복 적용·목록 변경 중 순회 점검. 일회성 LINQ부터 무조건 고치기보다 반복 경로 비용 우선 |

- 추가/제거·stage 변경 때 캐시를 갱신하며, 저장에 남길 필요가 없는 캐시는 로드 후 재구성한다. 실제 Pawn/Hediff 변경은 메인 스레드에 둔다.
- 구조·할당 최적화와 약물 밸런스·수치·효과 시점 변경을 별도 작업으로 분리한다. native API 전환이 저장 타입 이름 변경으로 이어지지 않게 한다.
- 유지해야 할 구형 타입은 얇은 호환 진입점으로 남길 수 있지만 비효율적인 내부 구현 전체를 보존할 필요는 없다. Main의 일괄 구형 코드 삭제 기준을 적용하지 않는다.

### B2. Blancas 단독·필수 통합 회귀

- 기존 약물 복용 중·각성/진정 중첩·offset stage·동률·금단/후유증·침대 수면 전환 전후·MKultra 상태가 있는 이전 저장을 읽고 다시 저장/로드한다. 시험 원본을 덮어쓰지 않는다.
- 약물·Hediff 소실, 전환 중복, 시간 리셋, 중독/부작용 값 변경, Def/타입 참조 오류가 없는지 확인한다.

## 3단계 — native 수학·시간·런타임 경계 정립

작업:

완료 기준: 독립 계산과 내부 렌더 데이터의 Unity 타입 의존이 제거되고, 변환이 경계에 집중된다. 계산·위치·방향·시간 동작의 기존 검증이 통과한다.

## 4단계 — 텍스처·메시·재질 소유권과 캐시 전환

작업:

- 아이콘·부품 이미지·방어구 미리보기를 native CPU 데이터 우선 경로로 옮긴다. CPU 데이터가 없을 때의 처리는 1.7 native 복구/렌더 경로로 구현한다.
- 필요한 알파 마스크·경계·축소 픽셀만 보관하고 원본 CPU 데이터를 불필요하게 붙잡지 않는다. CPU 데이터 퇴거·재상주 시나리오를 포함한다.
- 직접 생성 메시·텍스처·재질·렌더 타깃의 owner를 정하고 native 생성·업로드·폐기로 바꾼다. 게임 풀의 공유 리소스는 소유하지 않는다.
- 색 공간·premultiplied alpha·텍스처 방향·mip·필터·압축 포맷을 처리하고, 모드 캐시와 엔진 캐시가 이중 보관하지 않게 한다.
- P1 캡처와 미리보기 렌더 타깃은 실제 host capture/readback API를 조사해 옮긴다. native 대체가 없는 경로만 구체적인 예외로 등록한다.

완료 기준: 모드 소유 리소스의 Unity 생성·Destroy·GPU readback 호출이 가능한 범위에서 제거된다. UI 재개방·부품 교체·캐시 퇴거·맵 변경을 반복해 외형과 리소스 수명이 정상이다.

완료 기준: 모드의 자체 월드 draw는 native로 제출한다. 남은 Unity 렌더 타입은 게임 계약·공유 리소스 연결에 제한되고, 기능군별 화면 비교·draw/메모리 측정이 기록된다.

## 7단계 — .NET 최적화와 작업 시스템 적용

작업:

완료 기준: 결과 일치와 작업 취소 안전성을 확인하고, 작업 분리 전후의 총비용·긴 프레임·할당·명령 반응 지연을 함께 기록한다. native 전환 완료 여부와 별도로 실제 성능 개선을 판정한다.

## 8단계 — 패키징·잔존 의존성·전체 검증

작업:

- native 전환 목록의 각 항목을 완료 또는 구체적인 게임 API 경계로 확정한다. 미조사 상태를 완료로 처리하지 않는다.
- 코드에 남은 `UnityEngine`, 직접 Unity 정적 호출과 구버전 이행 코드를 재검색한다. 새 직접 의존이 추가되지 않도록 가벼운 목록 검사를 마련한다.
- Assets.zip 베이크와 원본 에셋 로딩을 검증하고 cold/warm load와 RAM/VRAM을 비교한다.
- 외부 연동은 1.7용 상대 모드가 있는 항목부터 확인한다. 필요한 현행 연동과 구버전 지원을 혼동하지 않는다.
- Blancas 필수 구성의 단독/이전 저장 회귀와 VF 1.7 기반 Lobos 전체 구성을 최종 목록에 포함한다. Blancas의 기존 버전 폴더·필수 호환 코드가 정리 과정에서 삭제되지 않았는지 확인한다.
- 구현 단계에서 관련 검증을 완료했다면 중복 실행을 반복하지 않고 마지막 통합 시험으로 이어간다.

완료 기준: Main의 1.7 단일 패키지와 Blancas의 버전별 배포가 아래 검증을 통과하고, Main의 불필요한 구버전 코드·외부 DLL 동봉·중간 산출물이 없다. Blancas의 기존 버전 지원과 필요한 호환 진입점은 유지한다. Lobos는 VF 기반 검증 결과를 별도 기록한다.

성능 수치는 1.7 자체의 변화와 이번 리팩토링 효과를 구분한다. 화면 캡처는 Headless로 검증하지 않는다. 불안정한 실제 렌더 환경을 계산 테스트 성공으로 대신하지 않는다.

## 커밋과 완료 관리

- 1단계 빌드/테스트 기반, 2단계 저장 구조 정리, 3단계 타입 경계는 각각 의미 있는 부분마다 커밋한다.
- 이후는 이미지 데이터·메시 수명·무기 draw·각 장비군·각 UI군처럼 독립 검증 가능한 기능군으로 나눈다.
- 이미 완료한 검증의 명령과 결과를 각 커밋에 연결한다. 계획 단계의 compile-only API 확인은 실행 검증으로 표기하지 않는다.
- 최종적으로 남은 Unity 사용 목록에는 `파일/심볼 / 1.7 게임 계약 / native 대안 조사 결과 / 경계 변환 위치`를 적는다.
- Blancas 저장 호환 검증과 구조 최적화는 별도 기능 단위로 커밋하고 해당 저장 fixture·전후 결과를 연결한다. 외부 모드 저장소의 변경은 각 저장소에서 관리한다.
- 최초 계획 작성 이후 사용자가 3단계까지의 구현과 Steam 1.7 unstable 전환을 승인했다. 현재 실행 범위는 0~3단계와 그 선행 조건인 Blancas 기반·기존 저장 회귀이며, 완료한 부분과 남은 항목은 전환 실행 기록에 구분한다. 4~8단계의 렌더 제출·리소스·입력 전체 전환은 후속 범위다.
