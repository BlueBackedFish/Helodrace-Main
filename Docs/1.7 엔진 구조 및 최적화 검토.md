# RimWorld 1.7 엔진 구조 및 Helodrace 최적화 검토

검토일: 2026-10-30. 비교 대상은 설치된 RimWorld 1.6.4871 rev590과 `Krafs.Rimworld.Ref 1.7.4990-unstable`이다.

후속 실행 방침은 [1.7 전용 전환 계획](1.7%20전용%20전환%20계획.md)을 따른다. Main은 1.7 전용·Waylith native 최대 전환·구버전 호환성 폐기를 적용한다. 이미 배포된 필수 종속성 Blancas Drugs는 기존 버전·저장 호환성을 보존하며 구조를 개선하고, Lobos Arsenal은 VF 1.7 기반의 검증 대상에 포함한다. 아래 내용은 당시의 기술 조사 결과로 읽는다.

**가장 먼저 할 일은 1.7에서 병목을 다시 측정하는 것이다.** 이후 사격 판정의 박싱 제거, 텍스처 CPU 데이터 활용, 큰 전술 계산의 작업 스레드 분리를 순서대로 검토한다. 틱과 게임 객체 조작은 현재처럼 메인 스레드가 소유하는 구조를 유지한다.

## 확인 범위와 한계

- 1.6의 실제 `Assembly-CSharp.dll`과 1.7 참조 DLL의 타입·필드·메서드 선언을 직접 비교했다. 공개 멤버뿐 아니라 private 멤버도 포함한다.
- 1.7 참조 패키지는 함수 본문을 포함하지 않는다. 따라서 메서드 내부 알고리즘, 실제 호출 경로, 락 동작, GPU 동기화 비용을 역컴파일해 확인한 결과가 아니다.
- 1.7 엔진 API는 `Waylith.dll`, 호환 API는 `UnityStubs.dll`의 메타데이터에서 확인했다. 실행 게임은 1.6으로 유지했다.
- 공식 Modder Primer와 .NET 문서를 함께 확인했다. 아래에서 API 존재 사실과 적용 제안을 구분한다.
- 검토용 프로젝트와 원본 비교 결과는 `.codex-staging/api17`, `.codex-staging/build17`, `.codex-staging/compat17`에 있다. 제품 소스와 배포 DLL은 변경하지 않았다.

## 실제 구조 변화

| 영역 | 1.6 | 1.7에서 확인한 구조 | 모드에 주는 의미 |
|---|---|---|---|
| 실행 기반 | Unity / Mono | Waylith / CoreCLR .NET 10 / Vulkan | 같은 C# 코드의 실행 특성이 달라진다. 예전 성능 수치를 그대로 적용할 수 없다. |
| 게임 로직 | Assembly-CSharp | Assembly-CSharp 유지 | 전술·경로·틱 코드를 전면 교체할 근거는 부족하다. |
| Unity API | UnityEngine 모듈들 | UnityStubs → Waylith | `using UnityEngine`을 일괄 제거할 필요가 없다. |
| 엔진 기능 | Unity 모듈들 | Waylith.dll | 작업 스케줄러, 렌더링, 텍스처, 프로파일러 API에 직접 접근할 수 있다. |
| 실행 호스트 | Unity 플레이어 | RimWorld.dll | 시작과 UI·렌더 기능 설정을 호스트가 담당한다. |

게임 어셈블리의 타입 정의 수는 16,158 → 16,222개였다. 추가 124개, 제거 60개, 공통 타입 중 필드·메서드 선언에 차이가 있는 타입은 81개다. 컴파일러 생성 타입도 포함한 수치이며, 함수 본문 변경량을 뜻하지 않는다.

`Verse.PathFinder`, `Verse.GasGrid`, `Verse.TickManager`, `Verse.PawnRenderTree`, `Verse.AI.Pawn_PathFollower`는 이번 비교에서 필드·메서드 선언 차이가 없었다. 이 사실은 내부 구현이나 실행 엔진까지 같다는 뜻은 아니다.

다음 변화는 메타데이터에서 직접 확인했다.

- `GlobalTextureAtlasManager`: 압축, 캐시 쓰기, CPU 데이터 해제, 원본 텍스처 퇴거 관련 멤버 추가.
- `StaticTextureAtlas`: 캐시된 페이지 채택, 페이지 캐시 키, 원본 퇴거 관련 멤버 추가.
- `ContentFinder<T>`: 번들 검색 결과 캐시와 갱신 stamp 관련 멤버 추가.
- `ModContentLoader<T>`: 경로 사전 검색과 DDS 중복 처리 관련 멤버 추가.
- `ThingWithComps`: `compsByTypeCount`, `compsByTypeLast`, `RebuildCompsByType` 추가. 캐시 관련 구조가 늘었지만 실제 GetComp 비용 감소량은 미측정이다.
- `Building_Door`: `willCloseSoonForJobs`, `SnapshotWillCloseSoonForJobs()` 추가. 이 선언만으로 다른 Map/Pawn API의 스레드 안전성을 보장할 수는 없다.
- `GlowGrid`: `RegisterCustomGlower(...)`, `DeregisterCustomGlower(int)` 추가.
- `ShaderDef`, `ShaderDefRegistry`, `MaterialDef` 및 내장 프로파일러 UI 타입 추가.

## 우선순위 1: 내장 프로파일러로 기준 재설정

현재 `Source/Helodrace/Profiling/AgentMethodProfiler.cs`와 `MethodCapture.cs`는 선택적 Harmony 계측과 메인 스레드 중심의 측정을 사용한다. 다른 스레드 호출은 별도 카운트하고 상세 추적에서 제외한다. `WindowsMethodClock.cs`의 CPU 측정도 Windows의 거친 시간 계측에 의존한다.

1.7에는 `Waylith.Profiling.FrameProfiler.Scope(string)`, 스레드 타임라인, 할당 추적과 런타임 정지 관찰 API가 있다. 전술 계획·통신·관측·가스·아이콘 생성에 큰 단위 scope를 넣으면 작업 스레드와 GC에 걸친 비용을 같이 살필 수 있다. 모든 작은 메서드에 계측을 넣으면 계측 자체가 비용을 만들므로 범위를 제한한다.

적용 제안:

1. 같은 맵·병력·명령 조건으로 1.6과 1.7을 비교한다. 초기 로딩과 캐시가 준비된 상태를 구분한다.
2. 평균 TPS뿐 아니라 긴 프레임, 할당량, 작업 대기, 명령 접수부터 실제 Job 발행까지의 지연을 기록한다.
3. 기존 전술 증거·회귀 검증용 기록은 유지하고 성능 관찰을 내장 프로파일러와 연결한다. 현재 측정기를 전부 삭제할 근거는 없다.

## 우선순위 2: 사격 판정의 박싱과 리플렉션 제거

확인한 현재 코드:

- `Gas/HelodGasSystem.cs`, `Patch_HelodGas_ShotReport`: ShotReport를 object로 박싱하고 `shootLine`, `factorFromCoveringGas`를 FieldInfo로 읽거나 쓴다.
- `Core/CompMultiCrewTurret.cs`, `Patch_ShotReport_MultiCrewAccuracy`: 같은 방식으로 `factorFromShooterAndDist`를 갱신한다.

1.7에서도 이 필드 이름과 타입이 유지되며 `ShotReport.ShootLine` 공개 getter도 존재한다. .NET 10에서는 `UnsafeAccessor`로 private struct 필드에 ref 접근하는 표준 기능을 사용할 수 있다. 예시는 다음 형태다.

```csharp
[UnsafeAccessor(UnsafeAccessorKind.Field, Name = "factorFromCoveringGas")]
static extern ref float CoveringGas(ref ShotReport report);
```

읽기는 공개 getter를 우선하고, 필요한 필드 쓰기는 박싱 없는 접근으로 바꾸는 것이 작은 범위의 최적화 후보다. API 사용 문법은 1.7 참조 빌드로 확인했으며, 런타임 바인딩과 명중률 결과 일치는 게임에서 별도로 검증해야 한다.

이 최적화 자체가 1.6에서 불가능했던 것은 아니다. Harmony의 필드 접근 delegate 등 다른 수단이 있었다. 1.7에서는 표준 런타임 기능으로 구현할 선택지가 생긴 것이다.

## 우선순위 3: 텍스처 원본을 다시 읽는 비용과 메모리 수명 조정

현재 무기 아이콘과 부품 이미지 코드는 `Graphics.Blit → RenderTexture → ReadPixels → GetPixels32` 경로를 쓴다. 방어구 미리보기는 읽기 불가능한 텍스처에 대해 원본 크기 버퍼도 만든다. 무기 아이콘 쪽은 이미 256px 크기 제한, 캐시, 프레임 작업 예산을 갖추고 있으므로 그 장점을 보존해야 한다.

1.7에서 확인한 API:

```text
UnityEngine.Texture2D.CoreTexture
Waylith.Rendering.Texture2D.CpuData
Waylith.Rendering.Texture2D.TryGetCpuMip0()
Waylith.Graphics.Textures.TexturePixelData.GetRgba32OrNull()
Verse.GlobalTextureAtlasManager.LeavesSourceEvicted(...)
```

적용 제안은 **이미 CPU에 있는 RGBA 데이터부터 읽고, 없을 때만 기존 경로를 쓰는 것**이다. 전체 색상 복사 대신 알파 경계나 축소된 알파 마스크만 보관하면 후속 선택·배치 UI에서도 재사용할 수 있다.

주의할 점은 1.7이 아틀라스 원본과 CPU 데이터를 퇴거할 수 있다는 것이다. CPU 데이터가 항상 존재하거나 RGBA32라고 가정하지 않는다. 압축 포맷, 상하 방향, premultiplied alpha, 재로딩 수명도 확인해야 한다. 원본 CPU 데이터를 강제로 계속 붙잡으면 엔진의 메모리 절감과 충돌할 수 있다. 새 native API가 기존 stub보다 항상 빠르다는 결과도 아직 없다.

## 우선순위 4: 큰 전술 계산을 스냅샷 기반 작업으로 분리

`Waylith.Jobs.WaylithJobRuntime`에서 다음을 확인했다.

```text
Schedule(Action, ReadOnlySpan<int> dependencies, int timeCostEstimate)
ScheduleFor(int start, int end, Action<int> action, int batchSize, int dependsOn)
IsCompleted(int handleId)
Complete(int handleId)
CombineDependencies(...)
IWaylithJob / IWaylithParallelForJob
```

일반 C# 작업과 배열·리스트 대상 병렬 작업, 의존성 연결이 가능하다. 공식 문서상 Unity Burst의 제한된 작업 형식에 맞출 필요가 줄었다. 반면 일반 멀티스레딩 자체는 1.6에서도 가능했다.

현재 `TacticalPlanPreparation.cs`, `TacticalLocalPlan.cs`, `TacticalRoomClearing.cs`는 메인 스레드에서 반복자를 여러 틱에 나누어 진행한다. `CreateRoomScan`의 콜백은 Map 조회, 지붕·건물 조회와 LOS 판정을 포함한다. 이를 그대로 작업 스레드에 넘기면 안 된다.

권장 분리는 다음과 같다.

```text
메인 스레드: 필요한 로컬 지형·관측·대원 위치·예약 상태를 스냅샷으로 수집
    ↓
작업 스레드: 변경하지 않는 배열에서 후보 점수·연결성·배치 계산
    ↓
메인 스레드: 명령/계획 버전과 대상 상태를 재확인한 뒤 예약·이동·Job 반영
```

스냅샷 비용도 계산에 포함한다. 전체 맵을 매번 복제하지 않고 해당 계획의 로컬 범위를 쓴다. 작은 방, 소수 후보, 대원 두 명의 좌석 배정은 현재 분할 처리보다 스케줄링 비용이 클 수 있다. 게임을 저장하거나 맵을 제거할 때 작업 결과를 폐기·정리하는 수명 규칙도 필요하다.

완료 직후 무조건 `Complete()`로 기다리면 메인 스레드 지연을 옮기는 데 그칠 수 있다. 기존 Pending 준비 상태와 연결해 나중에 수거하고, 결과는 고정된 순서로 반영한다. 전역 Rand나 실시간 Map/Pawn 변경을 작업에서 사용하지 않는다.

가스는 `byte[][]` 데이터라 계산 분리 후보지만, 현재 확산은 이웃 셀을 즉시 갱신하고 CellTick은 게임 상태에 영향을 준다. 단순 Parallel.For 적용은 경합과 결과 변경을 만든다. 검토한다면 이전/다음 밀도 버퍼 또는 충돌 없는 작업 분할과 메인 스레드 효과 반영부터 설계해야 한다. 틱별 확산 결과·질량·효과 발생 시점이 검증 기준이다.

## 우선순위 5: 계산 예산을 없애기보다 처리 지연을 재조정

`TacticalWorkBudget.cs`는 1.5ms 누적 시간과 Job 2개, 경로 4개, 계획 1개, 관측 1개 같은 고정 제한을 함께 사용한다. `TacticalCommands.cs`도 한 틱에서 최대 두 분대만 실제 처리한다. `TacticalRoomScan.CellsPerStep`은 128이다.

CoreCLR에서 한 계산이 빨라져도 이 고정 개수 제한은 그대로다. 따라서 CPU 여유 증가가 곧바로 전술 반응 속도 향상을 뜻하지 않는다. 1.7 측정 후 제한 때문에 기다린 틱 수와 긴 프레임을 같이 비교해 개수·분할 크기를 조정한다. 작업 스레드 계산에는 별도의 동시 작업 수·메모리 예산도 필요하다. 시간 제한을 제거하거나 하드웨어별 제한을 무작정 키우는 방향은 권하지 않는다.

## 시각 효과와 로딩 구조에서 열린 선택지

- `ShaderDef`와 `MaterialDef`, GLSL 소스 로딩으로 Unity 에디터에서 셰이더 번들을 만드는 과정 없이 새 효과를 개발할 수 있다. SSBO·instancing 경로도 공식 문서에 설명돼 있다. 이는 API/제작 경로의 변화이며 instancing 자체가 1.6에서 불가능했던 것은 아니다.
- 현재 손전등은 폰을 순회하며 cone/pool mesh를 그린다. `Waylith.Rendering.MeshBatchRenderer`도 존재하므로 엔진의 실제 배칭 결과부터 확인한다. 수동 instancing 전환의 이득을 선언만 보고 단정하지 않는다.
- `GlowGrid.RegisterCustomGlower`는 실제 밝기장을 추가하려는 기능에 쓸 수 있다. 현재 손전등은 시각 효과이므로 이 API를 쓰면 게임플레이 의미도 달라진다. 성능 수정 명목으로 밝기 효과를 추가하지 않는다. 이동할 때마다 재등록하는 비용도 별도 측정 대상이다.
- `-BakeModAssetPacks`로 Assets.zip을 만들고 `-ColdBoot`로 캐시가 없는 로딩을 비교할 수 있다. 새 아틀라스·텍스처 캐시와 함께 로딩 및 메모리 최적화 후보이다. 틱 연산 최적화와는 구분한다.
- `-mod=...`, `-Headless`, `-NoWindow`를 이용하면 모드 구성·기능 시험·렌더링 시험을 분리하기 쉬워진다. 렌더링 검증은 그래픽을 초기화하지 않는 Headless 시험으로 대체하지 않는다.

## 빌드로 확인한 전환 범위

전체 제품 C# 소스를 별도 검토 프로젝트에 포함해 `net10.0`, 1.7 참조 DLL, 설치된 1.7용 Harmony 3으로 빌드했다. 원래 csproj와 Assemblies는 수정하지 않았다.

| 조건 | 결과 |
|---|---|
| C# 13 지정 | 빌드 성공, 경고 0 / 오류 0 |
| SDK 기본 C# 14 | CompOilProducer.cs:118의 `field` 변수명 충돌, CS9273 1개 / CS9258 경고 5개 |
| 새 API 사용 예제 포함, C# 13 | 빌드 성공, 경고 0 / 오류 0. 작업 스케줄러·프로파일 scope·native 텍스처 접근·custom glower·UnsafeAccessor 선언 문법 확인 |

C# 14 전환 시 `OilField` 속성 내부의 `field` 지역변수를 `oilFieldRecord` 같은 이름으로 바꾸면 된다. C# 13 고정은 이번 검토에서 다른 오류를 분리하기 위한 방법이며 제품의 최종 전환 결정은 아니다. 참조 빌드 성공은 Harmony 패치 적용, Def 로딩, 그래픽 동작, 저장/로드와 성능 검증을 대신하지 않는다.

## 추가 관측: 실제 1.7.4995 rev309 (2026-11-01)

설치된 Assembly-CSharp/UnityStubs/Waylith를 과거 1.7.4990 바이너리 및 메타데이터와 비교했다. 게임에는 LoadedModManager의 생성 closure 추가가 있었고, stubs에는 SystemInfo/ModLoadingHooks, Waylith에는 오디오·메모리 보고·queue 선택·압축·프로파일러의 변경이 있었다. 원시 비교는 `.codex-staging/migration17/api-4995/`에 보존한다. 이는 함수 본문 전체의 의미나 성능이 같다는 판정이 아니다.

확인한 공개 진단 연결점은 GraphicsDevice.SubmitOutOfMemoryRetries getter다. EngineApplication.GraphicsDevice를 통해 현재 장치에서 읽을 수 있는 API이므로 후속 리소스/배칭 측정에서 OOM 재시도와 긴 프레임·캐시 사용량의 연관을 조사하는 후보로 둔다. 현재 메모리 최적화나 성능 향상을 실측한 것은 아니다. GpuMemoryReport에 추가된 GetDeviceLuid/AppendProcessCommitment는 private이므로 새 모드용 공개 API로 계산하지 않는다. 이 진단 확장으로 4~7단계 완료를 선언하지 않는다.

현재 실제 호스트에서는 native 기하 36개·런타임 14개·M167 7개와 최종 재빌드 Main 시작/저장 7개 검사가 통과했다. 전체 UI/최종 프레임·추가 모드 조합은 해당 단계의 검증 범위를 따른다.

### 실제 맵 소유 구조 확인

현재 1.7.4995에는 Map.spawnedThings와 Map의 IThingHolder 진입점이 있다. Thing.SpawnSetup 본문은 새 thing을 map.spawnedThings에 넣으며, GenSpawn.Spawn은 그 전에 기존 holdingOwner에서 제거한다. 따라서 착지해 정상 spawn된 폰에도 holdingOwner가 있고 ParentHolder가 맵일 수 있다. 항공기/운반 container에서 벗어났는지는 !Spawned일 때의 owner와 구분해 판단해야 한다.

MH-60 실제 검사에서 착지 틱이 기대값과 같았지만 holdingOwner null 가정이 실패해 이 동작을 확인했다. 맵 owner 일치·항공기 holder 제거·실제 새 저장/재개를 검사한 후 통과했다. 본문 증거는 `.codex-staging/migration17/api-4995/Thing.cs`, `GenSpawn.cs`, `ThingOwner.cs`에 보존했다. 이는 해당 로컬 엔진에서 확인한 소유 계약이며 메타데이터 이름만으로 추정한 구조가 아니다. 기존 1.6 API와의 모든 소유권 차이를 이 한 사례로 일반화하지 않는다.
