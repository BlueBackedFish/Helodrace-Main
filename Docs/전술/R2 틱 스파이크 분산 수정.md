# R2 틱 스파이크 분산 수정

2026-10-08. [원인 분석](R2%20틱%20스파이크%20원인%20분석.md)의 세 후보에 대해 새 엔진이 유발하는 작업 전환과 경로 요청의 몰림을 줄였다. 바닐라 폰 처리 전체를 교체하거나 모든 긴 단일 호출을 제거한 변경은 아니다.

## 변경

1. **분대 완료 시 바닐라 반환 분산.** `Enter → Returning → Complete`로 진행한다. 모든 맵이 공유하는 예산에서 한 틱에 최대 1명만 소유 Job을 종료하고 바닐라의 다음 행동 검색으로 넘긴다. 분대 전체가 반환될 때까지 입구·자리 사용권을 유지한다. 실패로 임무를 해제하는 경우도 같은 반환 절차를 사용한다. 맵 제거는 다음 행동 검색 없이 즉시 소유권을 정리한다.
2. **새 작업 및 후속 판단 유발 횟수 제한.** 작업 발행과 반환을 합쳐 틱당 최대 2회다. 예산이 없으면 기존 작업을 유지하고 분대 판단을 다시 예약하며, 불필요한 새 Job 생성도 피한다. 이동 정지 복구는 바닐라 행동 검색을 사이에 넣지 않고 지정 자리 Job으로 직접 교체한다. 분산 대기 중에도 계획 재시도 240틱 간격은 보존한다.
3. **이동 전환·초기 계획 분산.** 스택 이동, 해머 접근, 진입의 외부/개구부/첫 실내/최종 자리 이동 앞에 예산 대기를 둔다. 모든 맵·폰이 공유하는 틱당 최대 4회의 전술 이동 단계 시작과 최대 1회의 신규/재사용 계획 검사로 제한한다. 바닐라 경로 탐색을 수정하지 않고 요청의 동시 발생을 줄인다. 이미 이동 중인 바닐라의 자체 재경로 요청은 이 제한의 직접 대상이 아니다.

완료한 동기 작업의 경과 시간을 누적해 1.5ms를 사용한 틱에는 나머지 작업을 미룬다. 단일 계획/바닐라 작업 내부를 선점하는 상한은 아니다. 이동·반환에 몇 틱의 지연이 생길 수 있으며, 길찾기 자체는 기존 바닐라 이동을 사용한다.

보조적으로 새 엔진의 조직 재평가는 한 틱 최대 2개 조직/4개 due 확인으로 분산했다. 누락 등록 확인도 300틱 간격의 전체 단일 스캔 대신 한 틱에 한 전술 단위를 확인하는 순회로 바꿨다. Vanilla/Legacy의 기존 조직 재평가 주기는 유지한다.

구현은 [TacticalWorkBudget](../../Source/Helodrace/Tactics/TacticalWorkBudget.cs), [TacticalCommands](../../Source/Helodrace/Tactics/TacticalCommands.cs), [TacticalJobs](../../Source/Helodrace/Tactics/TacticalJobs.cs), [조직 레지스트리](../../Source/Helodrace/Squads/OrganizationRegistry.cs)에 있다. 새 엔진 활성화 인수는 계속 `-hdTacticalEngine=new`다.

## 약식 검증

빌드 경고/오류 0, 실제 게임 바인딩 검사와 새 전역 예산의 반환/발행/이동/계획 제한·틱 초기화·경과 예산 초과 후 재개 검사가 통과했다.

게임은 LOW 실제 204명/17분대, 닫힌 외벽, fixture v9, 동일 시드와 지도/폰 지문, 준비 1,200틱/측정 1,200틱의 짧은 사례로 확인했다. 첫 구현 1회에서 분대 판단 최대가 1.4ms까지 줄었지만 대기 중 계획 재시도 횟수가 248회로 늘었다. 재시도 간격 보존을 보완한 **최종 DLL을 1회 더** 실행해 134회로 돌아온 것을 확인했다. 전체 행렬이나 반복 CPU 합격 검사는 실행하지 않았다.

| 측정 | 수정 전 약식 | 최종 약식 |
|---|---:|---:|
| 지휘 Tick 호출 최대 ms | 21.400 | 1.213 |
| 분대 Advance 호출 최대 ms | 21.398 | 1.211 |
| 전술 EndOwned 호출 최대 ms | 3.068 | 0.984 |

| 조직 Tick 호출 최대 ms | 0.195 | 0.057 |

| 바닐라 TryFindAndStartJob 호출 최대 ms | 18.433 | 14.818 |

최종 수집은 1,200틱 완료/누락 0/수집 중 예외 0이다. 종료 시 6개 분대가 진입 및 반환을 마쳤고, 72명이 개구부를 통과했으며 작업 실패는 0회였다. 8개 분대에 계획이 있고 다른 분대는 계속 진행/대기 중이다. 짧게 종료한 시험이므로 17개 분대 전원 완료와 물리 계획 전체 검사는 false로 보존한다. 이를 전체 기능 완료나 정식 CPU 합격이라고 하지 않는다.

위 메서드 값은 경과 시간이다. inclusive 부모/자식을 합산하지 않는다. Core 기준은 `GenRadial.NumCellsInRadius` 10,000회 배치이며 CPU 점유율이 아니다. 실제 틱 CPU는 수정 전 5.156ms/틱, 최종 4.141ms/틱으로 관측됐다. 수정 전에는 고빈도 방 갱신 검사 등을 계측했고 수정 후에는 실제 경로 처리 경계를 선택했으므로 계측 대상이 다르다. 원본 조건의 지도/폰 지문은 같지만, 이 단일 실행의 CPU 감소를 엄밀한 개선율이나 바닐라 대비 2배 판정으로 확정하지 않는다.

## 남아 있는 문제

전술 판단의 분대 일괄 전환 스파이크는 이번 창에서 줄었다. 그러나 **전체 틱 최대는 오히려 46.8ms**였고 TickList 최대는 46.3ms다. 바닐라의 단일 다음 행동 검색도 14.8ms가 남았다. 전술 코드에서 유발하는 호출을 나눴어도 일반 폰 처리의 긴 호출은 계속 발생하므로 전체 스파이크 해결을 선언하지 않는다.

최종 창에서 `PathFinderTick` 최대는 0.520ms, `ForceCompleteScheduledJobs` 최대는 0.026ms였다. 이번 준비 후 창에서는 경로 완료 대기가 주 병목으로 드러나지 않았다. 초기 계획과 JIT 비용의 상한을 증명한 시험은 아니며, 신규 계획 내부의 긴 단일 호출 가능성은 남는다.

이후 큰 스파이크가 지속되면 일반 폰의 다음 행동 검색 내부를 짧게 좁혀 조사한다. 이번 작업에서는 바닐라 AI 전역 후크, 추가 워커, 전체 방 캐시를 도입하지 않았다.
