2026-10-11 사용자 요청으로 정기 성능 수집·반복 CPU 게이트·최종 성능 행렬을 계획에서 제외했다. 아래는 당시 절차와 측정 해석을 보존한 기록이며 현재 실행 지침이나 완료 조건이 아니다.

# 최적화 전술 AI 검증 기준

2026-10-08. [로드맵](../../최적화%20전술%20AI%20로드맵.md)의 각 단계에서 적용한다. R1 대조 실행/수집·검증을 완료했으며 [결과](../../R1%20대조%20실행과%20격리%20검증%20결과.md)를 보존했다. R2 최소 돌파·진입의 최종 30회 검증도 완료했으며 [R2 결과](../../R2%20최소%20돌파%20진입%20구현과%20검증.md)에 범위와 합격 조건을 기록했다. 후속 작업은 아래 약식 검증을 기본으로 한다. 정식 CPU 합격 조건은 최종 검증용으로 유지한다.

## 기본 검증은 약식으로 진행

2026-10-08 사용자 지침: 테스트에 드는 시간을 줄인다. 이후 작은 수정뿐 아니라 후속 단계 작업도 변경한 부분의 짧은 검증을 기본으로 하고, R2처럼 전체 행렬을 매번 반복하지 않는다.

- 코드 변경에 필요한 빌드와 관련 검사만 실행한다. 문서만 바꾸면 내용·링크·diff 확인으로 끝내고 게임을 실행하지 않는다.
- 실제 게임 확인이 필요하면 변경한 행동을 보여 주는 대표 사례 1개를 1회 실행한다. 기본은 한 분대이며, 다중 분대 문제가 대상이면 필요한 규모만 사용한다. 여러 기능을 한 사례에서 확인할 수 있으면 합친다.
- 성능 검증은 관련 메서드 소수와 Core 기준, 전체 틱 CPU/경과 시간만 짧게 수집한다. 측정 창은 우선 1,200틱으로 하고, 필요한 행동이 창 안에서 발생하도록 준비한다. 평균·호출 수·p95/p99/최대와 실제 진행 여부를 기록한다. 행동을 관측하지 못한 창은 기능 검증으로 인정하지 않는다.
- 최근 같은 조건의 결과가 있으면 참고하고, 직접 대조가 필요한 경우에만 변경 전/후 또는 Vanilla/New를 각 1회 수집한다. 다른 DLL·조건의 수치를 엄밀한 대조로 합치지 않는다.
- 200명급 시험, 모든 사례, 3회 반복, 비계측 대조, 원본 전체 재대조는 기본 작업에 넣지 않는다. 대규모 스파이크를 고치는 작업이면 해당 규모의 짧은 1회 측정만 우선한다. 실패나 새로운 우려가 없으면 검사를 더 늘리지 않는다.
- 약식 결과는 회귀 확인 또는 성능 경향으로 보고한다. 1회 결과를 기존 CLI의 정식 3회 반복 CPU 합격으로 표기하지 않는다. 전체 반복 행렬은 사용자가 요청하거나 R7 최종 통합 검증을 진행할 때 실시한다.

## 대조군과 2배의 의미

주 지표는 게임의 `DoSingleTick` 구간 **메인 스레드 user+kernel CPU 시간 / 실제 처리 틱 수**다. 같은 테스트 조건에서 반복 실행의 중앙값을 비교한다.

```text
V = 전술 확장이 비활성인 바닐라 습격의 평균 메인 틱 CPU ms/tick
N = 새 전술 AI를 활성화한 습격의 평균 메인 틱 CPU ms/tick
합격 목표: N / V ≤ 2.0
```

분모는 Core 기준 배치, 과거 Legacy AI, 전체 바닐라 게임의 모든 메서드 합계가 아니다. 같은 모드/장비/폰 생성과 조직 메타데이터를 유지하고 전술 엔진만 달리한다. Legacy도 따로 측정해 이전 대비 개선을 보여 주지만 2배 판정에는 쓰지 않는다. 사용자의 기존 5~6배 관측과 새 fixture 결과는 구분해 기록한다.

일반 습격의 열린 경로 이동과 공병 습격의 직접 돌파는 별도 시나리오로 비교한다. 신형 돌파 AI와 벽 앞에서 멈춘 일반 습격을 비교하거나, 신형의 영구 대기를 정상 바닐라 진행과 비교하지 않는다. 공개할 주 바닐라 대조는 시나리오별로 미리 정하고 실행 뒤 유리한 분모로 바꾸지 않는다.

## 함께 보고할 값

| 값 | 쓰임과 한계 |
|---|---|
| 전체 틱 메인 CPU ms/tick, N/V | 실제 합격의 중심. 짧은 메서드별 CPU 귀속과 구분 |
| 전체 틱 경과 ms/tick, p95/p99/max | 틱 지연·긴 호출. CPU 시간과 같은 값이 아님 |
| 틱 밖 메인 전술 CPU/경과 시간 | MapComponentUpdate, 스냅샷/결과 적용 등으로 비용을 옮겼는지 확인 |
| 프로세스 CPU/틱, 워커 CPU·큐 대기 | 다른 스레드로 옮긴 비용과 코어 포화 확인 |
| 관련 메서드 총 경과 시간·호출 수·평균·max/p95/p99·호출/틱 | 단계 변경의 국소 원인 확인. 부모·자식 inclusive 합산 금지 |
| Core 배치 대비 메서드 비용/틱·호출 | 환경 차이를 줄이는 기존 기준. CPU 점유율이나 N/V가 아님 |
| 완료율·완료 틱·이동/Job/경로 요청 수·실패/재시도 | 싸게 멈춘 실행과 잦은 길찾기 증가를 발견 |
| 큐 최장 지연·연령별 미처리 수·보고/관측 신선도 | 예산 분산이 영구 대기/반응 소실로 이어지는지 확인 |

틱 밖 추가 메인 작업이 있으면, 바닐라에도 동일한 경계를 적용해 **전체 측정 창의 메인 CPU/처리 틱**을 보조 합격 지표로 비교한다. 이 값도 2배 이내여야 한다. 현재 수집기가 이 경계를 측정하지 못하면 먼저 수집을 보완하며, 틱 구간만 통과한 결과를 최종 합격이라 부르지 않는다. 일반 렌더링/일시정지 구간은 같은 창 조건으로 통제한다.

현재 도구의 Core 기준은 `Verse.GenRadial.NumCellsInRadius(float)` 10,000회 고정 배치다. 반지름 `8+(i%16)`, 준비 호출, 배치 중앙값을 유지한다. 메서드 경과 비용은 `누적 경과 ms / 틱 수 / 기준 배치 ms ×100`으로 보고한다. 실제 CPU ms와 이 경과 시간 비율을 같은 단위로 섞어 합산하지 않는다. Core 보정은 작업량·GC·스케줄링 차이를 없애 주지 않는다.

현재 프로파일러의 실제 스레드 CPU 수집은 `DoSingleTick`에만 적용되고 대상은 메인 스레드다. 메서드 p95/p99는 마지막 2048회 호출의 분포다. 워커 CPU/틱 전체 분포를 이미 수집한다고 가정하지 않는다. R1에서 필요한 보조 수집 범위를 확인하고 부족한 항목은 미측정으로 명시한다.

## MapComponentTick와 다른 메서드의 수집 범위

맵 컴포넌트 비용은 필수 확인 대상이다. 로컬 바닐라 코드에서 확인한 호출 관계는 `TickManager.DoSingleTick → Map.MapPostTick → MapComponentUtility.MapComponentTick → 각 컴포넌트의 MapComponentTick`이다. 따라서 이 경계 안의 컴포넌트 비용은 전체 틱 CPU에 이미 포함된다. 개별 콜백과 내부 메서드를 따로 계측해 어느 컴포넌트가 비용을 만드는지 분해한다. 부모인 전체 틱과 자식 컴포넌트 시간을 더하지 않는다.

`MapComponentUpdate`는 `Map.MapUpdate`에서 실행되고 `GameComponentUpdate`도 프레임 측 작업이므로 전체 틱만 수집해서는 해당 비용을 확인할 수 없다. R7 구형 제거 후에는 신규 명령 스케줄러와 실제 남아 있는 Map/GameComponent의 Tick/Update를 확인한다. 구형 계획·이동 영역·지도 분석 컴포넌트는 제거 대상이며 정상 실행에 남겨 측정하지 않는다. Dubs 화면의 `MapComponentTick`이 전체 컴포넌트 호출기인지 개별 구현인지도 구분한다.

현재 [프로파일러 등록 코드](../../../../Source/Helodrace/Profiling/AgentMethodProfiler.cs)는 Helodrace Map/GameComponent의 구체적인 Tick/Update 구현을 기본 선택한다. 이전 Raid 이름 필터를 제거했고 수집기 자신과 감사 도구는 제외한다. 모든 모드/Unity 메서드를 자동 선택하는 것은 아니다.

| 범위 | 현재 지원과 확인 방법 |
|---|---|
| 신규 전술 스케줄러·분대 실행·통신 | `GameComponent_TacticalCommands.GameComponentTick`, `MapComponent_TacticalCommands.Advance/AdvanceCore/ReturnMembers`, `TacticalCommunications.Pump` 기본 등록 |
| 신규 관측·연락 협력·방 정리·야전·치료·Job 발행 | detailed에서 `ScanContacts/RespondToContacts/AdvanceCoordination/AdvanceRoomClear/AdvanceFieldResponse/AdvanceMedicalCare/Issue` 추가 등록 |
| 구형 계획·이동 영역·지도 분석·통신 컴포넌트 | R7에서 제거. 과거 결과의 대상이며 현재 등록 목록에 없어야 함 |
| `Helodrace.Squads.GameComponent_CombatOrganizations.GameComponentTick` | 기본 등록. 공통 조직 유지 비용도 확인 |
| `Verse.Map`의 PreTick/PostTick/Update | 기본 등록으로 맵 처리 상위 구간 확인 |
| `Verse.MapComponentUtility`·`Verse.GameComponentUtility`의 Tick/Update 호출기 | 기본 등록. 전체 컴포넌트와 개별 콜백 중복 합산 금지 |
| Pawn·Job·PathFinder 등의 바닐라 메서드 | 실제 선언 타입과 메서드 이름을 추가 지정. 지휘 비용 감소가 바닐라 재경로 비용 증가로 바뀌는지 확인 |
| 다른 모드/Unity DLL·워커 메서드 | 현재 추가 대상 어셈블리 제한 또는 메인 스레드 전용 수집으로 직접 지원하지 않음. 필요하면 R1의 수집 보완 범위로 분리 |

추가 선택은 실행 인자 `-hdMethodProfileTargets=타입::메서드;타입::메서드` 또는 감사 실행기의 `-ProfileTargets`로 가능하다. 기본 콜백에서 비싼 구간을 찾은 뒤 내부 처리와 바닐라 작업을 추가한다.

```text
Helodrace.Tactics.MapComponent_TacticalCommands::AdvanceRoomClear;
Verse.AI.Pawn_JobTracker::StartJob;
Verse.PathFinder::CreateRequest
```

위 목록은 한 줄의 세미콜론 구분 값으로 전달한다. 메서드는 초기화 때 등록되므로 새로운 대상을 추가하려면 게임을 다시 실행한다. CLI `search`/`capabilities`는 등록된 대상 확인용이며 실행 중 임의 메서드 패치를 추가하는 기능이 아니다.

현재 추가 대상은 Helodrace 또는 Assembly-CSharp의 구체적 메서드 본문으로 제한된다. public/private, static/instance는 선택할 수 있고 같은 이름의 오버로드는 함께 등록된다. 상속받은 메서드는 실제 선언 타입을 지정해야 한다. 빈 기반 MapComponent 메서드만 측정해서 개별 override 비용을 알 수 있다고 보지 않는다. 전체 등록 상한은 기본 대상 포함 128개라 필요하면 묶음을 나눠 수집한다.

메서드별 총 경과·호출·평균·최대·p95/p99·Core 비율은 현재 도구로 확인 가능하지만 **각 메서드의 실제 OS CPU 시간은 현재 수집되지 않는다.** `cpuMeasured=false`의 0을 무비용으로 해석하지 않는다. R1에서는 전체 CPU 판정, 구체적 컴포넌트/내부 메서드의 경과 시간 분해, 틱 밖 작업 측정을 구분한다. 저빈도 전체 호출기와 비싼 내부 작업부터 좁혀 짧은 메서드 과다 계측을 피한다.

## 실험 절차

1. 엔진 선택만 다른 Vanilla/New로 지도·생성 시드·실제 인원·편제·장비·무전 보유·목표·진입 방식·배속·게임 버전·모드 목록을 고정한다. 지도 해시와 DLL SHA256를 기록한다. Legacy 실행은 R7에서 제거하며 과거 비교 기록만 보존한다.
2. 생성/처음 계획/돌파 시작의 cold 구간과 준비 후 steady 구간을 분리한다. 기존 기본 준비 600틱/측정 1200틱부터 시작하되 새 AI가 측정 전에 모든 작업을 끝내는 fixture는 길이/전장을 조정한다.
3. 고정 틱 창의 CPU와 전체 목표 완료까지의 CPU·틱 수를 둘 다 기록한다. 엔진별 종료 단계는 달라도 실제 작업 진행을 보여 준다. 정지한 구간만 골라 비교하지 않는다.
4. 최소 구현 R2는 한 분대 기능 시험 → 약 50명 → 약 200명 순서다. High는 13인 단위의 실제 52/208명 등을 기록하며 LOW 50/200명과 같은 인원이라고 쓰지 않는다.
5. 후속 작업은 위 약식 검증을 기본으로 한다. 정식 최종 검증 또는 사용자가 요청한 반복 대조에만 동일 조건 최소 3회와 교대 실행을 적용하고 중앙값·반복 범위를 보존한다.
6. 프로파일러 비활성 대조도 측정해 계측 자체 영향을 확인한다. 상세 타깃은 병목 진단용 별도 실행에만 넓히고 최종 CPU 판정과 섞지 않는다.
7. 실패/사상자/불완전/조건 불일치/무진행 기록은 원본을 보존하고 제외 이유를 쓴다. 교전 시험의 사상자는 기능 결과로 별도 보고하며 다른 생존 인원 조건의 비용을 동일 그룹으로 묶지 않는다.

실제 저장/로드 기능 시험은 `-NoMethodProfile`로 실행한다. 프로파일러의 전역 활성 세션은 새 게임/맵 수집기 인스턴스로 자동 승계되지 않으므로 로드를 가로지르는 계측은 지원하지 않는다. 해당 잘못된 조합은 런처에서 거부한다. 메서드 등록·실행 수집은 저장하지 않는 별도 실행으로 확인하며, 저장 비용과 재시작한 틱 창을 최종 CPU 비교에 섞지 않는다.

기존 실행기의 quicktest·관련 메서드 선택·반복 수집·검사 후 비교는 재사용 후보다. R1에서 새/구형 전술뿐 아니라 조직 관리·지도 분석·전체 컴포넌트 호출기·틱 밖 작업의 수집 목록을 먼저 확정한다. 현재 비교기는 엔진/시작 단계 차이를 거부할 수 있으므로 비교 허용 조건을 명시적으로 조정한다. 기존 JSON에서 단순히 metadata를 지워 통과시키지 않는다. 그 변경은 R1 구현 범위다.

## 기능과 부하 행렬

R7의 1/3배속 비교는 `-Speed 1` 또는 `-Speed 3`으로 요청하고, 실제 `TickRateMultiplier`의 표본 최소/최대가 요청과 같은지도 검사한다. 바닐라는 전투 감속을 통해 Fast 설정에서도 1배속이 될 수 있으므로, CLI 격리 시험에만 `DebugViewSettings.neverForceNormalSpeed`를 켜고 `r7AutoSlowdownDisabled`를 기록한다. 일반 플레이 설정은 변경하지 않는다. 요청 배속과 실제 배율, 벽시계 기준 실제 TPS를 구분한다. 배율이 달라지거나 통제 증거가 없는 현재 R7 수집은 정식 CPU 자료로 사용하지 않는다.

큐 지연·due 명령 수·단계 체류는 기존 30틱 진행 표본에서 기록한다. 표본 최대값은 정확한 모든 틱 최대나 백분위수가 아니며, 단계 체류에는 전술 작업 대기가 포함된다. 0명 조건은 임의 진입 성공을 만들지 않고 명령·작업 발행·스케줄러 판단이 실제 0인지 별도로 검사한다.

| 상황 | 주 확인 | 처음 필요한 단계 |
|---|---|---|
| 열린 야외, 일반/공병 습격 각각 | 같은 목표 진행, 기본 폰/Job 비용 대비 추가 비용 | R1~R2 |
| 한 겹 외벽/일반 문, 좁은 방, 바위/코너 | 연결 스택·돌파·벽 파괴 후 진입, 현재 방 목표 처리 | R2~R3 |
| 기존 먼 문이 열려 있는 외벽 | 새 개구부로 선두와 후미가 통과, 입구 겹침/긴 우회 없음 | R2 |
| 여러 분대가 같은 입구/서로 다른 입구 | 대기 지연, 진행/중복 자리, 후속 분대 정지 없음 | R2 / 협력은 R5 |
| 관측 적/문 위 적, 작은 실내/야외 | 관측 복귀, 수류탄/연막 선택, 2칸 거리, 폭발 전 진입 금지 | R3~R4 |
| 공병 다운/사망, 장비 지면/사상자 | 대체 작업자·회수·현재 임무 지속, 재시도 폭주 없음 | R3 |
| 새 구멍·이미 확보한 방·미관측 반대편 문 | 국소 복구, 완료 이력 유지, 불필요 재돌파/왕복 없음 | R3~R4 |
| 후방 적·다른 문 적 후퇴·복도 앞뒤 적 소실 | 마지막 위치 기억/경계/재확인, 숨은 추적 없음 | R4 |
| LOW 분리/재접촉, High 무전 제거/고장 | 보고 지연/단절, 연락 없는 새 정보 유입 없음 | R5 |
| 다중 입구 합의·아군 실내 조우 | 시작/실패·승계, 식별 지연, 투척 충돌 방지 | R5 |
| 사거리 밖 접근·고정 기총/저격·지원 요청 | 엄폐 준비·이동 중 대응·분대 계획 연막·임무 복귀 | R6 |
| LOW 활 모양 대형, High 3화력조 | 중앙 화력 집중, 실제 엄호 준비 후 교대 기동 | R6 |
| 다중 맵, 0명·1분대·50/100/200/400명급, 1/3배속 | 인원/활동 분대 수에 따른 CPU 곡선, 여러 맵의 총 예산 공유 | R7 |
| 전투 중 저장/로드, 철수/종료 후 0명 | 진행 복구, 조직 정보 해제, 잔존 캐시/큐/이동 영역 갱신 없음 | R7 |

통제된 무사상자 부하 시험과 실제 교전 시험을 분리한다. 기존 `moved ≥95%`는 보조 지표로만 사용하며 집결·개구부 통과·방 정리의 완료를 대신하지 않는다. 늦은 인원 각각의 필수 통과 성공과 영구 정지 여부를 확인한다.

## 예산 가설과 통과 규칙

정규화된 작업 예산은 우선 새 지휘·계획·관측·통신 자체를 **바닐라 틱 CPU의 약 0.5배 이내**로 제한하는 안부터 시험한다. 남은 약 0.5배는 추가 전용 Job·길찾기·안전 처리의 여유로 본다. 이 배분은 측정 전 가설이며 추가 작업이 실제로 여유 안에 들어간다고 보장하지 않는다. 평균 예산만 맞추고 단일 호출의 스터터링을 방치하지 않는다.

- 단계별 약식 확인에서는 필요한 실제 행동 완료와 비용 악화 여부를 우선 확인한다. N/V ≤2.0 목표는 유지하되 반복하지 않은 수치를 정식 합격으로 확정하지 않는다. 정식 CPU 판정에서는 틱 밖 메인 추가 비용도 포함한다.
- 전체 틱 p95/p99와 최대 지연은 모든 단계에서 보고한다. 2배는 평균 CPU 기준이며 p99까지 사용자 합격 조건이라고 바꾸지 않는다. 다만 새 긴 정지/복구 지연이 있으면 기능 확장을 보류하고 원인을 조사한다.
- 전체 목표 완료율과 진행 지연을 함께 본다. 아직 수치 합의가 없는 전술 반응 지연은 실제 틱 수로 보고하고, 임의로 수백 틱 대기를 무조건 합격 처리하지 않는다.
- 최종 R7은 완료된 기능 범위의 모든 대표 부하 시나리오에서 판정한다. 쉬운 한 방 시험만 통과한 것을 전체 CQB/야전/협력 2배 달성으로 선언하지 않는다.
- 메인 시간을 줄이기 위해 워커가 증가한 경우 실제 메인 CPU 감소와 프로세스 CPU 증가를 함께 적는다. 스냅샷·큐·적용 비용이 절감분을 소모하면 병렬화 우선순위를 낮춘다.

각 결과 문서에는 엔진/커밋/DLL/게임 조건, raw·Core 기준 지표, 진행/완료/실패, 제외 사유, 변경한 관련 메서드, 다음 병목을 기록한다. 원본은 새 결과 폴더에 보존하며 기존 측정 자료를 덮어쓰지 않는다.
