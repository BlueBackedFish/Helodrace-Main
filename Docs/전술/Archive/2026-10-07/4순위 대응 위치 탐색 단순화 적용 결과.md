# 4순위: 대응·엄폐 위치 탐색 상한과 계산 공유

2026-10-07. CPU 최우선 방침에 따라 야전 수비·저격 대응·폭발 회피가 사용하는 `FindReactivePosition`의 탐색을 단순화했다. 통신 최적화 이후의 구조를 기준으로 비교했다.

## 적용 내용과 희생

기존 방식은 반경의 모든 유효 칸을 수집하고 연결 BFS, 모든 칸의 LOS·엄폐·위험 점수, 전체 정렬, 최대 12후보의 경로 검사를 수행했다. 이제 현재 위치와 8방향 3개 거리의 최대 25후보를 사용한다. 후보 평가도 최대 32개로 제한하고, 상위 2후보만 실제 도달 가능성을 확인한다. 막혔을 때 전체 탐색으로 돌아가는 예외 경로는 없다.

계획과 4칸 단위 위협 좌표로 물리 점수 캐시를 공유한다. LOS·엄폐율·지형 비용은 최대 120틱 재사용한다. 최대 64문맥, 문맥마다 최대 1,024칸이며 습격 조직 소멸·맵 제거 때 정리한다. 실제 이동 비용 대신 맨해튼 거리를 사용한다.

현재 standable 여부, 점유·목적지 예약, 회피 함정, 같은 고정 방 여부는 후보마다 확인한다. 폭발 위험 점수는 가까운 4개 위험을 우선 사용하되, 최종 후보는 전달받은 모든 위험에 대한 현재 폭발 노출 여부를 검사한다. 최종 경로 검사도 메인 스레드에서 한다.

좋은 엄폐를 놓치거나 상위 두 후보가 막혀 현재 위치에 남을 수 있다. BFS 연결성 점수를 제거했으므로 멀리 돌아가는 경로를 과소평가할 수 있다. 이동 예약과 폭발 안전성은 오래된 캐시에서 가져오지 않지만, 위협의 작은 이동·엄폐/문 변화는 최대 120틱 늦게 반영될 수 있다. 이 품질 저하는 이번 CPU 우선 방침에서 허용한 범위다. 선택된 목적지를 매번 다시 만드는 동작은 추가하지 않았다.

## 관련 메서드 수집 결과

기존 프로파일러에 `FindReactivePosition`, `CoverReactiveTeam`, `FieldDefense` 세 메서드만 추가했다. coarse 기본 대상은 전체 틱 맥락 확인용이다. 일반 대기 시험에서는 탐색 호출이 없어, 샌드백이 있는 동일 맵에서 활성 분대에 지원 수비 요청을 주는 전용 시험을 추가했다. `-Reactive`로만 실행하며 일반 게임에는 적용되지 않는다.

LOW 200/400/0명, 같은 시드·맵, 1,800틱 준비와 900틱 수집이다. 처음 600틱 준비 시험은 활성 계획이 없어 실패했으며 성능 근거에서 제외했다. 유효 수집에는 실제 탐색 호출이 각각 200/397회와 200/400회 발생했다. 캡처 완료, dropped와 계측 메서드 예외는 모두 0이다.

다만 **이전 시험에는 사상자가 있어 엄격한 전후 비교 자격을 통과하지 못했다.** 아래 표는 원자료의 탐색적 비교다. 공식 `low-review.json`은 이 실패 사유를 보존하고, `low-comparison.json`의 인정된 비교는 0명 구간뿐이다. 표를 동일 전술 작업량이 보장된 개선율로 해석하지 않는다.

Core 100%는 각 캡처의 `GenRadial.NumCellsInRadius(float)` 10,000회 배치 7회 중앙값이다. 메서드 시간은 경과 시간이며, 짧은 메서드의 실제 CPU 시간을 별도 측정했다고 주장하지 않는다.

| 대상 | 이전 ms/틱 → 이후 | Core 대비 이전 → 이후 | 정규화 감소 관찰 |
|---|---:|---:|---:|
| 200명, FindReactivePosition | 0.1811 → 0.0304 | 66.48% → 11.03% | 83.4% |
| 400명, FindReactivePosition | 0.4044 → 0.0523 | 148.55% → 19.22% | 87.1% |
| 400명, CoverReactiveTeam | 0.5868 → 0.2295 | 215.57% → 84.42% | 60.8% |
| 400명, FieldDefense | 0.5930 → 0.2365 | 217.84% → 86.96% | 60.1% |

부모 메서드는 자식 탐색 비용을 포함하므로 표의 행을 더하지 않는다. 400명 Find의 총 시간은 364.32→47.09ms, 평균은 917.7→117.7µs/호출, p95는 1.143→0.165ms, p99는 1.661→0.226ms였다. 최대는 9.197→0.402ms, FieldDefense 최대는 21.100→3.421ms였다. 한편 200명 Find 최대는 5.288→8.314ms로 늘었다. 평균/상위 지연의 감소와 별개로 모든 긴 호출이 없어졌다고 말할 수는 없다.

새 Find의 200→400명 구간 비용은 0.0304→0.0523ms/틱이다. 호출은 수비 요청 직후에 집중되며 900틱 전체에 균일하게 발생하지 않는다. 0명에서는 세 메서드 호출이 모두 0이었다.

## 전체 틱 결과와 병렬화 판단

전체 `DoSingleTick` 실제 메인 스레드 CPU는 400명에서 **13.98→15.23ms/틱으로 증가**했다. 변경 전 생존 397/이동 396명, 변경 후 생존 400/이동 397명이며 시작 단계도 Complete와 CrossBreach로 달랐다. 200명도 전후 생존 199→200명, 종료 단계 차이가 있었다. 시험은 동일 시드여도 같은 실행 작업량을 보장하지 않는다. 따라서 전체 틱 개선은 이번 수집으로 입증하지 못했다. 해당 탐색의 관찰 절약량은 약 0.35ms/틱이며 전체 틱 시간의 일부다.

이번에는 워커를 추가하지 않았다. 전체 탐색을 유지한 채 워커로 이전하는 것보다 후보 상한으로 먼저 연산을 제거했다. 현재 남은 평균 비용은 약 0.05ms/틱이고, 최종 예약·도달성·안전 검사는 계속 메인 스레드에 필요하다. 이 크기에서는 상태 복사·큐·결과 검증을 추가할 실익이 작다. 이후 큰 다중 분대의 공동 엄폐 격자 계산이 새 병목으로 측정되면, 메인 스레드에서 값 배열을 만들고 워커에서 물리 점수만 계산하는 방식을 다시 검토한다.

## 검증과 자료

빌드 경고·오류 0. 순수 계산 검사 1,257개 및 실제 게임 클래스 바인딩 검사를 통과했다. 추가 검사에서는 안전/점유 우선순위, 막힌 최상위 후보의 한 번 대안 검사, 전체 탐색으로 되돌아가지 않는 상한, 작은 공간, 공유·만료·시간 역행·위협 방향 변경·문맥 상한, 조직 종료와 맵 제거 정리를 확인했다.

프로파일 DLL은 `f0c00031a8848205a50ba9ddb0a1a2d2aa624a1e768cf43a2678924d8099359b`다. 테스트 추가 후 빌드는 생산 코드가 같고 통신 커밋에 따른 AssemblyInformationalVersion이 바뀌어 `73be061b194ffe705ecc54b08e22ca2e0d5b607ced923992df0c72ef92225370`이 됐다. 최종 설치본은 후자다.

실제 이동 기능 시험은 비교용 DLL과 최종 DLL 재시험 모두 7단계를 통과했다. 열린 문·새 구멍·보이지 않는 문 변경·늦은 Security 합류·HC 연막·외벽 개구부·중복 자리 처리를 검사한다. 다만 최종 DLL 첫 시험은 **1단계에서 멈췄다.** `(119,116)`의 한 폰에서 Job·명령·assignment가 사라졌고 다른 폰에는 ContactGuard가 남았다. 2순위 검증에서도 유사한 최초 실패와 재시험 통과 기록이 있으나 같은 원인이라고 확정하지 않는다. 이번 최적화로부터 독립적인 문제인지도 미확정이다. 최초 실패·비교용 통과·최종 재시험 통과를 모두 보존하며, 간헐적 Security 멈춤의 원인 규명은 남아 있다.
