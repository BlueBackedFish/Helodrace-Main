# 전술 AI 계산량 축소 1차 구현 결과

작업: 2026-10-05~06. [구조 개편 검토](%EC%A0%84%EC%88%A0%20AI%20%EA%B5%AC%EC%A1%B0%20%EA%B0%9C%ED%8E%B8%20%EA%B2%80%ED%86%A0.md)의 A 계산량 축소 중 진입점·경로·다음 방의 반복 계획을 줄였다. 전체 개편이나 틱 지연 목표 달성 완료를 뜻하지 않는다.

## 적용한 변경

| 항목 | 이전 | 현재 |
| --- | --- | --- |
| 돌파 후보의 구조 검사 | 최대 400개 구조에서 후보 생성, 예비 대형 검사 반복 | 한 번에 최대 48개 구조의 기본 연결/도구 조건만 검사 |
| 상세 돌파 검사 | 예비 순위 후보를 검사하며 유효한 3개를 비교, 실패가 많으면 추가 검사 | 최대 8개 상세 검사, 실제 대형과 경로가 유효한 첫 후보 채택 |
| 실내 후보 연결 | 벽의 각 접근 방향마다 두 개의 국소 경로 생성 | 허용 방 연결과 전체 국소 연결을 각각 한 번 탐색해 재사용 |
| 경로 탐색 | 후보 경로마다 별도의 무제한 A* | 한 계획의 모든 경로가 합계 4096회 frontier 꺼내기 한도 공유 |
| 우회 후보 | 여러 우회 경로를 완전 계산하고 비교 | 관측 적이 없으면 생략, 있으면 첫 유효 우회 채택. 공통 경로 한도 사용 |
| 다음 방 | 한 갱신에서 여러 완전한 계획 생성 가능 | 일반 다음 방 또는 접촉 재확인 중 한 대상의 완전한 계획만 시도 |
| 다음 방 실패 | 같은 첫 실패 후보를 다시 검사하기 쉬움 | 실패 대상은 180틱 보류하고 다른 대상 시도. 보류를 전체 클리어로 취급하지 않음 |
| 다음 방 후보 | 앵커마다 전체 계획과 넓은 위치 비교 | 계획/국소 지도 세대별 후보 목록 재사용, 최대 12개 방, 첫 유효 앵커 칸 사용 |

48개 구조와 8개 상세 검사는 서로 다른 한도다. 실패 뒤에는 구조 묶음 내부의 남은 상세 후보부터 이어 가고, 그 묶음을 다 검사한 뒤 다음 구조 묶음으로 넘어간다. 첫 묶음만 영원히 반복하거나 한도 밖의 모든 후보를 영구 배제하지 않는다. 목표·현재 방·구조 버전 변경과 성공 시 재시도 위치를 초기화한다.

경로 한도는 확정된 전체 계획에 대한 작업량 한도이며, 같은 호출을 여러 프레임에 나누는 구현은 아직 아니다. stale frontier 항목을 꺼내는 작업도 한도에 포함한다. 아주 긴 우회가 필요한 경우에는 한도 때문에 계획이 실패할 수 있다. 이 경우 더 비싼 무제한 재탐색으로 넘어가지 않고 대기·다른 후보·후속 재시도로 처리한다.

최초 계획이 한도 때문에 실패하면 전술 명령 소유권을 유지하고 180틱 이후 재시도한다. 일반 습격 AI에 맡겨 다른 열린 입구로 움직이는 fallback을 추가하지 않았다. 정지 대형 연결·고유 자리·투척 안전과 실제 경로 검사도 유지했다.

## 진단과 검증

개발자 정보에 상세 검사 수, 경로 작업 수, 한도 도달 여부를 추가했다. CPU 표본도 Navigation·BreachSearch·RouteSearch로 나눴다. 해당 표본은 Planning/Execution의 하위 구간이므로 더해서 총 비용으로 해석하지 않는다. 실게임 감사 도구에는 계획 작업 수를 기록한다.

- 모드 빌드: 오류/경고 0개.
- 순수 전술 정책 검증: 기존 CQB·관측·투척·연막 검증과 새 방 실패 보류/후보 공정성/공통 탐색 한도 검사 통과.
- 지형/이동/워커 검증: 933개 검사 통과.
- 실제 게임 클래스 바인딩: 기존 검사와 추가 10개 재시도 진행·한도 실패 소유권 검사 통과.
- Security 실제 이동: 알려진 문, 새 구멍, 숨은 반대편 문 유지, 경계 해제 후 합류, HC 연막 통과의 5개 시험 통과.

처음의 HC 시험에서는 이동 인원 11명이 도착했지만 검사 시점에 연막 조건이 충족되지 않았다. 검증 도구가 Update에서 `tick % 10`일 때만 연막을 보충해 고속 실행에서 해당 틱을 건너뛸 수 있었다. 매 검사 프레임에 연막을 유지하도록 수정했으며, 도착/다른 입구 사용/연막 밀도 판정은 완화하지 않았다. 이 수정 이후 5개 시험을 통과했다. 이후 추가한 실패 후보 순회는 실제 게임 클래스 검사로 검증했고, 최종 DLL은 아래 성능·장시간 시험에 사용했다.

## 400명 비교와 한계

같은 감사 도구의 250×250 맵, LOW 폰 400명/37개 실행 단위, 300틱 준비+600틱 표본으로 변경 전후를 한 번씩 비교했다. 상세 조건과 원자료는 [1차 측정 JSON](%EC%A0%84%EC%88%A0%20AI%20%EA%B3%84%EC%82%B0%EB%9F%89%20%EC%B6%95%EC%86%8C%201%EC%B0%A8%20%EC%B8%A1%EC%A0%95.json)에 있다.

| 항목 | 이전 | 변경 후 |
| --- | --- | --- |
| 1배 계획 CPU p50/p95 | 9.937 / 15.212ms | 6.967 / 24.936ms |
| 3배 계획 CPU p50/p95 | 10.121 / 17.020ms | 7.247 / 10.533ms |
| 1배 TPS | 47.333 | 33.401 |
| 3배 TPS | 49.743 | 38.820 |
| 3배 실행 CPU p95/최댓값 | 58.381 / 106.552ms | 54.868 / 95.027ms |

최종 계획 37개 모두 성공했고 한도 때문에 실패한 계획은 0개였다. 변경 후 계획당 상세 검사는 최대 1회, 경로 작업은 최대 568회였다. 배열 준비 대기는 시험 종료 시 0건이었다.

**계획 계산의 반복은 줄었지만, 이번 비교에서는 TPS가 개선되지 않았다.** 계획 중앙값 감소만으로 틱 지연 목표를 달성했다고 판단하지 않는다. 같은 시험에서도 1배 계획 p95는 높아졌다. 한 번씩의 비교에는 초기 상태·정리/GC·게임 시간/행동 차이가 포함되므로 변화율이나 확정적인 원인으로 일반화하지 않는다.

400명 중 389명은 같은 개구부 작업 구역의 대기 상태였다. 모든 폰이 동시에 CQB를 수행하는 조건이 아니다. 남은 전체 틱 비용과 대기 분대의 반복 실행을 분리해서 계측하고, 조건 순서를 바꾼 반복 시험이 필요하다.

## 장시간 실제 방 진행

최종 DLL로 LOW 50명/5개 단위를 300틱 준비+6000틱, Fast(3배)에서 시험했다. 전원 생존·이동, 성공 계획 5개, 종료 시 배열 준비 대기 0건이었다. 종료 단계는 SecureRoom 2, ClearRoom 1, CrossBreach 1, Assemble 1이었다. 앞/후속 단위의 돌파와 방 진행은 확인했지만 모든 방 정리 완료를 뜻하지 않는다.

이 조건의 TPS/FPS는 180.018/57.956, 계획 CPU p50/p95는 4.944/15.464ms였다. 계획 최댓값은 82.535ms, 실행 프레임 최댓값은 155.692ms가 남았다. 한도를 걸어도 단일 바닐라 검사·지도/배치·GC 등의 시간 상한을 보장하는 것은 아니다. 해당 실행의 Native 배열 최고 사용량은 4,375,000 bytes였다.

## 이어서 필요한 작업

1. 계획의 남은 수집·후보 검증·배치를 중단/재개 가능한 서비스로 분할하고, 다음 방마다 공통 수집을 반복하는 부분을 줄인다.
2. 대기 분대가 반복하는 전체 대기 자리/사용권 조회를 지속 인덱스로 바꾼다. 대기 분대·이동 분대·실제 작업 분대의 갱신을 구분한다.
3. 전체 게임 틱과 메인 스레드 프레임 비용을 함께 측정한다. 전술 코드 일부를 프레임/워커로 이동한 것만으로 성능 개선이라 판단하지 않는다.

이번 변경은 첫 유효 후보 선택과 호출당 작업량 축소까지다. 전술 품질이 낮아지는 것은 허용하지만, TPS와 순간 지연의 개선은 후속 검증에서 따로 입증해야 한다.
