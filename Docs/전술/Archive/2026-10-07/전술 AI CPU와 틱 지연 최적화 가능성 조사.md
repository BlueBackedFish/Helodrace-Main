# 전술 AI CPU·틱 지연 개선 가능성 조사

2026-10-07. 이번 작업은 기존 프로파일러를 이용한 측정과 소스 분석이다. 전술 코드, DLL, 실행 동작을 수정하거나 새 최적화를 구현하지 않았다. 아래 절감률과 갱신 주기는 **구현 전 가설과 제안**이다. Temporal accuracy, state freshness, determinism, decision quality, update frequency, consistency를 모두 낮출 수 있다는 조건에서 CPU와 메인 틱 지연을 우선 평가했다.

## 핵심 판단

가장 먼저 줄일 곳은 매 폰의 작업·대기 처리에서 반복되는 `MapComponent_RaidTacticalOrders.For/Get` 소유권 검증이다. 분대 계획 수립보다 훨씬 자주 실행되며 인원 증가에 따라 누적 비용이 커진다. 다음은 관측 결과의 재검증, 대기 분대의 주기적 실행, 통신 프레임 전체 갱신이다. 큰 계산을 모두 병렬화하기 전에 **계산 자체를 생략하고 오래 재사용하는 방식**이 유리하다.

멀티코어를 적극적으로 사용할 후보는 국소 합류 경로, 대응 엄폐 후보 평가, 반복되는 방 그래프 탐색이다. 작은 조회·연결 그래프를 작업마다 워커에 보내는 것은 스냅샷과 큐 비용 때문에 우선순위가 낮다. 정적 구조 분석과 일반 이동 마스크 계산은 이미 워커에서 수행한다.

수집 규모와 재현 상태, 좁은 계측 결과와 절감 시나리오는 아래에 기록했다. 모든 성능 수치는 계측된 상황의 값이며, 모든 분대가 동시에 실내 교전하는 경우의 상한을 측정한 것은 아니다.

## 측정과 해석 기준

- 기존 설치 DLL SHA256: `4dc08f5f64226ef5becf8b20f8afa00fa12ee520e5f471e9d8383cea43e93178`. 빌드·배포 없이 이 DLL을 사용했다.
- LOW 50/200/400명, HIGH 52/208/403명. 분대 수는 각각 5/19/37, 4/16/31이다. HIGH는 13인 분대이고 LOW 마지막 분대는 부분 편제일 수 있다.
- 기존 격리 quicktest의 실제 Pawn, Job, PathFinder와 전술 컴포넌트를 사용했다. 준비 600틱, 측정 1200틱, 3배속을 기본으로 했고 계획·정적 캐시는 준비 0틱의 별도 cold 구간을 기록했다. 게임 초기화·폰 생성 전체가 측정 구간에 들어오는 것은 아니다.
- 고정 지도 형상 해시 `2DCA10EF6A532BA820CA2CFA41B18D21E564655193AC63E429759ED9D0135787`, 시드 `hd-perf-20261007`. 여러 분대가 같은 외벽으로 접근해 다수가 대기하는 부하가 포함된다. cold/steady/기능 재현 구간은 서로 섞어 비교하지 않는다.
- 128개 타깃 제한 때문에 실행·관측, 이동·명령, 계획·캐시, 통신, 생명주기, 지원·협력, 바닐라 작업 호출로 나눴다. C# iterator는 생성 메서드 외에 해당 compiler-generated `MoveNext`를 선택했다. 공용 LINQ 열거 본문은 일부 부모 비용에 남는다.
- 기준 100%는 Core `Verse.GenRadial.NumCellsInRadius(float)`의 고정 **10,000회 배치 한 번**이다. `Core%/tick = inclusiveMs / 측정 틱 수 / 배치 중앙값 × 100`. CPU 점유율이나 Core 전체 비용 대비 비율이 아니다.
- **실제 스레드 CPU 시간은 `DoSingleTick`만** Windows `GetThreadTimes`로 수집된다. 짧은 메서드의 순위는 `Stopwatch` 경과 시간으로 판단한다. 이 값에는 선점·GC·JIT·중첩 계측 비용이 포함될 수 있다. CSV의 미측정 CPU 칸은 비워 두었다. 기존 `cpuCumulative`의 각 stage 합계도 이름과 달리 Stopwatch 경과 시간이다.
- inclusive 합계는 부모·자식 사이에 겹친다. `For + Get`, `RunScheduledUnit + RefreshContactsCore`, `RefreshFrames + Delays`를 더하지 않는다. `trackedSelf`는 선택한 하위 호출만 제외한 값이며 정확한 self CPU가 아니다.
- max는 전체 완료 호출의 최대값이다. p50/p95/p99는 메서드별 **마지막 2048회**의 nearest-rank 값이다. 수십만 회 호출되는 메서드는 마지막 몇 틱의 분포일 수 있어 전체 구간 p99로 해석하면 안 된다.
- 상세 타깃 묶음이 다르면 계측 부하도 다르다. 동일 DLL이어도 전투 단계·무전기 보유 인원·갱신 횟수가 달라질 수 있다. Core 보정은 이 차이를 제거하지 않는다. 좁은 계측을 별도로 수행하고 구현 효과라고 주장하지 않았다.

전체 메서드의 총 경과 시간, CPU 수집 여부, 호출 수, 평균, max/p95/p99, 틱당 호출과 Core 비율은 [측정 CSV](../../../../Source/Benchmarks/AgentProfiler/Results/2026-10-07-wide-tactical-analysis/methods.csv), 미호출 여부는 [coverage CSV](../../../../Source/Benchmarks/AgentProfiler/Results/2026-10-07-wide-tactical-analysis/coverage.csv), 상태·원본 JSON은 [결과 폴더](../../../../Source/Benchmarks/AgentProfiler/Results/2026-10-07-wide-tactical-analysis/README.md)에 보관한다.

## 병목별 검토

### 1. 반복 명령 조회·소유권 검증 — 최우선

1. **현재 비용과 병목 정도:** 넓은 이동 계측에서 LOW 50/200/400명 `For`는 약 6.9만/29.0만/59.2만 회, 0.504/2.146/4.366ms/tick. `Get`은 그 대부분의 중첩 비용이다. 단일 호출보다 호출 총량이 문제다. 좁은 재측정 결과를 뒤에 별도로 제시한다.
2. **비용 원인:** `For → Get → ForPawn/OwnedBy/ControlsPawn`을 대기 facing, 자동 공격, think tree, 작업·이동 검토 등에서 반복한다. `OwnedBy`는 다시 그룹과 분대 뷰를 조회하고 `group.Members.Contains`의 LINQ 열거를 수행한다. `ControlsPawn`은 습격 Lord, 판단 대기, 실행 상태, assignment를 재검증한다. 이미 등록·검토한 상태를 매 호출에 확인하는 중복이다. `GetGroup` 자체는 사전 조회이므로 전체 조직 선형 탐색이라고 해석하지 않았다.
3. **가능한 최적화:** Pawn별 명령 포인터·소유권·전술 제어 가능 여부를 등록/명령 발행 시 확정하고 30~120틱 재사용한다. 읽는 쪽은 빠른 사전/배열 조회만 수행한다. 탈퇴·사망·다운·draft·Lord/명령 변경 이벤트에서 해당 항목만 무효화하고, 이벤트 누락 보정은 300~600틱으로 낮춘다. 같은 틱의 여러 hook은 같은 검증 결과를 공유한다. 대기 facing은 방향 변경 이벤트 또는 30~120틱 갱신으로 줄인다. 반복 lookup의 음성 결과도 캐시한다.
4. **멀티코어/비동기화:** 낮은 가치. 이 작은 조회를 워커로 보내면 전달 비용이 더 크고, Pawn/Game 접근이 주된 작업이다. 메인 스레드에서 캐시와 빠른 조회로 없애는 것이 효과적이다.
5. **정확도·반응성·일관성 희생:** 상태 전환 뒤 수십 틱 동안 이전 제어 가능 상태를 사용할 수 있다. 분대별 확인 시점이 달라도 된다. 죽거나 despawn된 객체에 실제 Job을 적용할 때의 짧은 유효성 검사는 남기는 편이 예외 방지에 유리하다.
6. **예상 틱 시간 감소:** 해당 조회 경과 비용의 70~90% 제거를 탐색할 만하다. 전체 틱 감소는 이 비용의 실제 비중에 제한되며, 세부 계측 4.366ms를 그대로 절감량으로 약속할 수 없다. 가장 큰 평균 CPU 감소 후보다.
7. **구현 난이도:** 중간. hook마다 서로 다른 조회 의미를 명령 수명에 맞춰 정리해야 한다.
8. **위험 요소:** 잘못 유지된 명령, 탈퇴 뒤 제어, 이벤트 누락. 부정 캐시의 긴 TTL은 새 명령 시작을 늦출 수 있다. 캐시 유효성을 매 조회에 전체 검증하면 절감 효과가 사라진다.
9. **추천 우선순위:** P0. 아래 최적화들의 공통 호출 경로라 먼저 처리할 가치가 가장 높다.

### 2. 관측과 알려진 적의 반복 재검증

1. **현재 비용과 병목 정도:** 실행 계측의 `RefreshContactsCore`는 LOW 50/200/400명에서 0.049/0.274/0.272ms/tick. LOW 200명의 `RespondToFire`는 0.220ms/tick, `VisibleArmedEnemies`는 0.061ms/tick이다. `RespondToFire` 안의 관측·LOS 비용은 중첩이다. HIGH 403명 통신 계측에서도 contacts 0.287ms/tick이 확인됐다.
2. **비용 원인:** 관측 broad phase는 분대 사각형 주변의 아군도 열거한 뒤 적을 걸러낸다. 적당 최대 4명 관측자의 LOS를 검사한다. `VisibleArmedEnemies`는 이미 기억한 적을 찾으면서 다시 전체 `AllPawnsSpawned`와 LOS를 검사하고, `RespondToFire`와 `FieldDefense` 등이 같은 결과를 사용한다. passage 관측은 관측 폰별 반경 4칸 검사·문 보고서 검색을 반복한다. LOS 캐시는 현재 한 틱만 유지된다.
3. **가능한 최적화:** 맵/적대 관계별 적 후보 인덱스를 30~120틱 공유하고 분대 결과는 60~180틱 재사용한다. 알려진 적은 ID 사전으로 찾아 전체 pawn 열거를 없앤다. 관측·저격·야전 방어 판단은 한 관측 snapshot을 공유하고 재LOS는 위치가 2~4칸 이상 바뀌거나 관련 문/연막 chunk가 바뀔 때만 수행한다. 관측자 4→1~2명, 적 후보 32→8~16명, LOS 예산 축소, 전체 정렬 대신 제한된 후보만 선택할 수 있다. 문 관측은 주변 모든 바닥 대신 캐시상의 portal 목록과 변경된 문만 검사한다. passage 보고를 120→300~600틱 동안 재발행하지 않는다. 조용한 대기 분대는 180~600틱으로 낮춘다.
4. **멀티코어/비동기화:** 중간~높음. 기존 `CanSeePawn`/`GenSight`/연막 조회를 그대로 워커에서 호출하면 안 된다. 메인에서 관측자의 위치·적 후보 ID/좌표·사거리·기존 관측 정보와 관련 벽/문/연막의 값 배열을 만들고, 워커에서 근사 ray/거리/우선순위를 계산하면 이득이 있다. 준비에 전체 맵 live 읽기를 다시 요구하면 이득이 줄어든다.
5. **희생:** 적 감지·사라짐·후방 접근·문 변경·연막 변화를 수십~수백 틱 늦게 반영한다. 사격 LOS와 관측 LOS가 완전히 같지 않아도 되는 가정이다. LOW의 접촉 기반 정보 공유는 유지하고, 공유할 물리 캐시와 개인/분대가 알고 있는 적 정보를 구분하는 편이 기존 방향을 보존한다.
6. **예상 감소:** 해당 관측/반복 재검증 묶음의 50~85%. LOW 200명의 두 부모 비용만 기준으로도 약 0.25~0.40ms/tick을 탐색할 수 있으나 서로 겹치는 범위는 제외해야 한다. 적이 많은 상황의 절감률은 이번 단일 보호 적 fixture로 정량 확정하지 못했다.
7. **난이도:** 캐시·빈도 감소 중간, 값 기반 LOS 워커 높음.
8. **위험:** 적을 늦게 감지하거나 빈 위치를 계속 겨냥한다. 전역 revision 하나로 모든 LOS를 무효화하면 캐시 이득이 사라진다. 스냅샷 비용, 거대 후보 사각형, 긴 비활성 캐시가 병목을 다시 만들 수 있다.
9. **우선순위:** P1. 빈도·공유·후보 제한부터 검토하고 워커 이전은 그 뒤에 평가한다.

### 3. 통신 프레임 전체 갱신

1. **현재 비용과 병목 정도:** 통신 계측 HIGH 52/208/403명의 `RefreshFrames`는 0.056/0.232/0.408ms/tick. 403명에서 총 489.76ms, 60회, 평균 8.163ms/회, max 13.901ms. 같은 구간 `Delays`는 99.26ms, 623회, 0.083ms/tick이다. 연결 그래프는 프레임 부모 비용의 약 20.3%이다.
2. **원인:** 20틱마다 전체 활동 분대의 멤버 유효성·의식·무전 장비를 확인하고 사전과 배열을 만든다. 위치가 정확히 동일해야 재사용하므로 이동 중에는 TTL 60틱의 이점이 작다. 송수신 중인 분대는 재사용을 우회한다. `Delays`는 분대 내 O(m²) 그래프이고 고정 13인 편제에서는 전체 인원에 대체로 선형이지만, 전체 분대 동시 갱신이 긴 한 호출을 만든다. 장비 LINQ의 실제 열거 비용은 `Radios/InstalledRadios` 생성 메서드보다 부모에 더 남는다.
3. **최적화:** 장비/운용 가능 정보 300~1800틱 재사용 + 장착/파손/다운 이벤트 무효화. 연결 그래프는 120~300틱 TTL, 이동 4~8칸 임계치, 관련 지역의 문 변화로만 부분 갱신. 같은 부대·무전망은 commander/operator 중심의 단순 그래프, voice는 commander/근접 대표 몇 명만 연결한다. 전체 분대를 한 번에 만들지 않고 틱당 1~2분대로 분산한다. pending packet은 목적지 분대·운용자만 재검증한다. 보고 ledger의 반복 `Any/First/RemoveAll`, receipts, in-flight 검색은 ID 인덱스와 최신 변경분 큐로 대체 가능하다. 8개 ordered pair 순환 대신 근접 지휘자/무전망 그룹만 후보로 유지한다.
4. **병렬화:** 그래프를 값 배열로 계산하는 것은 가능하지만 이것만 완전히 없애도 현재 HIGH 403 구간에서 최대 0.083ms/tick, 전체 틱의 약 0.37% 경과 시간이다. snapshot/apply를 빼면 더 작다. 장비 검사 재사용·분대별 갱신 분산의 우선순위가 높다. 그래프 워커는 여러 분대를 묶어 보내는 경우에만 탐색할 가치가 있다.
5. **희생:** 연결·단절·radio 고장 반영 지연, 일시적으로 실제보다 빠른 relay, ACK/수신 시점 차이, voice relay의 근사화. 숨은 문 변경을 즉시 분대 지식으로 전달할 필요는 없다.
6. **예상 감소:** 전체 통신 비용의 60~85%, HIGH 403 예시 약 0.25~0.35ms/tick. 갱신 분산은 max burst를 더 크게 줄일 수 있으나 같은 횟수를 수행하면 총 CPU는 줄지 않는다. graph-only 워커는 낮은 효과다.
7. **난이도:** TTL/장비 캐시 중간, 보고·연결 partial update 중간~높음.
8. **위험:** 접촉 없이 LOW 정보를 공유하는 변화, 잘못된 접속 캐시, 재시도/ACK 큐 폭증. 사건마다 전역 전체 refresh를 호출하면 event 방식이어도 더 비싸질 수 있다.
9. **우선순위:** P1~P2. 평균 비용보다 한 번에 모든 분대를 갱신하는 지연에도 대응해야 한다.

### 4. 대기 분대 실행·개구부 대기 상태 관리

1. **현재 비용:** 실행 계측 LOW 400 `RunScheduledUnit` 4439회/1200틱(3.699회/tick), 0.643ms/tick. 내부 `WaitForSharedOpeningCore` 1480회, 0.234ms/tick. 이 둘은 중첩이다. LOW 200에서는 야전 반응 때문에 Run 0.859ms/tick으로 오히려 더 컸다. 인원만으로 단조 증가한다고 볼 수 없다.
2. **원인:** review를 180틱으로 늦춰도 ticket 자체는 10틱마다 다시 스케줄된다. 비review 경로에서도 관측·긴급 반응·routine·30틱 admission을 수행한다. 대기 폰별 자리를 검사하고 동일 Hold/Move 명령을 재발행한다. roster는 60틱마다 전체 분대를 열거한다. 2ms/틱 예산은 한 `RunScheduledUnit`의 내부 반복을 중단하지 못하고 casualty urgent 경로는 예산을 우회한다.
3. **최적화:** ticket의 다음 실행 시각 자체를 상태별로 변경한다. 이동/교전 30~60틱, quiet/opening wait 180~600틱, Hold/Complete 300~1800틱, 변화 없는 완료 상태는 잠재운다. 개구부 임대 해제·사망·새 관측·명령 종료 같은 사건에서 관련 ticket만 깨운다. 대기 위치의 재할당과 명령 발행은 변경분에만 수행한다. roster는 event + 300~600틱 보정으로 낮춘다. 긴 반복은 폰 1~2명 또는 후보 8~16개 단위로 나누고 urgent도 별도 제한 큐에서 처리한다. 저우선순위 재검토는 부하가 높으면 건너뛴다.
4. **병렬화:** 상태 머신과 Job 적용 자체는 메인에 남겨야 한다. 후보 계산만 워커로 보내고 결정 snapshot을 오래 쓰는 구조는 가능하다. 단순 대기 ticket에 worker를 만들 필요는 없다.
5. **희생:** 개구부가 열려도 후속팀이 늦게 움직임, 대형·멤버 상태 stale, 부하에 따른 판단 시점 차이, casualty 반응 지연. vanilla Job의 실제 이동은 판단 사이에도 계속 진행한다.
6. **예상 감소:** quiet ticket 호출 80~95%, 이 묶음의 실질 경과 비용 50~85% 감소 후보. 관측 감소와 명령 조회 캐시 절감에 겹치므로 독립 합산하지 않는다. time slicing만 적용하면 평균 CPU보다 p99 개선이 주효하다.
7. **난이도:** 중간. 상태별 wake 조건과 갱신 주기를 함께 설계해야 한다.
8. **위험:** wake 누락으로 영구 정지, 큐의 낮은 우선순위 작업 기아, 대열 준비 완료 상태를 지나치게 오래 보존. 주기적 저빈도 fallback은 필요하다.
9. **우선순위:** P1. 조용한 분대가 많은 대규모 레이드에서 큰 효과 후보다.

### 5. 대응 위치·엄폐 탐색의 긴 실행

1. **현재 비용:** LOW 200 실행 구간의 `FindReactivePosition` 165회, 총 136.13ms, 평균 825µs, 0.113ms/tick, max 6.059ms, p99 1.142ms. `FieldDefense` 0.191ms/tick은 이 탐색 일부를 포함한다. 같은 400명 구간에는 이런 상황이 거의 없어 평균 순위를 고정할 수 없다.
2. **원인:** 폰마다 반경 8~14칸의 후보 집합·연결 거리·예약·위협 LOS·엄폐 확률·지형 비용·위험물 LOS를 평가하고 정렬한다. 같은 분대가 같은 위협에서 도주해도 반복한다. 최종 후보 최대 12개에 native reachability를 사용한다. 한 분대에 여러 폰이 동시에 새 자리를 찾으면 scheduler 예산을 넘는다.
3. **최적화:** 분대 단위 반응 snapshot, 같은 지역·위협의 점수/연결 거리 공유, 반경 축소, 8방향×2~3거리 또는 16~32후보만 샘플, 최선 후보 전체 정렬 대신 첫 적절 후보, 최종 CanReach 1~2회 제한. 위치 TTL 120~300틱, threat가 4칸 이상 이동하거나 자리가 막힐 때만 재탐색. 늦은 꼬리 인원은 대표자의 결과 주변으로 배정한다. 1틱의 새 자리 탐색 수에 상한을 둔다.
4. **병렬화:** 높은 가치 후보. 벽/문/엄폐 등급/지형 비용, threat/폭발 좌표·반경, pawn 좌표만 캡처하고 pure BFS·ray·점수를 워커에 보낸다. `CoverUtility/CanReach/예약 관리자`를 워커에서 직접 읽지 않는다. 최종 1~2개 후보의 예약/실제 이동 적용만 메인에서 확인한다. live 점수 계산을 메인에 그대로 남기면 이득은 작다.
5. **희생:** 덜 좋은 엄폐, 순간 위험에 늦은 반응, 서로 다른 시점의 자리 선택, 근사 폭발/LOS 판단. 늦은 결과를 기다리는 동안 기존 이동을 계속하거나 단순 반대 방향 이동을 사용할 수 있다.
6. **예상 감소:** 후보 단순화 70~95%의 탐색 비용 감소 후보. pure 계산 이전으로 해당 탐색의 메인 시간 60~90% 이전을 탐색할 수 있다. 이번 평균 기준 약 0.08~0.10ms/tick이며, 동시 탐색 burst가 많은 실전에 더 큰 효과를 기대할 수 있다. 총 연산 증가도 허용할 수 있지만 현재 worker 순이득은 미측정이다.
7. **난이도:** 후보 제한 중간, 공유 snapshot/워커 높음.
8. **위험:** 회피 방향이 막힘, 여러 폰이 같은 자리를 선정, 결과 도착 시 위험물이 이미 이동/폭발, main snapshot이 계산보다 비싸짐. 메인에서 다시 전체 후보를 재평가하면 효과가 사라진다.
9. **우선순위:** P2, 순간 지연이 최우선이면 P1. 단순화부터 수행할 가치가 있다.

### 6. 실내 합류·국소 CQB 맵·대형 재배치

1. **현재 비용:** 넓은 steady 이동 구간에서 `KnownIndoorJoin`은 호출되지 않았다. `FollowNodes`도 LOW 50/200명에서 5/8회여서 초기 접근 최악 비용을 대표하지 않는다. `FollowBreachCrossing`은 LOW 50명에서 19회, 22.45ms 합계, max 13.964ms였지만 LOW 200명에서는 max 2.852ms다. cold LOW 400 `RaidCqbLocalMap.Refresh` 90회, 0.047ms/tick. 기능 재현 구간은 뒤의 추가 측정에 분리했다.
2. **원인:** `KnownIndoorJoin`은 pawn별 최대 49×49=2401칸의 room/usable/portal 배열을 다시 구성하고 BFS와 목록을 만든다. `RaidCqbLocalMap`은 최대 33×33=1089칸을 30틱마다 순회한다. 맵이 같아도 창 위치/지식/피해야 할 자리 때문에 유사 계산을 반복한다. formation claim과 후보 정렬·예약·CanReach도 재검사한다. FOLLOW/resolve/ingress가 여러 계층에서 동일 합류 가능 여부를 확인한다.
3. **최적화:** 같은 분대·목표·허용 방·알려진 portal 버전의 공통 topology와 목표 역방향 distance field를 공유한다. 개인 결과 TTL 180~600틱, 실패 결과도 재사용한다. 24→12칸 합류 반경은 최대 셀 수를 약 74% 줄인다. CQB는 16→8~12칸, 30→120~300틱, origin을 몇 칸 움직일 때만 갱신한다. 안정적인 바닥/room은 정적 캐시를 참조하고 알려진 portal 변화만 patch한다. 폰별 전방 route 정렬·LOS는 60~180틱 재사용하거나 간단한 방/portal 그래프와 다음 지향점만 유지한다. 대형 변경은 사건 기반, 후보 8~16개, 슬롯 점유 snapshot 공유와 재탐색 rate limit을 적용할 수 있다.
4. **병렬화:** 합류 BFS와 공통 거리장·후보 점수는 좋은 후보다. 이미 고정된 값 기반 geometry와 분대 knowledge의 값 snapshot을 참조하면 메인에서 2401칸을 다시 복사할 필요도 줄일 수 있다. 현재 재활용 중인 CQB 배열을 그대로 워커에 주면 다음 refresh가 덮어쓰므로 immutable generation/별도 버퍼 수명이 필요하다. `Pawn.CanReach`와 reservation/Job 적용은 메인에서 소수 후보만 수행한다.
5. **희생:** 작은 창 때문에 우회 가능한 경로를 놓침, 오래된 개구부 사용, 늦은 합류, 대형 정확도 감소. 연결성은 거친 방 그래프로 유지하고 폰별 완벽한 경로·한 칸 단위 순서를 덜 관리하는 선택이 가능하다.
6. **예상 감소:** 반복 grid/탐색 비용 50~90%, 워커로 pure 탐색 메인 시간 60~90% 이전 후보. 이번 steady 구간의 평균 절감은 작다. 특정 합류/대형 burst의 틱 지연 개선 대상으로 평가해야 하며 아직 전체 AI 절감에 크게 더할 근거는 없다.
7. **난이도:** TTL/반경/후보 상한 중간, 지식별 공유 topology/worker 높음.
8. **위험:** 알려지지 않은 문을 이동 계획에 사용, 허용 room 집합의 잘못된 공유, 좁은 창의 반복 실패, 위치 예약 충돌, 결과 적용 때의 revision churn. 실패 시 다시 무제한 재계산하는 fallback은 금물이다.
9. **우선순위:** P2. 재현되는 순간 지연은 중요하지만 미호출 method를 평균 최대 병목으로 순위에 올리지 않는다.

### 7. 계획 수립·정적 캐시·이동 마스크 준비

1. **현재 비용:** cold LOW 400명의 plan scheduler는 0.150ms/게임틱으로 정규화한 메인 프레임 비용, `AssignmentSteps.MoveNext` 0.084ms/틱, static `Pump` 0.051ms/틱이었다. `Capture` 125,000회는 0.021ms/틱 수준이었다. LOW 50의 plan slice max 9.017ms, 실행 unit max 54.686ms가 관측돼 예산은 hard cap이 아님을 확인했다. steady에서는 계획 대부분이 끝나 비용이 훨씬 낮다.
2. **원인:** 계획마다 geometry/문 상태 graph와 경로·스택/지원 후보·assignment를 계산한다. yield 사이의 한 덩어리가 길면 3ms/frame allowance를 넘긴다. 초기/방 변경 뒤 static capture가 두 차례 전체 순회할 수 있다. 반응 이동 마스크는 일반 마스크와 달리 생성 시 메인에서 동기 계산한다. 긴 graph/search가 끝나기 전 내부 yield가 없으면 분산만으로 burst를 막지 못한다.
3. **최적화:** 같은 벽면/목표 방의 후보·경로 뼈대·연결 graph를 600~1800틱 공유, 자세한 후보 4~8개 제한, 가장 가까운 적절 돌파점 선택, 오래된 plan 유지와 replan debounce 120~600틱. 정적 맵은 관련 지역의 dirty 변경을 모아 부분 갱신하고 전역 room 재계산은 묶어서 수행한다. snapshot 획득과 결과 적용도 여러 틱으로 분산한다. 긴 후보/assignment/route 반복 안에 분할 경계를 둔다. 반응 mask는 오래된 공통 room mask 또는 지역 권한만 재사용한다.
4. **병렬화:** geometry와 일반 mask는 이미 값 입력을 worker에서 계산한다. 해당 워커 수 증가만으로 메인 틱 CPU가 크게 줄어든다는 근거는 없다. 새로운 대상은 현재 main iterator 안의 값 기반 경로·돌파 후보·assignment 점수다. live Map/Room/Pawn/CanReach 호출을 snapshot/근사로 분리해야 한다. 프레임 update로 옮기기만 하는 것은 메인 전체 시간을 줄이지 않는다.
5. **희생:** 최선 진입점 미선택, 새 구멍/문 변경 뒤 재계획 지연, 분대별 계획 세대 차이, 후보 탐색 불완전. 분대별 다양한 진입 방향이라는 목표는 유지하면서 상세 경로 정확도를 낮출 수 있다.
6. **예상 감소:** cold 계획/메인 snapshot 묶음 30~70%, 예시 0.05~0.14ms/게임틱 정규화 비용 감소 후보. steady 전체 틱에서는 효과가 작다. 분할은 시작/재계획 max를 줄이는 데 유리하지만 평균 연산량 감소와 구분해야 한다.
7. **난이도:** 빈도/후보 제한 중간, planner 값 모델 분리 높음.
8. **위험:** 변경마다 worker 취소→처음부터 재시작, 새 snapshot 복사비·GC, 결과 배치 적용 burst, native grid를 읽는 Unity path job과 버퍼 수명 충돌. 지금의 native lease 보호는 단순히 제거할 대상이 아니다.
9. **우선순위:** P3. cold/재계획 burst 대응은 P2로 높일 수 있으나 steady 평균 감소의 첫 작업은 아니다.

### 8. 전술 명령이 유발하는 바닐라 Pawn·Job·이동 비용

1. **현재 비용:** 전체 `DoSingleTick`과 전술 부모 사이에는 큰 차이가 있다. 세부 바닐라 계측 결과를 뒤에 별도로 제시한다. `Pawn.TickInterval/JobTrackerTick/DriverTick`은 전술 hook와 건강·need 등 다른 작업도 포함하므로 전체 inclusive를 전술 AI 비용으로 간주하지 않는다.
2. **원인:** 판단이 cheap해도 매 Pawn의 기존 Job/대기/사격/think tree가 실행되고, 동일 또는 거의 같은 이동 명령을 다시 발행하면 job override와 path request가 증가할 수 있다. 현재 이동 path 연산에는 이미 Unity job과 native reader가 있다.
3. **최적화:** 목표와 명령 revision을 120~360틱 유지, 의미 있는 이동/단계 변화에서만 override, 반복 실패의 지수형 retry와 낮은 상한, 같은 tick/같은 목적지 요청 합치기. 전술 Hold의 facing·자동 타깃 검색·적 검증은 저빈도 캐시를 사용한다. 신규 path request 수를 제한하고 기존 경로/Job을 계속 실행시킨다. 저우선순위 target/cover 개선은 생략한다. 바닐라 Pawn 건강·need 등의 전체 tick 생략은 이 요청의 전술 최적화와 별도 범위다.
4. **병렬화:** Job/stance/예약/Pawn_PathFollower를 그대로 worker에서 실행하는 것은 실용성이 낮다. 기존 native path 작업을 다시 Task로 감싸도 이미 밖에서 도는 연산을 이전한 것으로 계산할 수 없다. 공유된 이동 지향점/권한/후보 계산을 먼저 worker에서 준비해 main API 호출 수를 줄이는 방식이 타당하다.
5. **희생:** 목표 변경·사격 재획득 지연, 장애물에서 늦은 재시도, 위치 오차 허용, 경로 deviation/순서의 느슨한 유지.
6. **예상 감소:** 실제 request/override 빈도가 높은 상황에선 추가 이득이 가능하다. 이번 측정의 전체 Pawn 시간을 전부 제거할 수 있다는 계산은 하지 않는다. 상위 세 병목의 절감률에 이 부모 시간을 더하지 않는다.
7. **난이도:** 명령 유지·retry 중간, 바닐라 AI 전체 교체 매우 높음.
8. **위험:** 오래 막힌 Job, override 폭주가 다른 단계로 이동, engine의 비전술 기능까지 생략, 네이티브 reader 강제 동기화. 요청 감소는 실제 `GenerateNewPathRequest/CheckForJobOverride` 호출과 함께 확인해야 한다.
9. **우선순위:** P2~P3. 큰 바닐라 부모보다 그 안의 반복 전술 검증을 먼저 줄이는 것이 명확하다.

### 9. 종료 후 이동 영역 캐시의 유휴 서비스

1. **현재 비용:** 정리 0명 구간의 movement `MapComponentTick` 약 0.0015ms/tick, update 약 0.0006ms/게임틱, `CompleteReaders` 약 0.0006ms/tick. 캐시가 남아 있다는 사실과 의미 있는 CPU 소모는 구분된다.
2. **원인:** 컴포넌트 callback과 빈 pending/reader 확인. 현재 Pump는 pending 또는 cache/budget 초과 때 실제 서비스한다.
3. **최적화:** 활동 레이드·pending·reader가 없으면 완전히 잠재우고 신규 요청 시 재활성화. trim은 600~1800틱 또는 필요 시에만 실행. 단발 cleanup을 조각내고 추가 polling을 없앨 수 있다.
4. **병렬화:** 필요성이 낮다. 워커 큐 비용이 유휴 검사보다 크다.
5. **희생:** retire/trim이 늦어지고 stale 캐시가 오래 남는다. 메모리를 우선 목표로 삼지 않는 이번 가정에 부합한다.
6. **예상 감소:** 현재 예시 전체 틱에서 수 µs 수준. 유의미한 평균 CPU 개선의 우선 대상은 아니다.
7. **난이도:** 낮음~중간.
8. **위험:** 다음 레이드에서 깨우지 못함, 진행 중 native reader의 버퍼 조기 해제. 단순 해제는 오히려 다음 준비 비용을 늘릴 수 있다.
9. **우선순위:** P4. 이전에 관측된 높은 idle 부하가 이번 현재 빌드에서 계속 재현된 것으로 보지는 않는다.

## 워커/비동기 구조의 평가

Unity API의 대부분은 thread-safe하지 않다. 현재 mod의 Pawn/Map/Room, 건강·장비, LOS/예약·Job 변경은 main 소유로 취급하는 편이 타당하다. 순수 값 계산을 background thread에서 하고 Unity 접근을 main에서 수행하는 원칙은 [Unity 공식 문서](https://docs.unity3d.com/ja/2023.2/Manual/overview-of-dot-net-in-unity.html)와도 일치한다. 문서의 새 Awaitable API를 이 RimWorld 런타임에 그대로 도입하겠다는 뜻은 아니다.

`async` 표기만으로 CPU 계산이 다른 코어로 이전되지 않는다. CPU-bound 계산을 실제 워커/thread pool로 보내야 하며, 메인에서 동기 Wait/Result를 호출하면 틱 지연을 다시 만든다. [Microsoft의 CPU-bound 비동기 지침](https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/async-scenarios)을 기준으로 판단했다.

권장 탐색 구조는 다음과 같다. 이는 설계안이며 구현하지 않았다.

1. **메인:** 이미 캐시된 정적 geometry를 공유하고, dirty pawn/분대의 ID·좌표·flag·사거리·명령 revision·허용 room/known portal·관측 적 좌표만 값 배열로 만든다. 변화 없는 snapshot은 60~300틱, 정적 부분은 더 오래 재사용한다.
2. **큐:** 분대/판단 종류별 최신 요청 한 개를 유지하고 중복 요청을 합친다. 전체 길이와 동시 실행 수를 제한한다. 낮은 우선순위는 drop/coalesce하며 오래된 결과를 사용할 수 있다. 매 폰/매 틱 Task는 만들지 않는다.
3. **워커:** pure topology BFS, 역방향 거리장, 후보 점수·근사 LOS, 간단한 연결 그래프를 여러 분대/영역 묶음으로 계산한다. Map/Pawn/Unity 객체와 game callback을 참조하지 않는다. 적 정보 공유 범위는 snapshot의 분대 knowledge로 유지한다.
4. **메인:** 완료 결과만 비차단 polling으로 가져온다. 적용 수·시간을 제한하고 pawn 생존/지도/현재 소유권·최종 후보의 실제 사용 가능성만 짧게 확인한다. 모든 최신 좌표·LOS를 다시 계산하지 않는다. generation은 구조 크기와 소유권 같은 필수 조건에만 엄격히 검사하고 작은 변화는 오래된 결과를 허용한다.

순이득의 기준은 `이전된 메인 계산 시간 − snapshot 생성 − enqueue/poll − 결과 적용 − 버려진 작업의 재요청 비용`이다. worker의 CPU 합계나 경과 시간만 보고 성공으로 판단하면 안 된다. time slicing은 max/p99를, 생략·cache는 평균 CPU를, offload는 메인 CPU를 각각 줄이는지 확인해야 한다.

| 후보 | 메인 시간 절감 가능성 | 판단 |
|---|---|---|
| 명령 조회를 Task로 변환 | 매우 낮음 | 캐시/직접 조회로 제거 |
| 통신 `Delays`만 worker | 현재 작음 | 0.083ms/tick보다 순이득이 작음 |
| 대응 위치·합류 BFS를 공유 snapshot에서 worker | 높을 수 있음 | 후보 단순화·cache 후 남는 큰 계산에 적합 |
| planner의 값 기반 경로/후보 탐색 | cold/burst에 유효 | live query 분리가 비용을 결정 |
| 이미 worker인 정적 geometry/일반 mask의 코어 수 증가 | 메인 감소 근거 약함 | 준비 대기 개선 가능성과 main CPU를 구분 |
| 틱 계산을 frame update로 이동 | 총 메인 시간 감소 없음 | 단독으로 평균 CPU 개선으로 평가하지 않음 |
| 매 틱 전체 live map snapshot | 순손해 가능 | 공유 정적 값 + 필요한 dirty 부분만 캡처 |
| worker 결과를 기다리며 main block | 틱 지연 증가 가능 | 완료 결과만 사용하고 stale 결과 허용 |

현재 worker 풀은 최대 동시 작업 2개(설정 범위 1~4), 정적 구조 계산은 동시 한 개이며 이동 mask를 함께 처리한다. 추가 계산을 같은 풀에 무조건 넣으면 critical movement 준비가 밀릴 수 있다. 작은 작업은 batch하고, 큐에서 우선순위를 두거나 별도 제한을 고려할 수 있다. 코어 수를 늘려 main과 CPU·GC·메모리 대역폭을 경쟁하게 만드는 구조는 낮게 평가한다.

정확도/일관성 희생을 허용하더라도 예외·영구 정지를 비용 절감으로 착각하면 안 된다. 이후 구현 평가에서는 완료율·이동 진행 여부를 함께 확인해야 한다. 이는 현재 전술 정확도를 유지하라는 요구가 아니라, 동작을 멈춰서 싸게 보이는 결과를 구분하기 위한 기준이다.

## 좁은 계측: 조회 호출량과 인원 증가

이 묶음은 `For`의 내부 `Get/OwnedBy/ControlsPawn`을 추가 계측하지 않았다. 기본 컴포넌트와 Run/contacts 및 소수 상태 메서드만 선택해 내부 계측 증폭을 줄였다. 값은 전체 구간 1,200틱 기준이며 HIGH 403 재시도는 1,201틱이다.

합집합은 `DoSingleTick.inclusive − trackedSelf`로 계산했다. 부모·자식 중복은 제거하지만 **모든 전술 AI의 실제 self CPU를 뜻하지 않는다**. frame update의 계획 비용, 미선택 전술 hook, 게임의 다른 메인 작업은 이 분모에 포함되지 않는다. 광범위 수집에서의 비싼 내부 패치와 좁은 계측을 동일한 전후 최적화로 비교하지 않았다.

## 바닐라 호출에서 확인된 한계

HIGH 403명 바닐라 상세 계측에서 전체 틱은 경과 25.421ms/tick, 실제 CPU 25.052ms/tick이었다. `Pawn.Tick` 733,200회, `Pawn.TickInterval` 52,167회, `JobTrackerTick/DriverTick` 각각 489,600회가 관측됐다. 부모 inclusive 10.295/10.986/5.745/5.498ms/tick은 서로 겹치고 전술 이외 작업도 포함한다. 게임 전체 메서드 호출 수이므로 403명만의 횟수로 나누지 않는다.

반면 측정 중 `GenerateNewPathRequest`는 24회, 합계 1.614ms, max 0.096ms였다. `CheckForJobOverride`는 4,093회, 합계 280.951ms, `TryFindAndStartJob`은 11회, 합계 25.003ms, max 17.611ms였다. 사격 위치의 `TryFindCastPosition/TryFindShootingPosition`은 이 구간에서 호출되지 않았다. 따라서 이 대기 중심 실험에서 native path 생성이나 사격 엄폐 탐색을 평균 최상위 원인으로 지목할 근거는 없다. 실제 전투·새 경로 요청이 많은 별도 구간은 달라질 수 있다.

## 상위 병목만 처리할 경우의 가능성

아래는 구현 효과가 아니라 **계측 구간에서 계산한 절감 시나리오**다. P0 조회 70~90%, contacts 50~85%, 통신 프레임 60~85% 감소를 가정했다. 좁은 구간에서 contacts와 RefreshFrames의 trackedSelf가 inclusive와 같아 선택된 For와 중첩되지 않는 것을 확인했다. `RunScheduledUnit` 전체를 다시 더하지 않았다.

| 가정 | LOW 400 | HIGH 403 |
|---|---:|---:|
| 조회만 줄이는 계측 시간 감소 | 2.49~3.20ms/tick | 2.52~3.24ms/tick |
| contacts 재사용 추가 | +0.12~0.21ms/tick | +0.12~0.20ms/tick |
| 통신 갱신 축소 추가 | +0.09~0.12ms/tick | +0.19~0.26ms/tick |
| 세 묶음 합계 | **2.70~3.53ms/tick** | **2.83~3.71ms/tick** |
| 계측된 전술 하위 구간 대비 | **60~78%** | **60~79%** |
| 해당 실행의 전체 틱 경과 시간 대비 | **15~20%** | **14~19%** |

여기에 quiet ticket 축소, 중복 위치 탐색 제거를 적용하면 추가 여지가 있지만, 이미 제거한 조회·contacts와 겹친다. 남은 Run trackedSelf는 LOW 400 약 0.271ms/tick, HIGH 403 약 0.249ms/tick이므로 이 전체를 없앤다고 해도 추가 감소에는 그 상한이 있다. 실제 남는 실행·명령 적용은 필요하므로 전부 제거하는 목표는 부적절하다.

**60~80%는 전체 전술 AI 실제 CPU 절감 보장이 아니라, 선택된 계측 구간에서의 공격적인 상한 탐색 범위다.** 짧은 조회의 Harmony 계측 자체, 미계측 전술 hook, snapshot/apply와 상태 전환 비용 때문에 제품 실행의 개선율은 달라진다. 전체 게임 틱 60~80% 감소는 이번 결과로 뒷받침되지 않는다. 별도의 경량·비활성 대조군도 아래에 기록한다.

| 5 / P2 | 실내 합류·국소 topology | steady에서 작음 | 상황 의존 | 거리장 공유, 반경/빈도 감소, BFS worker |
| 6 / P3, cold P2 | plan/static capture | steady에서 작음 | 초기/재계획에 큼 | scaffold 재사용, 후보 상한, dirty snapshot |
| 7 / P2~P3 | Job/path 재요청 | 현재 작음 | 재시작 순간에 유효 | 명령 유지, backoff, 새 request 상한 |
| 8 / P4 | 종료 후 유휴 캐시 서비스 | 수 µs 수준 | 작음 | dormant flag, 저빈도 정리 |

이 순서는 모든 구현을 한 번에 권장하는 계획이 아니다. 가장 큰 세 묶음의 생략·재사용을 먼저 평가하고, 그 뒤에도 메인에 남는 큰 pure 탐색만 worker로 옮기는 것이 총 CPU와 틱 지연 모두에 유리할 가능성이 높다. 비동기화의 복잡성에 비해 현재 통신 그래프만 이전하는 효과는 낮다.

추가로 실제 적 10/30/60명, 이동→스택→관측→투척→연속 방 정리, 여러 분대가 다른 portal을 쓰는 전장을 따로 수집해야 한다. 이번 fixture는 단일 보호 적과 많은 대기 분대를 포함해 적 후보 수에 따른 scaling, grenade·casualty의 동시 burst, 전체 건물 클리어 비용을 충분히 측정하지 못했다. 미호출은 저렴하다는 의미가 아니다. 이 후속 수집도 이번 단계에서는 신규 게임 코드 없이 가능한 기존 시나리오 범위부터 검토하는 것이 맞다.


## 경량·비활성 대조군과 해석 제한

추가 LOW 400명 단독 시나리오도 각각 감사 complete로 끝났다. 경량 수집에서는 좁은 계측의 `For`조차 선택하지 않고 기본 컴포넌트만 기록했다. 비활성 실행은 신규 메서드 프로파일러를 완전히 끄고 기존 stage 계측만 사용했다.

| 수집 | 전체 틱 경과 ms/tick | 전체 틱 실제 CPU ms/tick | Core%/tick | 생존 / 이동 | 종료 단계 |
|---|---:|---:|---:|---|---|
| 좁은 LOW 400 | 17.870 | 17.617 | 6,432.6% | 400 / 399 | Assemble 36, CrossBreach 1 |
| 기본 coarse LOW 400 | 16.718 | 16.510 | 6,074.7% | 400 / 399 | Assemble 36, EntryWait 1 |
| 프로파일러 비활성 LOW 400 | 17.069 | 미수집 | 미수집 | 400 / 393 | Assemble 36, EntryWait 1 |

비활성 값은 기존 `GameTick` stage 합계 20,483.3ms / 1200회에서 계산한 **경과 시간**이다. 기준 Core 계측과 OS CPU 수집도 비활성이라 정규화 CPU를 만들어 넣지 않았다. 경량 실행이 비활성 실행보다 조금 빠르게 나온 사실 자체가 환경·진행 차이를 보여 준다. 좁은 실행은 앞서 50/200명 시나리오를 거친 실행이고 대조군은 400명부터 시작했으며, 종료 단계도 다르다. 따라서 세 결과를 같은 조건의 전후 개선으로 집계하거나 1.152ms 차이를 전부 profiler 비용이라고 차감하지 않았다.

coarse에서 execution scheduler 0.647ms/tick(235.1% Core), orders tick 0.171ms/tick(62.0%), communications tick 0.168ms/tick(61.2%), 그 안의 RefreshFrames 0.143ms/tick(52.0%)가 기록됐다. 이 컴포넌트 합계만으로 전체 전술 시간을 판단하면 **Pawn의 바닐라 대기·작업에서 직접 호출하는 For/Controls 계열**을 놓친다. 반대로 작은 내부 메서드를 모두 패치하면 계측 부하가 커진다. 두 수집은 서로 다른 제한을 가진다.

따라서 상위 세 묶음은 유망하지만, 실제 제품 CPU 절감률을 확정하려면 이후 구현마다 같은 시나리오 순서·시작/종료 단계·타깃 집합의 반복 수집과 비활성 대조군을 다시 맞춰야 한다. 지금은 코드 수정 없이 병목과 절감 가설을 제시한 단계다.

## 수집 범위·완료 상태와 추가 발견

총 **44개 완료 capture, 서로 다른 350개 구체적 메서드 서명, 실제 호출 260개**를 기록했다. 총 CPU는 전체 게임 틱만 수집하고, 나머지는 호출·경과 시간 기반으로 기록했다. 이름이 같아도 오버로드/iterator MoveNext는 별도 서명이다. 90개 미호출 타깃도 coverage에 남겼다. 선택 대상으로 등록됐다는 것과 실전 비용을 검증했다는 것은 다르다.

실행 상태/단계/사상자 재평가, contacts/LOS/연막/portal 관측, 계획 iterator와 assignment/route, 국소 합류/스택/진입/security/명령 검토, roster/index/지식/보고 전달/통신 장비·연결, 지원 요청/협력 상태, 바닐라 Pawn/Job/path를 포함했다. 수류탄 준비·관측 보조 함수도 선택했다. 일부 callback, 공용 generic LINQ/engine/native worker 및 실전에서만 발생하는 경로는 완전하게 계측되지 않았다.

지원·협력의 NotifyLaunch는 LOW 50 구간 1회, Return은 9회/총 0.429ms, SupportEffects는 7회/총 0.465ms로 평균 최대 병목이 아니었다. 현재 큰 협력 비용은 후속팀의 공유 개구부 대기와 roster/명령 확인 쪽이다. 사상자 조정 ReconcileCasualties는 예를 들어 HIGH 403에서 231회/3.289ms였지만 공병 다수 사망 burst의 비용을 보장하지 않는다. `BlocksGun`은 LOW 400에서 134,764회/79.907ms였고 `Active`는 151,602회/16.670ms였다. 이 작은 보조 조회도 actor별 준비 상태를 공유하는 P0 캐시에 묶을 수 있다. 실제 grenade 투척 시작 등 미호출 기능은 비용 순위에 억지로 포함하지 않았다.

### 완료·비교 제한

- 정상 수치 감사 12개 실행은 마지막 `complete:true`와 원본 이동·생존 정보를 확인했다. 모든 capture는 `complete:true`, dropped=0, 계측된 메서드 예외=0이다. 이 조건은 기능 전체 성공을 보장하지 않는다.
- `support-low` 400명은 394명 생존/393명 이동으로 사상자가 발생해 균일 인원 scaling·절감률 산정에서 제외했다. 원본은 보관한다.
- 최초 `verify-high`는 52/208명 capture 뒤 전체 감사 완료 없이 종료했다. 예외·종료 원인은 로그에서 확정하지 못했다. 표의 52/208명은 완료된 개별 capture의 기술 통계로만 사용하고, 완결된 동일 조건 반복 검증이라고 부르지 않는다. 403명과 cleanup은 새 격리 실행 `verify-high-retry`에서 정상 완료했다.
- HIGH 403의 실행/좁은 재측정에는 10개 미시작 이동 명령이 600틱 이상 남는 결과가 있다. retry/destination reservation이 기록돼 있다. 이동 발생률이 높더라도 모든 security 도착이 정상이라는 결론은 내리지 않았다. CPU가 낮아진 사례로 해석하지 않는다.
- 최초 `functional-movement`는 fixture 시작 전 전체 완료 없이 종료해 측정 근거에서 제외했다. `functional-movement-retry`는 7개 기능 단계를 통과했지만 임시 수동 제어기의 UTF-8 BOM 때문에 profiler 명령 읽기가 실패했다. 기능 결과만 사용하고 메서드 계측 완료라고 부르지 않는다.
- BOM 없는 임시 제어기로 다시 실행한 `functional-movement-profile`에서는 3개 capture가 정상 종료됐지만 **기능 감사 1단계가 1800틱 제한을 넘겨 실패**했다. 11명 중 한 폰은 `(124,115)`에서 `(128,115)`로 Goto 중이었고 나머지 대부분은 지정 위치에서 대기했다. 원본 error를 보관했다. 타이밍/진행/계측 부하가 달라진 실행이므로 계측이 원인이라고 단정하지 않았다. 이 실패는 수정하지 않았다.
- 시험 완료·필터 이유는 [review.json](../../../../Source/Benchmarks/AgentProfiler/Results/2026-10-07-wide-tactical-analysis/review.json)에 별도 기록한다. 서로 다른 target 집합/phase/cold/functional을 합쳐 하나의 개선율을 만들지 않았다.

### 기능 실패 구간에서 기록된 합류 비용

이 구간은 11인 LOW 1분대의 강제 security 합류 fixture다. 수동 capture의 기본 metadata population/scenario/speed는 -1이며, 실제 fixture 인원을 CSV의 자동 population으로 덮어쓰지 않았다. 준비 600틱을 거친 steady 400명 구간과 비교하지 않는다. 창 3개는 각각 299/300/467틱이며 마지막 미완료 창은 게임 종료로 저장되지 않았다.

| 메서드 | 세 창의 호출 합계 | 경과 합계 ms | 평균 µs/회 | max ms | 창별 Core%/tick |
|---|---:|---:|---:|---:|---|
| KnownIndoorJoin | 28 | 21.537 | 769 | 3.548 | 16.15 / 5.02 / 3.02 |
| FollowNodes | 6 | 46.714 | 7,786 | 20.286 | 47.24 / 3.53 / 3.47 |
| RunScheduledUnit | 102 | 184.461 | 1,808 | 47.327 | 139.92 / 37.67 / 28.23 |
| RaidCqbLocalMap.RefreshMeasured | 6 | 6.920 | 1,153 | 2.825 | 6.75 / 0.87 / 0.45 |

위 행은 중첩되므로 더하지 않는다. 첫 창에 초기 계획·JIT/첫 실행이 섞여 있다. 뒤의 KnownIndoorJoin 평균은 약 596/563µs/회로, 초기 max를 정상 매 호출 비용으로 사용하지 않았다. 기능 재현이 실패했기 때문에 이 수치를 정상 완료 전체 단계의 평균으로 쓰거나 상위 세 병목 절감 시나리오에 추가하지 않는다. **국소 합류는 공유·반경 축소·순수 BFS worker를 검토할 실제 계산량이 있지만, 이번 대규모 steady 평균의 지배적 병목으로 확인된 것은 아니다.**

코어·전술·조직·프로파일링 소스 130개 파일의 작업 전후 SHA256이 모두 같고, 저장소/설치 DLL도 같은 해시를 유지했다. 신규 산출물은 이 분석 문서와 측정 데이터뿐이다. 코드 수정, 빌드, 배포, 최적화 구현은 하지 않았다.
