# 전술 AI 대기 처리 최적화 구현 결과

작업: 2026-10-06. [구조 개편 검토](%EC%A0%84%EC%88%A0%20AI%20%EA%B5%AC%EC%A1%B0%20%EA%B0%9C%ED%8E%B8%20%EA%B2%80%ED%86%A0.md)의 C 실행 비용 축소 중 개구부 대기 처리부터 적용했다. 전체 계획 서비스와 작업 구조의 교체는 아직 남아 있다.

## 적용 내용

| 처리 | 이전 | 변경 |
| --- | --- | --- |
| 대기 칸 소유자 조회 | 분대마다 다른 모든 대기자의 목적지를 다시 모음 | 폰→칸, 칸→폰 인덱스를 유지하고 개별 칸을 직접 조회 |
| 대기자 정리 | 같은 120틱에 각 분대가 전체 대기자를 반복 정리 | 해당 맵에서 한 번만 정리 |
| 개구부 사용권 정리 | 각 분대마다 전체 사용권 유효성 검사 | 해당 맵에서 같은 틱에 한 번만 검사 |
| 안전한 대기 분대의 구성·장비·배치 검사 | 매 30틱 반복 | 처음 30~180틱으로 분산한 뒤 180틱 간격. 피해 사건은 우회하여 즉시 재평가 |
| 안전한 대기 분대의 정기 관측 | 기본 20틱 간격 | 90틱 간격. 보이는 무장 적, 반응 작업, 접촉 중단, 지원 수비 상태에서는 기본 간격 사용 |
| 관측한 무장 적 없음 | 매번 관측자 조회와 맵 전체 폰 목록 검사 | 알려진 유효 무장 적이 없으면 바로 빈 결과 반환 |
| 폭발 위험 없음 | 인원마다 빈 위험 목록·점수·정렬 생성 | 살아 있는 위험 투척물·알려진 폭발물·진행 중 폭발 회피가 모두 없으면 바로 반환 |

정기 관측과 구성 검토를 늦춘 것이며, 폭발 회피·이미 식별한 적에 대한 대응은 기존 10틱 안전 갱신을 유지한다. 대기열 입장 가능 여부와 대기 칸 유효성은 정기 30틱에 계속 확인한다. 앞 분대가 공간을 반환하면 구성 검토 180틱이 끝날 때까지 기다리지 않고 입장한다. 실제 피해 사건은 다음 틱에 해당 분대를 재평가한다.

정지 자리를 다른 폰이 소유하고 있으면 새로 배정하지 않는다. 새 배정 실패가 이전 소유권을 훔치지 않으며, 사용권 획득·먼 거리 접근 전환·해당 단계 종료 시 자기 대기 칸을 해제한다. 후보의 실제 통행·예약·방 연결 검사와 정보 공유 조건은 유지한다. 이 변경은 통로의 물리 대기를 처리하며 LOW/HIGH 전술 보고를 새로 공유하지 않는다.

대기 칸 인덱스와 다음 구성 검토 시각은 런타임 자료다. 로드 시 다시 만든다. 현재 단계·선택 개구부·확정 명령·접촉 기억의 저장 방식은 그대로 사용한다.

## 계측과 검증

CPU 보고에 `OpeningQueue`와 `GameTick`을 추가했다. `GameTick`은 선택된 맵의 보고에 전체 `TickManager.DoSingleTick` 비용을 기록하며, 해당 맵 전술 코드만의 비용이 아니다. 개발자 CPU 계측을 켰을 때만 표본을 기록한다. 여러 맵의 보고를 더해 전체 게임 비용으로 해석하면 안 된다.

`Execution`은 하위 `Observation`·`OpeningQueue` 등을 포함한다. 구간 합계를 더하지 않는다. 감사 도구의 CPU 표본은 준비 구간까지 포함하며 TPS/FPS는 측정 구간만 사용한다. `queueMaintenance` 정리 횟수는 동일 맵에서 시나리오를 넘겨 누적된다.

표본의 개수·합계·최대값은 전체 구간, 분위수는 각 구간의 최근 최대 2048개 표본을 사용한다. 특히 6000틱 시험의 전체 틱 분위수는 전체 6000틱의 분위수가 아니다.

- 모드 빌드: 오류·경고 0개. 작업 디렉터리의 SourceLink 파일 잠금 때문에 `-p:EnableSourceLink=false`로 빌드했다.
- 지도·이동·사용권 자동 검증: 940개 통과. 다른 폰의 칸 중복 소유 금지, 실패한 재배정의 기존 소유권 보존, 해제·정리 일관성 포함.
- 설치된 실제 게임 클래스 검증: 기존 Security·외벽 합류·대형·관측·통신·수류탄·피해 재평가 검증과 새 전체 틱 계측 패치 바인딩 통과.
- 최종 DLL의 Security 실게임 5개 시험 통과: 열린 문 362틱, 관측한 새 개구부 378틱, 보이지 않는 반대편 문 개폐 433틱, 경계 해제 후 늦은 합류 276틱, HC 연막 중 통과 445틱. 각 시험 인원은 11명이다.

## 400명 대기 시험

같은 LOW 400명·37개 실행 단위, 300틱 준비·600틱 표본을 자리 인덱스만 바꾼 중간 DLL과 정기 작업까지 축소한 최종 DLL로 한 번씩 순서대로 실행했다. 현재 입구에서 389명이 대기하고 11명이 작업하는 조건이다. 전체 교전 인원이 400명인 시험이 아니다.

| 측정 | 중간: 자리 조회 개선 | 최종: 정기 작업 축소 추가 |
| --- | --- | --- |
| 1배 TPS | 23.981 | 30.938 |
| 3배 TPS | 27.178 | 33.892 |
| 1배 실행 CPU 합계 | 2476.2ms | 1859.3ms |
| 3배 실행 CPU 합계 | 2458.6ms | 1322.2ms |
| 3배 관측 CPU 합계 | 1542.7ms | 680.1ms |
| 1배 전체 틱 p50 / p95 | 22.885 / 54.338ms | 20.367 / 40.942ms |
| 3배 전체 틱 p50 / p95 | 21.503 / 49.203ms | 19.449 / 37.034ms |
| 1배 전체 틱 최대 | 221.720ms | 307.758ms |
| 3배 전체 틱 최대 | 302.475ms | 386.573ms |

두 DLL 모두 성공 계획 37개, 실패·한도 도달 계획 0개, 시험 종료 시 Native 준비 대기 0건이었다. 정리 횟수는 첫 시험까지 대기 칸 6회·사용권 26회, 두 번째 시험까지 누적 13회·53회였다. 같은 틱에 분대별 정리가 중복 실행되지 않았다.

**일반 틱과 실행 CPU 총량은 이번 두 측정에서 줄었지만, 가장 긴 틱은 줄지 않았다.** 단일 순차 시험이므로 개선율이나 수용 인원을 보장하지 않는다. [1차 계산량 축소](%EC%A0%84%EC%88%A0%20AI%20%EA%B3%84%EC%82%B0%EB%9F%89%20%EC%B6%95%EC%86%8C%201%EC%B0%A8%20%EA%B5%AC%ED%98%84%20%EA%B2%B0%EA%B3%BC.md)의 400명 TPS보다도 최종 결과가 낮다. 시험 순서·초기 상태·실행 중 게임 작업·GC 차이를 배제한 반복 비교가 아직 필요하다. 계획·실행 조각을 나누는 B 단계가 남아 있으며, 단일 바닐라 검증이나 배열 준비·GC의 순간 비용을 현재 코드가 끊어 처리하지는 못한다.

최종 DLL SHA-256: `5B00185874DA1A3AFA5EA5B94B9EB824103347165AEA78101C6044525B1F1C98`. 원시 결과는 [대기 처리 측정 JSON](%EC%A0%84%EC%88%A0%20AI%20%EB%8C%80%EA%B8%B0%20%EC%B2%98%EB%A6%AC%20%EC%B5%9C%EC%A0%81%ED%99%94%20%EC%B8%A1%EC%A0%95.json)에 보관한다. 중간 DLL의 해시는 별도로 확보하지 못했으므로 해당 측정은 단계별 진단 자료로만 사용한다.

## 후속 분대의 장시간 진행

최종 DLL로 LOW 50명·5개 실행 단위, 300틱 준비·6000틱 표본을 3배속에서 시험했다. 전원 생존·이동, 성공 계획 5개, 계획 실패와 한도 도달 0개, 종료 시 Native 준비 대기 0건이었다. 종료 단계는 `SecureRoom 3 / Breach 1 / Assemble 1`이며 후속 분대도 돌파와 방 확보를 진행했다. 모든 방의 정리 완료를 뜻하지는 않는다.

TPS/FPS는 179.561/57.699, 실행 CPU 합계는 1814.5ms, 전체 틱 p50/p95는 2.412/5.831ms, 전체 틱 최대는 159.712ms였다. 대기열 6명과 예약 등 다른 대기 원인도 종료 시 남아 있으므로 전원 진입 완료로 기록하지 않는다. Native 최고 사용량은 2,375,000 bytes였다. 대기 검토 간격이 늘어도 후속 진행은 확인했지만, 긴 순간 지연이 사라진 것은 아니다.

## 남은 범위

전체 계획의 중단·재개 가능한 서비스, 모든 실행 갱신의 분산 큐, 역할 작업과 명령 소유권 통합은 이번 변경에 포함하지 않았다. 기존 안전 폴링은 여전히 모든 활성 분대를 확인하며, 실제 교전 분대가 여러 개 늘어날 때의 비용은 별도 검증해야 한다. 개구부가 같은 400명 대기 시험만으로 다수 동시 CQB 성능을 보장할 수 없다.
