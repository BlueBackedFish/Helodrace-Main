# Security 이동 정지 원인과 대규모 전술 최적화 검토

작성: 2026-10-05. 분석 기준: `8fec0efe` 이후 현재 소스.

## 1. 결론과 확인 범위

Security에 문제가 집중되는 이유는 경계 인원이 돌입조와 다른 위치·임무를 갖는데도 같은 노드 완료 조건과 이동 제한을 적용하기 때문이다. 특히 **접촉 경계 명령과 집결 완료 조건의 충돌**, **이전 방에서 합류할 때 연결 문칸을 막는 제한**이 확인되었다. 이동 재시도 주기만 줄여서는 해결되지 않는다.

성능은 폰·분대·계획별 반복 조회와 맵 전체 크기의 이동 제한 배열을 함께 줄여야 한다. 현재 비동기화와 프레임 예산이 적용되어 있어도, 중복 생성·대기열·메인 스레드의 관측/계획 비용까지 해결된 상태는 아니다.

이번 작업은 원인 분석과 최적화 검토다. 게임 실행 코드는 수정하지 않았다. 생산 코드의 값 기반 정책을 직접 링크한 [분석 도구](../../Source/Benchmarks/RaidMovementAudit/Program.cs)와 [측정 결과](Security%20이동%20정지와%20대규모%20전술%20최적화%20측정.json)를 추가했다. 정책 반례는 재현했지만, 사용자가 보고한 게임 장면을 동일하게 재현하거나 현재 습격의 TPS를 측정한 것은 아니다.

## 2. Security 이동의 구조적 충돌

### 2.1 접촉 경계로 남겨 둔 폰에게도 노드 집결을 요구한다

관련 코드:

- [RaidCqbContactResponse.cs](../../Source/Helodrace/Core/RaidCqbContactResponse.cs): `RespondToCqbContacts`, `ApplyContactGuard`, `ContactGuardFor`.
- [RaidTacticalOrders.cs](../../Source/Helodrace/Core/RaidTacticalOrders.cs): `Set`.
- [RaidNodeMovement.cs](../../Source/Helodrace/Core/RaidNodeMovement.cs): `FollowNodes`.
- [RaidTacticalExecution.cs](../../Source/Helodrace/Core/RaidTacticalExecution.cs): `Update`의 Assemble 분기와 `AllReady`.

실행 순서는 다음과 같다.

1. CQB 접촉 대응에서 돌입 인원 이외의 폰을 우선 선택해 `ContactGuard`로 배정한다. Security가 이 대상이 되기 쉽다.
2. 전체 분대의 접근을 중단할 정도의 접촉이 아니어도 경계 인원은 유지될 수 있다. 경계 기한은 마지막 관측 시점에서 600틱이다.
3. `Orders.Set`은 해당 폰의 일반 이동 명령을 경계 위치의 Move/Hold로 바꾼다. 따라서 접근 노드로 이동하라는 요청이 실제로는 다른 위치를 유지하라는 명령이 된다.
4. `FollowNodes`는 Withdraw 이외의 모든 배정 인원을 진행 대상으로 포함한다. `ContactGuard`를 제외하지 않는다.
5. 마지막 Gather/BreachPreparation 노드는 그 대상 전원이 노드 진행을 완료해야 통과한다. 경계 위치에 남은 폰이 완료하지 못하면 전체 접근이 끝나지 않는다.
6. 이후 `AllReady`에서는 경계 인원을 제외하지만, `FollowNodes`가 성공해야 그 함수까지 도달한다. 이 예외는 앞 단계의 대기를 해소하지 못한다.

분석 도구에서 실제 `TacticalNodeProgress.Advance(true, 13, 12)`는 false다. 이는 13명 중 한 명을 경계 위치에 남겨 놓고 13명 전원의 최종 노드 완료를 요구하는 호출 조건의 반례다. 경계 폰이 우연히 노드 부근에 있는 장면에서는 발생하지 않을 수 있다.

**수정 방향:** 이동 참여 인원과 경계 잔류 인원을 명시적으로 분리한다. 경계 임무 중에는 일반 접근 진행을 일시 중지하고, 경계 해제 시 그 폰의 현재 위치에서 알려진 연결부를 통해 합류한다. 모든 단계의 완료 조건이 같은 참여 집합을 사용해야 한다. 수류탄 폭발 대기나 진입 순서까지 무조건 건너뛰는 처리는 하지 않는다.

### 2.2 이전 방에서 합류하는 길의 문칸·파괴된 벽칸을 막는다

관련 코드: [TacticalNodeProgress.cs](../../Source/Helodrace/Core/TacticalNodeProgress.cs)의 `AllowsStep`, [TacticalMovementMask.cs](../../Source/Helodrace/Core/TacticalMovementMask.cs)의 `Calculate`.

새 접근 계획의 허용 방이 B인데 경계 폰은 이전 방 A에 남아 있는 조건을 보자. 현재 코드는 허용 경로 밖인 현재 방에서 움직이는 것을 허용하지만, **현재 방과 다음 방 사이의 연결 칸도 허용되는지는 별도 문제**다. 정적 캐시의 문칸은 독립된 방 번호를 가질 수 있고, 파괴된 벽칸의 정적 번호는 0일 수 있다.

분석 도구에서 현재 방 1, 허용 방 목록 `[2]`를 적용한 결과:

| 다음 칸 | 정적 방 번호 | 물리 이동 허용 |
| --- | ---: | --- |
| 이전 방 바닥 | 1 | 허용 |
| 문 자체의 칸 | 3 | 차단 |
| 선택된 문 자체의 칸 | 3 | 차단 |
| 부서진 벽의 원래 칸 | 0 | 차단 |
| 다음 방 바닥 | 2 | 허용 |

문이 선택되어 있어도 방 제한 부분을 통과하지 못한다. 경로 비용 배열도 이 합류 조건에서 문칸과 벽칸을 차단한다. 허용된 다음 방이 존재하는 것과 실제 연결된 길이 존재하는 것은 다르다.

앞서 개구부 통과와 개인 노드의 비용/물리 제한을 맞춘 수정은 의미가 있지만, 돌입조 위치에서 만든 다음 계획에 후방 경계 폰을 합류시키는 문제까지 해결하지는 않았다. 후방 경계 인원에게는 이미 통과한 연결부를 통한 개인 합류 구간이 필요하다. 최종 Security 배정 위치가 이전 방에 있는데 돌입조의 다음 방 노드까지 다녀오게 하는 것도 피해야 한다.

**수정 방향:** 개인별로 현재 방에서 공통 접근 구간 또는 배정 위치까지의 짧은 합류 연결을 계산한다. 관측/확보한 연결부와 그 칸의 정적 방 번호를 함께 허용한다. 방 번호 0이나 모든 문을 전역 허용하면 외부 우회와 다른 개구부 선택 문제가 다시 생기므로 해당 연결 칸만 허용해야 한다.

### 2.3 “집결” 텍스트는 실제 이동 시작 확인이 아니다

현재 `HD_RaidTactical_Assemble` 텍스트는 실행 상태 생성과 다음 방 계획 활성화 시 출력된다. `RaidTacticalSpeech.Say`는 텍스트를 띄울 뿐, 실제 Goto 생성이나 경로 준비를 확인하지 않는다.

이후 실제 명령은 접촉 경계로 바뀔 수 있고, 연막·위협 대응 때문에 일반 접근이 보류될 수 있다. 이동 배열 미준비이면 Move 요청이 있어도 대기 작업을 받을 수 있다. Invalid 대형 위치, 보호된 장비 작업, 개구부 점유도 각각 다른 대기 이유다. 현재 표시만으로 이들을 구분하기 어렵다.

개발자 표시에는 요청 목적지, 최종 적용 목적지, 현재 명령 소유자, 이동 참여 여부, 실제 Job, 경로 준비 상태, 차단 이유와 지속 틱을 분리해 보여 주는 것이 좋다. “집결 시작” 상태와 “이동 Job 적용됨”도 분리한다.

### 2.4 공유 진입점의 대형 자리 부족도 별도로 남는다

개구부 직전 칸의 점유 대기는 이전 수정으로 추가했지만, 복수 조직이 같은 진입점에서 대형을 만들 때 자리 배정까지 조직 간 대기 순서로 관리하는 것은 별개다. 다른 조직의 대형을 제외하고 자리를 찾다 Invalid가 생기면 집결이 끝나지 않을 수 있다.

이 문제는 위의 접촉 경계 충돌과 구분해서 기록해야 한다. 진입점 사용 조직, 대형 구역 사용권, 후속 조직의 대기 구역을 명시하고 앞 조직의 통과 완료에 맞춰 넘기는 방향이 적절하다.

## 3. 지연과 확장성의 현재 비용

기호: 맵 칸 수 M, 분대 수 U, 전체 폰 수 N, 분대원 수 P, 적 후보 수 E, 생성된 이동 제한 배열 수 K.

| 항목 | 현재 구조와 비용 | 판단 |
| --- | --- | --- |
| 이동 제한 배열 생성 | 국소 이동에도 `ushort[M]`을 할당하고 전 칸 검사 | O(M×새 배열 수). 가장 먼저 중복 생성을 줄일 대상 |
| 배열 키 | 일반 이동은 Plan 객체별 사전, 진입/교전은 UnitId 등이 포함 | 같은 허용 조건이 서로 다른 계획·조직에서 중복 저장될 수 있음 |
| 준비 대기열 | 전체 맵에서 계산 작업 하나만 실행. 미완성 64개 초과 시 오래된 준비 취소 | 폭주 시 취소→재생성·오래된 요청 지연 가능. 실제 취소량 계측 필요 |
| 완성 배열 수명 | 현재 PathFinder 해제 때까지 NativeArray 보관 | 64는 미완성 대기 제한이며 완성 캐시의 메모리 상한이 아님 |
| 완료 통지 | 배열 하나 완성될 때 OwnerPlan의 배정 인원 전체에 준비 확인 통지 | 실제 그 배열을 기다리는 폰만 깨우도록 변경 가능 |
| 명령·조직 조회 | ForPawn의 기본 등록 조회는 사전이지만 이후 그룹 래퍼 생성, 소유권/배정 검색 등이 반복 | 한 틱의 확정 조회를 인덱스로 공유할 여지가 큼 |
| 대형/진입 조회 | 여러 실행 상태·배정 인원·점유 폰을 재조회하고 LINQ/목록 생성 | 분대마다 재작성하면 U×N에 가까운 반복 스캔 발생 가능 |
| 접촉 후보 탐색 | 분대별 전체 맵 폰 필터, 분대원 거리 검사/정렬 후 후보 32개 | 후보 탐색은 대략 U×E×P; 관측 지식과 물리 후보 조회를 분리할 필요 |
| 접촉 LOS | 분대당 기본 예산 96, 스캔 간격 20틱 | 분대 수가 늘면 전체 예산도 증가. 위치가 비었는지 재확인하는 추가 LOS는 이 후보 예산 밖 |
| CQB 국소 지도 | 반경 16, 최대 33×33칸을 읽고 배열 4개를 새로 구성 | 동일 중심은 30틱 간격. 중심 이동 시 그 간격보다 일찍 갱신 가능 |
| 접촉 경계 중심 선택 | 각 분대원의 다른 분대원 거리 합으로 중심 폰 선택 | 분대 내부 O(P²). 다수 분대에서 반복 시 추가 비용 |

CQB 국소 지도가 모든 칸에 매번 LOS를 쏘는 것은 아니다. `Knowledge.Read`는 기존 정보와 실제 값의 차이를 확인한 뒤 관측 여부를 검사한다. 그래도 국소 구역 전체의 건물·통행 정보 조회와 배열 할당은 남는다.

현재 `TacticalCacheBudget`의 프레임당 약 2ms/2048 작업 예산은 캐시 수집·배열 게시에 적용된다. 동기 계획 생성, 후보 경로 검사, 접촉 대응과 전체 LOS 비용을 제한하는 공통 전술 예산은 아니다. 라이브 칸 수집은 한 칸당 예산을 쓰지만 Native 복사는 256칸 묶음당 한 번을 쓰므로 2048을 모든 작업의 칸 수 제한으로 해석해서도 안 된다.

정적 최초 수집만 고려해도 250/400/600 정방형 맵은 최소 약 31/79/176 프레임이 필요하다. 이는 시간 예산과 다른 작업 경쟁을 제외한 하한이며, 매 폰 이동마다 최초 수집을 반복한다는 뜻은 아니다.

`BuildMilliseconds`는 준비 객체 생성부터 완료까지의 경과 시간을 합산한다. 작업 대기·프레임 예산 대기까지 포함하고, 동시 대기 시간도 중복 합산하므로 전술 CPU 사용 시간으로 보면 안 된다. 경로를 기다려 느린 것과 CPU 작업으로 프레임이 느린 것을 별도로 계측해야 한다.

## 4. 값 기반 코드 측정

Release, .NET 10.0.7, 워밍업 8회 후 각 48회. 실제 `TacticalMovementMask.Calculate`를 링크해 측정했다. 합성 입력은 단일 방의 평지이며 국소 조건은 31×31=961칸이다. Unity/Mono 런타임, 라이브 맵 수집, 비동기 대기, NativeArray 게시, 바닐라 경로 탐색 비용은 포함하지 않는다.

| 맵 | 일반 노드 중앙값 / p95(ms) | 961칸 국소 제한 중앙값 / p95(ms) | 배열 하나 | 완성 배열 64개 / 256개 |
| --- | --- | --- | --- | --- |
| 250×250 | 0.396 / 0.503 | 0.502 / 0.682 | 122.1KiB | 7.63 / 30.52MiB |
| 400×400 | 0.966 / 1.258 | 1.211 / 1.498 | 312.5KiB | 19.53 / 78.12MiB |
| 600×600 | 2.167 / 2.632 | 2.557 / 2.917 | 703.1KiB | 43.95 / 175.78MiB |

메모리는 `2×M×K`로 계산한 비용 배열 자체만의 값이다. 준비 중 관리 배열, HashSet, 구조 스냅샷, 바닐라 경로 탐색 메모리는 별도다. 실제 유지 배열 수가 64/256개라는 측정은 아니다.

확인된 것은 **작은 구역을 제한해도 계산·할당이 전체 맵 크기에 비례한다는 점**이다. 이 수치를 게임 내 TPS 개선율이나 현재 지연의 원인별 비중으로 환산할 수는 없다. 현 로그에는 이 증상을 설명할 명령/경로 상세 추적이 없었고, 기존 성능 보고서도 2026-09-15의 적 폰 0명 상태여서 현재 습격의 근거로 쓰지 않았다.

재실행:

```powershell
dotnet run --project Source/Benchmarks/RaidMovementAudit/RaidMovementAudit.csproj --configuration Release
```

| 높음 | 폰→실행 상태/배정/명령/노드 진행 인덱스, 틱별 조직 스냅샷 | 이동 한 칸마다 반복되는 검증·래퍼·선형 검색 감소. 사망/편제 변경은 즉시 무효화 |
| 높음 | 맵 단위 대형 점유·개구부 점유 인덱스 | 분대마다 다른 분대 전체를 반복 조회하는 구조 제거. 물리 점유는 최신 상태 유지 |
| 높음 | 허용 조건이 같은 이동 배열 공유 | Plan/UnitId 대신 구조 버전·허용 방/연결칸·초기 방·모드 등 실제 입력 내용으로 키 구성. 지식이 다른 조직은 무조건 공유하지 않음 |
| 높음 | 완성 캐시 메모리 상한과 안전한 회수 | NativeArray 참조 중인 경로 Job이 끝난 후에만 회수. 배열을 쓰는 Job의 수명 추적이 선행되어야 함 |
| 높음 | 실제 대기 폰 목록과 공정한 작업 대기열 | 같은 요청 중복 합치기, 필요한 배열만 준비, 준비 완료 시 관련 폰만 통지. 오래된 실제 이동 요청을 신규 예비 요청보다 우선 |
| 중간~높음 | 국소 구역 변경 이벤트와 청크 버전 | 문/벽 변화가 일어난 구역만 갱신. 안전망 저빈도 폴링을 유지하고 관측되지 않은 변화는 조직 지식에 반영하지 않음 |
| 중간~높음 | 전체 맵의 적 후보 공간 인덱스와 LOS 결과 캐시 | 분대마다 전체 폰 스캔 제거. 같은 관측자/대상 위치·구조·연막 버전의 검사를 공유. LOW 접촉/무전 지식 공유 규칙은 유지 |
| 중간 | 맵 전체 관측·계획 예산과 분대별 최소 서비스 | 분대 수에 비례해 예산이 무한 증가하지 않게 관리. 긴급 피격·수류탄 대응은 일반 재계획 대기열보다 우선 |
| 중간 | 값 기반 작업 전용 워커 2개부터 검증 | 현재 단일 워커의 직렬 대기 감소. 이후 4개와 비교하되 Map/Pawn/Thing 접근은 메인 스레드에 남김 |
| 후순위 | 임시 배열/목록 풀, 방 허용 비트셋, 디버그 문자열 캐시 | 할당 감소. 워커 사용 중인 입력을 풀에 먼저 반납하지 않음. UI는 4~5Hz 정도로 문구 갱신 |

### 5.1 전체 맵 배열 의존을 줄일 수 있는가

가능하지만 바닐라 `PathRequest.IPathGridCustomizer.GetOffsetGrid()`는 맵 전체 인덱스로 읽는 `NativeArray<ushort>`를 받는다. 여기에 961칸짜리 배열을 그대로 넘기는 방식으로는 바꿀 수 없다.

단기에는 같은 조건의 배열을 공유하고 쓸모 없어진 조건을 안전하게 회수한다. 중기에는 방/연결부 그래프에서 개인 합류 구간과 다음 이동 지향점을 먼저 정하고, 그 짧은 구간에는 바닐라 Goto를 사용하면서 선택된 연결부와 크게 벗어난 경우만 재판단하는 방향을 검토한다. 이미 알려진 개구부로 후속 인원을 안내하는 규칙은 유지한다.

전체 비용 배열만 제거하고 기존 물리 이동 차단을 그대로 남기면 바닐라는 금지된 우회 경로를 계속 만들고 실제 이동이 거부되는 문제가 생긴다. 경로 선택과 물리 허용 조건을 함께 설계해야 한다. 공유 흐름장도 다음 지향점 제시에는 사용할 수 있지만 모든 폰에게 같은 칸을 강요하는 이동으로 바꾸지는 않는다.

### 5.2 NativeArray 회수는 단순 LRU만으로 충분하지 않다

바닐라 `PathFinder`는 비동기 Job이 사용자 비용 배열을 계속 참조할 수 있다. `PathRequest.Dispose()`는 취소 표시와 결과 경로 해제를 하며, 해당 Job 완료를 보장하지 않는다. 현재 캐시가 PathFinder 해제까지 배열을 유지하는 것은 이 수명 문제를 피하기 위해서다.

회수하려면 예약/실행 중인 Job과 배열 참조를 추적하고, 완료된 참조가 없는 배열만 지연 회수해야 한다. 매번 모든 Job을 강제로 완료시키거나 사용 중 배열을 덮어쓰는 것은 피한다. 이 조건을 해결한 후 메모리 예산·LRU·버퍼 풀을 도입한다.

### 5.3 멀티스레드, Jobs/Burst의 적용 범위

현재 정적 구조 계산과 이동 제한 계산은 값 기반이며 이미 백그라운드 작업이다. 다만 전체 맵 공통으로 동시에 하나만 실행된다. 긴급 이동 준비와 정적 갱신 작업을 분리한 제한된 워커 풀은 가능하다.

스냅샷을 메인 스레드에서 확정하고 워커는 불변 숫자/플래그만 처리한 뒤 결과를 게시한다. 세대 번호로 오래된 결과를 버리고, 취소/입력 소유권/완료 통지를 명확히 한다. 폰별 무제한 Task나 Map/Pawn/Thing을 직접 읽는 작업은 채택하지 않는다.

바닐라 PathFinder도 Job 스케줄링을 사용한다. 추가 워커는 이 작업들과 CPU를 공유한다. 중복 계산과 준비 의존성을 먼저 줄이지 않고 스레드만 늘리면 메모리, 게시 비용, 명령 충돌은 그대로 남는다. Jobs/Burst로 우리 값 기반 계산을 옮기는 것은 이후 프로파일에서 계산 자체가 충분히 큰 병목일 때 검토한다. GPU 경로 탐색이나 바닐라 전투 AI 전체의 스레드 이전은 이번 수정의 우선 대상이 아니다.

### 5.4 관측 정보와 물리 캐시는 분리한다

공유 가능한 것은 건물 구조·물리 점유·근처 적 후보·동일 LOS 계산 결과다. 캐시 결과가 존재한다는 이유로 모든 분대가 적을 관측한 것으로 처리하면 안 된다. 관측자별 감지 결과와 LOW의 접촉 통신, HIGH의 무전 통신, 방 클리어 기록은 기존 정보 접근 규칙을 따로 유지한다.

## 6. 권장 작업 순서와 검증

기존 8단계 계획의 번호를 바꾸는 것이 아니라 현재 문제를 해결하기 위한 별도 작업 묶음이다.

1. 경계 임무와 노드 진행 대상의 충돌 제거, 후방 개인 합류 구간, 명령 차단 이유 계측. 먼저 멈춤을 제거한다.
2. 폰/배정 조회 및 대형/점유 인덱스, 실제 대기자 통지, 공정한 대기열과 전체 전술 예산 도입.
3. 동일 이동 배열 공유와 NativeArray 수명 추적·메모리 상한 적용. 이후 전체 배열이 필요한 경우 자체를 줄인다.
4. 동적 구역 이벤트 갱신, 적 후보 공간 인덱스, LOS 캐시와 관측 예산 개선.
5. 남은 계산 대기와 CPU 프로파일을 근거로 워커 2/4개 또는 Jobs/Burst 비교.

게임 검증은 같은 외벽·복도·좁은 방에서 50/100/200/400명, 같은 개구부를 사용하는 복수 조직, 돌입조가 다음 방에 있고 Security가 이전 방에 있는 상황을 포함한다. 접촉 경계 유지/해제, 숨은 문 개폐, 예기치 않은 벽 파괴, 연막, 개구부 점유도 각각 구분한다. 빈 맵과 전술 없는 바닐라 공병을 같은 인원으로 비교하고 게임 속도 1배/3배를 기록한다.

필수 계측값:

- 메인 스레드의 계획/관측/대형/명령 처리별 CPU p50/p95/p99, 프레임 최댓값, FPS/TPS.
- Move 요청→실제 Job 적용까지 틱 수. 경계·폭발·점유 등 의도된 대기 시간은 따로 기록.
- 배열 신규 생성/재사용/취소/재생성 수, 최대 대기열 길이, 대기 요청 최대 나이.
- 완성/준비 중 NativeArray 메모리와 관리 할당량/GC 빈도.
- 차단 이유별 폰 수·지속 시간, 요청 목적지와 적용 목적지의 차이.

경계 임무로 남은 폰 때문에 다른 인원의 집결이 영구 대기하지 않고, 이전 방의 폰이 알려진 연결부를 통해 합류하는 것이 기능 검증의 첫 기준이다. 성능 개선율과 적정 예산은 이 실게임 기준 측정 후 정한다.
