# R2 최소 돌파·진입 구현과 검증

2026-10-08. **R2 완료: 최소 돌파·진입 기능과 반복 CPU 기준 통과.** 최신 작업 지침에 따라 `main`에서 진행한다. 이전 실험 브랜치의 R0/R1 기록은 fast-forward로 보존했다.

## 구현 범위

새 엔진은 [분대 명령 서비스](../../Source/Helodrace/Tactics/TacticalCommands.cs), [국소 계획](../../Source/Helodrace/Tactics/TacticalLocalPlan.cs), [지속 작업](../../Source/Helodrace/Tactics/TacticalJobs.cs)으로 구성된다. 기존 조직·편제·장비 정의와 해머/문 고장 효과를 사용하며, 구형 실행·통신·캐시·이동 후크는 설치하지 않는다.

- 전역 스케줄러가 모든 맵에서 한 틱당 최대 2개 분대를 판단한다. 최대 4개 due 항목을 확인하고, 처리 경과 시간이 1.5ms를 넘으면 다음 판단을 다음 틱으로 넘긴다. 하나의 판단 내부를 선점하는 제한은 아니다.
- 습격 Lord 생성 시 멤버와 작업 소유권을 등록한다. 300틱마다 누락/로드 상태를 확인한다. 분대 평상시 판단은 120틱, 돌파·진입은 30틱, 입구 사용 대기는 240틱, 완료 상태는 600틱 간격이다. 완료·실패·사상자 이벤트는 due 시점만 앞당긴다.
- 목표 방향으로 최대 256칸을 확인하고, 벽/문 경계 후보는 최대 8개, 최종 도달 가능성 검사는 최대 2개로 제한한다. 적합한 일반 문을 우선하고, 외벽 앞의 고립된 장애물은 외벽으로 해석하지 않는다.
- 스택은 같은 벽면에서 이어지는 고유 자리다. 기본은 한쪽 대형이며 짧은 벽에서는 입구 바로 뒤를 비워 두고 그 뒤쪽에서 양쪽을 연결한다. 코너 너머로 연장하지 않는다. 대형과 진입 후 자리는 계획 생성 때만 정한다.
- 각 폰은 하나의 지속 Job을 가진다. 집결 후 정지·방향 보기, 해머 돌파, 외부 칸→실제 개구부→첫 실내 칸→가까운 벽 자리의 진입 순서다. 후미도 동일한 진입 Job을 사용한다.
- 개구부를 지난 이력은 작업 중단 후에도 유지한다. 실내까지 통과한 폰은 재시도할 때 바깥 집결 칸으로 되돌아가지 않는다. 일반 이동에는 통과 노드나 매 셀 경로 교정이 없다.
- 이미 확보한 개구부의 작은 대형/실내 자리 목록을 최대 8개 보관한다. 같은 접근면·목표 방향이고 현재 통행/자리가 유효하면 후속 분대가 재사용한다. 전체 방 구조나 맵 격자를 캐싱하지 않는다.
- 물리적 자리와 입구 사용권을 분대끼리 공유해 중복 정지를 막는다. 전술 정보 공유/다중 진입 협력은 R5 범위다. 임무 완료 후 바닐라 전투에 제어를 반환한다.

이 단계는 한 겹 외벽/일반 문과 한 방 진입이다. 관측·수류탄·연막·폭발 장비·떨어진 공병 장비 회수·다방 정리·동적 교전은 R3 이후다. 착용한 해머가 남아 있으면 다른 운용자로 교체하며, 아무 운용자도 없으면 바닐라에 반환해 분대 전체의 영구 정지를 피한다. 저장/로드의 전체 실행 복원과 다중 맵 부하 검증은 R7에 남아 있다.

## 한 번 돌파하는 이유와 남은 틱 스파이크

현재 한 번 돌파한 뒤 새 전술 AI가 끝나는 것은 시험 맵만의 설정이 아니라 **R2 실행기의 구현 범위**다. `TacticalCommands.Advance`는 모든 생존 멤버의 진입이 확인되면 `Complete`로 전환하고 소유 Job·자리 사용권을 해제해 바닐라 전투로 넘긴다. 최종 목표까지 여러 방을 연속으로 돌파하는 반복은 아직 없다. 같은 입구가 다시 막히면 진입 중 돌파로 돌아가는 국소 복구는 가능하지만, 다음 방 임무를 생성하는 기능은 아니다. 인접 구역 정리와 연속 방 돌파는 R3에서 추가한다.

2026-10-08 사용자 플레이 관측: **인원이 많아지면 틱 스파이크가 발생한다. 미해결 성능 문제로 유지한다.** 위/아래 CPU 평균 합격을 이 문제의 해결로 해석하지 않는다. 실제 플레이의 발생 인원·반복 빈도·호출별 원인은 아직 특정하지 않았다. 기존 통제 시험에서도 전체 틱 최대 지연과 지휘 Tick 최대 약 16.92ms가 기록됐으나 사용자 관측의 직접 원인이라고 확정하지 않는다.

현 스케줄러의 1.5ms 예산은 분대 판단 사이에서만 검사한다. 한 `Advance` 내부의 멤버 순회·계획·Job 발행·바닐라 길찾기나 초기 JIT가 길면 중간에 멈추지 못한다. 이는 조사 후보이며 원인 확정은 아니다. 후속 성능 작업에서는 문제가 나타나는 규모에서 지휘 Tick/Advance와 실제 의심 내부 메서드, 전체 틱/Core 기준을 짧게 수집해 긴 단일 호출과 같은 틱에 몰린 호출을 구분한다. 기본 검증은 [약식 기준](최적화%20전술%20AI%20검증%20기준.md)을 따른다.

## 실행 방법

시작 인수 `-hdTacticalEngine=new`를 사용한다. 엔진 선택은 실행 중 바꾸지 않는다. 기본 선택은 비교용 Legacy로 유지한다.

개발자 도구 `Helodrace/New tactical AI`에서 명시 목표 칸을 지정하거나 분대 명령 상태를 확인할 수 있다. 명시 목표가 없으면 이름 있는 소유자의 침대를 기본 목표로 쓴다. 명시 목표를 사용하면 AI 대 AI 임무에도 사용할 수 있다.

## 검증 방법과 현재 결과

[독립 시험 실행기](../../Source/Benchmarks/TacticalEngineAudit/Run-R2Functional.ps1)는 야외 명시 목표 일반 이동, 문, 16칸 실내, 외벽 앞 장애물, 실내 통과 후 작업 중단, High 공병 사망, 200명 요청을 실제 게임에서 실행한다. 구형 컴포넌트/후크가 0개이고 New 컴포넌트가 정확히 2개인지 확인한다. 진입 완료뿐 아니라 실제 개구부 통과·후미 통과·연결 대형을 기록한다. 문 시험은 실제 고장을, 중단 시험은 바깥으로 돌아가지 않았는지 추가 확인한다.

초기 시험에서 LOW 12명 외벽 진입, 12명 일반 문 고장 후 진입, 50명 요청으로 생성한 LOW 60명/5개 분대의 진입이 완료됐다. 60명 시험은 60명 모두 선택한 개구부를 통과했고 5개 분대 모두 실내 자리에 도착했다. 이는 초기 구현의 기능 확인이며 최종 빌드 반복 대조 결과가 아니다.

성능 합격은 같은 최종 DLL·지도·장비·편제·시드·수집 대상·틱 구간의 Vanilla/New를 각 3회 비교한다. 실제 전체 틱 CPU와 틱 밖을 포함한 메인 스레드 구간 CPU 모두 2배 이하여야 한다. 새 실행기의 모든 분대 진입 완료가 확인되지 않으면 저렴해도 합격하지 않는다. 메서드 경과 시간은 Core 기준 배치 대비 비율과 함께 기록하며, 메서드별 실제 CPU 점유율이라고 해석하지 않는다.

## 최종 기능 회귀와 증거

최종 DLL의 실제 게임 회귀 6개가 모두 통과했다. CPU 행렬 24회와 합쳐 최종 검증은 30회다. HIGH는 13인 공병 사망 기능 사례이며 대규모 HIGH CPU 검증은 이번 결과에 포함하지 않는다.

| 사례 | 실제 생존/진입 | 전 분대 완료 틱 | 추가 확인 |
|---|---:|---:|---|
| 야외 명시 목표 | 12/12 | 963 | 벽 없는 일반 이동, 자동 침대보다 명시 목표 우선 |
| 일반 문 | 12/12 | 871 | 문 파괴 대신 고장 1개, 개방 후 실제 통과 |
| 16칸 방 | 12/12 | 1,110 | 외벽 코너 밖 오인 없음, 실내 고유 자리 |
| 외벽 앞 장애물 | 12/12 | 1,140 | 고립된 바위를 경계로 택하지 않음 |
| 진입 중 작업 중단 | 12/12 | 1,175 | 강제 중단 1회 복구, 활성 임무 중 외부 복귀 없음 |
| HIGH 공병 사망 | 12/12, 생성 13 | 1,299 | 공병 직접 사망 후 남은 착용 해머 운용자로 승계 |

새 스택의 연결 검사는 계획 슬롯의 연결과 벽면 배치를 확인한다. 모든 생존 폰이 동시에 자리를 채운 뒤에만 돌파한다는 보장은 아니다. 1,200틱 미도착 유예가 지나거나 입구가 이미 열리면 진행할 수 있다. 떨어진 해머를 주워 오는 동작은 R3다.

[검증 원본·요약](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-08-r2/README.md)에 최종 30회와 사전 31회 기록을 분리했다. gzip 원본 429개는 원래 바이트 길이/SHA-256으로 검증했고, 압축을 푼 원본에서 네 대조를 재실행해 같은 수치와 합격을 확인했다. `excluded`는 실패뿐 아니라 이전 DLL·fixture·서로 다른 생성 지문·부분 창·짧은 생성 확인도 포함한다. 이 기록은 최종 CPU 합격의 분모/분자에 넣지 않았다.

실제 게임 클래스 바인딩·새 엔진 격리·스택 연결·활성 Assault/ExitMap 소유권·시험 제약의 일반 생성 비적용 검사, 메서드 수집기/Core/Windows CPU/fixture v9 CPU 게이트 검사, 실제 capture 기반 CLI 비교 검사가 통과했다. 게임 빌드는 경고/오류 0개였다. 최종 로그 30개에 수집 시작 후 예외/오류는 없었다. 초기 콘텐츠 로딩에는 기존 탄약 텍스처 누락 5종이 모든 엔진/사례에서 동일하게 있었다. 이 내용과 원본 로그도 보존하며 R2 실행 오류와 구분한다.

기능 커밋은 `346f9f37`(새 실행), `d8e904a4`(개구부 재사용·중단 복구), `8388e3ba`/`c2064d36`(대조 생성 재현성)이다. R3는 아직 시작하지 않았다.

## 시험에서 발견한 문제와 수정

- 16칸 방 시험에서 외벽 코너 밖의 빈칸을 개구부로 오인했다. 빈 경계 후보는 양옆에 실제 벽이 있는 틈으로 제한하고, 최종 자리의 실제 실내 위치도 감사에 추가했다.
- 작은 방의 측면 자리만 사용하면 LOW 12명이 들어갈 자리가 부족했다. 입구 첫 칸을 비운 채 깊이 2~4의 연결된 자리를 제한적으로 허용하고, 깊이 4는 인접 벽이 있을 때만 선택한다.
- 실내 통과 후 작업이 중단되면 재시도 유예 동안 바닐라 escort/wander가 끼어들었다. 기존 실내 자리로 지속 정지 작업을 유지하고 통과 이력을 보존한다. 완료 후 바닐라에 반환한 움직임은 중단 회귀 판정에 포함하지 않는다.
- 204명 첫 시험은 17개 중 16개 분대만 새 임무를 완료했다. 마지막 분대가 새 대형 후보를 반복 탐색하다 바닐라로 반환된 실행은 실패로 보존했다. 확보한 개구부의 작은 자리 목록을 재사용한 다음 시험은 17개/204명 모두 실제 개구부 통과와 진입을 완료했다.
- 60명 반복 CPU 대조의 fixture v7은 일부 실행의 생성 폰 지문이 달랐다. 월드폰 관계를 제한한 v8의 짧은 204명 시험 4회는 일치했지만, 이후 배경·특성·유전자·열정까지 포함한 60명 지문은 다시 달랐다. 관계만으로 원인을 해결했다고 보지 않고 두 버전의 대조를 제외했다. 최종 v9는 시험용 이름·나이·성별·계통을 명시하고 무작위 배경·특성·관계를 제외한다. 나이는 18~35세, 실제 5종 계통을 순환하므로 속도 차이는 유지한다. 실제 조직·장비·기술 생성은 유지하며 일반 플레이 생성은 바꾸지 않는다. 원본을 편집해 맞추거나 다른 지문을 같은 그룹으로 합치지 않는다.
- 204명 긴 실행은 기존 300초 자동 종료에 걸려 측정 틱 창이 잘렸다. 일반 수집 제한은 유지하고 명시적인 격리 전술 감사만 1,800초까지 허용한다. 부분 수집은 CPU 합격에서 제외한다.

시험에서는 모든 엔진의 공격자 피해를 막아 고정 인원을 유지한다. 공병 사망 사례는 직접 사망을 강제한다. 이 조건은 최소 이동·돌파·진입의 비교이며 실제 피해·회피·동적 교전 성능을 증명하지 않는다. R3 이후 대표 전투 조건으로 다시 검증한다.
