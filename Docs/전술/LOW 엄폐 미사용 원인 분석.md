# LOW 엄폐 미사용 원인 분석 — 2026-10-13

기준 커밋 `790959f8`. 사용자는 LOW가 엄폐로 움직이지 않고 현재 자리에서 교전하며, Inspect의 `shelter/search/relocation` 세 값이 없다고 보고했다. 이번 작업은 원인 조사이며 전술 실행 코드는 변경하지 않았다.

## 우선 원인 재정리: 대형 도착 후 고정 경계 작업

후속 사용자 관찰은 **HIGH/LOW 모두 대형을 만들고 도착한 뒤 현재 자리에서 사격만 한다**는 것이다. 대형이 이미 만들어진 장면을 시작 조건만으로 설명한 앞선 우선순위는 적절하지 않다. 이번 증상의 주 검토 대상은 개인 자리 배정 이후의 작업 소유권과 교전 실행이다.

HIGH의 `AdvanceFieldResponse`는 `AssignFieldPost`로 각 폰의 개인 칸을 선택한 뒤 `HD_NewTacticalContactGuard`를 발행한다. 해당 작업의 `MakeNewToils`는 지정 칸으로 이동한 뒤 `Hold`를 수행하며, `Hold`는 `ToilCompleteMode.Never`다. `TickGuard`는 방향·시야·사격을 직접 처리하지만 주변 엄폐 위치를 찾는 기능이 없다. 컨트롤러도 같은 경계 작업이 진행 중이면 목표 적 좌표만 갱신하고 유지한다. 따라서 도착 이후 바닐라 `JobGiver_AIFightEnemies`의 위치 선택으로 넘어가지 않는다.

처음 자리 선택에는 엄폐 점수가 들어가지만, HIGH의 후보 구역은 화력점 주변 최대 7×7칸·49칸이다. 후보 중 사격 가능한 위치를 우선하고 엄폐는 선택 점수의 일부로 사용한다. 구역 밖의 좋은 엄폐는 후보가 아니며, 정지한 뒤 더 좋은 엄폐를 탐색하는 판단도 없다. 따라서 **처음 선택한 노출 위치에 계속 서서 사격하는 행동은 현재 실행 구조에서 가능한 정상 분기**다.

LOW의 정상 본대 `AdvanceLowField`는 이미 바닐라 `Goto/Wait_Combat/AttackMelee`를 사용하므로 모든 LOW가 HIGH와 똑같은 고정 개인 자리를 쓰는 것은 아니다. 그러나 LOW도 **일반 접촉 대응(`RespondToContacts`)과 임시 우회조 합류**에서는 같은 고정 `HD_NewTacticalContactGuard`를 사용한다. 접촉 대응 컨트롤러 역시 이 작업이 남아 있으면 적 좌표만 갱신한다. 이 경로는 `FieldResponse` 없이도 대형처럼 보이는 개인 배치를 만들 수 있으므로, 사용자의 대형 도착 관찰과 세 준비 값이 없다는 보고가 함께 성립할 수 있다. 해당 플레이 장면의 실제 작업 이름은 아직 직접 확인하지 않았다.

공통 수정 방향은 **조직 AI는 분대/화력조 지향점과 활동 구역을 제공하고, 도착한 개인에게는 구역 안의 바닐라 엄폐·사격 위치·이동 판단을 넘기는 것**이다. HIGH의 화력점 간격과 중앙 후퇴는 그룹 지향점 변경으로 유지한다. 엄폐로 조금 이동해도 정확한 개인 칸으로 복귀시키지 않는다. 야전의 고정 경계만 교체하고, CQB 스택업/관측/수류탄·C4 안전 대기 등 고정 위치가 필요한 작업을 함께 바꾸지 않는다. 기존 전역 작업/경로/계획 예산과 낮은 개인 판단 빈도는 유지한다.

## 별도 결함: LOW 엄폐 준비의 시작 조건

`AdvanceFieldResponse`는 LOW/HIGH를 구분하기 전에 모든 관측 적에게 `TacticalFieldPolicy.FormationAllowed`를 적용한다. 플레이어 적은 **55칸 이내·관측상 접근 중**이어야 통과한다. 제자리에서 사격하거나 첫 관측만 있는 플레이어는 거부한다. 이 조건은 HIGH 화력점 형성의 제한이지만 현재 LOW의 엄폐 준비도 함께 막는다.

`FieldResponse`가 생성되지 않으면 `AdvanceLowField → AdvanceLowDefense`가 호출되지 않아 공유 엄폐 탐색과 엄폐 이동이 전부 실행되지 않는다. 기존 접촉 경계/공격/바닐라 실행 경로가 계속될 수 있다. 개발자 표시의 해당 값들은 `FieldResponse?.…`를 읽으므로 객체가 없으면 비어 있다. 사용자 보고와 맞지만, 이번에 살아 있는 분대의 객체를 직접 읽지는 않았으므로 특정 장면의 유일한 원인까지 확정한 것은 아니다.

배포 DLL 수정 시각은 UTC 14:55:40, 현재 게임 시작 시각은 UTC 15:07:54로 게임이 배포 후 재시작된 것은 확인했다. 최신 로그에서 LOW 방어 준비 관련 예외는 발견하지 않았다.

현재 DLL의 실제 `FormationAllowed`를 별도 콘솔에서 호출한 결과:

| 관측 조건 | 야전 시작 허용 |
| --- | --- |
| 정지한 플레이어, 40칸 | false |
| 정지한 AI, 40칸 | true |
| 정지한 플레이어, 80칸 | false |
| 정지한 AI, 80칸 | true |

두 관측 모두 같은 위치인 유효한 최신 기억을 사용했다. LOW/HIGH별 분기 없이 공통 함수를 호출하는 구조가 문제다. 기존 `ContactResponse`가 이미 있으면 같은 함수의 시작부에서 즉시 반환하는 제한도 있어, 플레이어가 나중에 접근하더라도 살아 있는 기존 접촉 대응에서 LOW 준비로 넘겨지지 않을 수 있다.

## 별도 결함: 실제 보호 효과 없는 엄폐도 현재 엄폐로 판정

`LowCoverAt`은 적 방향과 인접 방향의 내적이 0 이상이고 인접 물체의 `fillPercent >= 0.2`이면 true다. `LowNeedsShelter`는 이 결과가 true이면 이동을 생략한다. 하지만 설치된 게임의 `CoverUtility.TryFindAdjustedCoverInCell`은 적 방향과 엄폐 방향의 각도를 검사한다. 각도가 65도 이상이면 보호 효과가 없으며, 대각선 인접 엄폐의 각도에는 1.75를 곱한다. 열린 문의 실제 차단도 0이다.

적이 정북쪽이고 fillPercent 0.3인 물체 하나만 있을 때, 유효한 바닥을 가정한 인접 판정 비교:

| 물체 위치 | 현재 LOW 판정 | 바닐라 각도 규칙상 차단 |
| --- | --- | ---: |
| 바로 북쪽 | 엄폐 중 | 0.3 |
| 바로 동쪽 | 엄폐 중 | 0 |
| 북동쪽 | 엄폐 중 | 0 |
| 바로 남쪽 | 엄폐 아님 | 0 |

이 표는 LOW의 인접 조건과 역컴파일한 바닐라 각도 수식을 비교한 격리 계산이다. Unity의 네이티브 `AngleFlat` 호출은 별도 CLR에서 실행할 수 없으므로 실제 게임 사격 재생/바닐라 함수 전체 실행 결과라고 해석하지 않는다. 또한 현재 판정은 최초 대형 방향 `Forward`를 사용해, 적이 옆으로 이동한 뒤의 실제 사격 방향과도 달라질 수 있다.

## 추가로 제자리 교전에 돌아가는 경로

공유 목록 중 폰당 최대 24칸을 확인해 가장 가까운 후보 하나만 고른 뒤 도달성을 검사한다. 그 후보가 도달 불가하면 다른 후보는 시도하지 않고 바닐라 교전으로 돌아간다. 바닐라 교전은 현재 자리에서 사격 가능하고 보호 효과가 1%를 넘으면 더 좋은 엄폐 위치를 검색하지 않는 조기 대기가 있다. 따라서 LOW 준비가 정상 시작된 상황에서도 약한 엄폐/후보 실패로 현 위치 대기가 유지될 수 있다.

## 수정 순서

1. HIGH의 야전 개인 고정 자리/무기한 경계를 그룹 지향점·활동 구역 안의 개인 교전으로 바꾼다. LOW에도 일반 야외 접촉 대응에서 구역 기반 교전으로 넘길 경로를 만든다.
2. LOW의 우회 합류 같은 이동 준비와 실제 교전을 구분한다. 합류가 끝나면 고정 경계를 계속 유지하지 않는다. CQB 관측/투척·진입/C4·직접 근접 위급 대응은 각 제어권을 유지한다.
3. 현재 엄폐 충족 판정은 적의 관측 위치에 대한 실제 차단 방향과 최소 효과를 사용한다. 넓은 50칸 후보 검색은 근사 평가를 유지하고 개인 판단의 소수 후보만 정밀 확인한다.
4. 가까운 후보 하나가 불가능해도 제한된 다음 후보를 시도하고, 이동하지 않은 이유를 개발자 표시로 구분한다. 별도 시작 조건 결함은 LOW와 HIGH의 준비 정책을 분리해 처리한다.

대형이 이미 만들어진 뒤 움직이지 않는 이번 관찰에는 첫 번째와 두 번째를 우선 적용한다. 시작 조건 결함은 대형/야전 준비 자체가 시작하지 않는 별도 사례의 문제다. 현재 실행 코드와 DLL은 그대로 유지했다.
