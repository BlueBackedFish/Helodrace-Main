# R2 틱 스파이크 원인 분석

2026-10-08. 기존 R2 원본 24회를 재검토하고, 같은 DLL로 204명/17분대의 닫힌 외벽 사례를 **1회만** 추가 실행했다. 준비 1,200틱 이후 1,200틱을 수집했다. 게임 동작·수집기 코드는 변경하지 않았다.

**새 전술 판단의 가장 뚜렷한 병목은 분대 완료 시 작업을 일괄 종료하면서 바닐라의 다음 행동 검색까지 동기적으로 실행하는 부분이다.** 전체 틱의 더 큰 지연은 폰·사물 처리에서도 발생한다. 두 문제를 구분해야 한다.

## 짧은 측정 결과

이 짧은 창은 완료 시험이 아니다. 종료 시 6/17분대 완료, 개구부 통과 80명, 작업 실패/재시도 5회였다. 아직 계획이 없는 대기 분대가 있어 `newFunctionalComplete`와 전 분대 물리 계획 검사도 false로 남았다. 이 상태를 완료 합격으로 바꾸거나 R2 최종 결과에 합치지 않았다.

## 1. 분대 완료 시 12명의 다음 행동 검색이 한 판단에 몰린다

[Advance](../../Source/Helodrace/Tactics/TacticalCommands.cs)는 전원이 진입하면 `Complete`로 전환하고 자리 사용권을 해제한 다음 `foreach (member in active) EndOwned(member)`를 실행한다. LOW 분대는 12명, HIGH는 13명이므로 작업 종료가 한 번에 몰린다.

`EndOwned`는 `pawn.jobs.EndCurrentJob(InterruptForced)`를 호출한다. 로컬 바닐라 DLL의 메서드 서명을 확인하면 생략된 인자 `startNewJob`의 기본값은 **true**다. 바닐라 IL에서도 작업 정리 이후 `TryFindAndStartJob` 또는 다른 `StartJob`으로 이어지는 경로를 확인했다. 단순한 소유권 해제가 아니라 생각 트리 평가와 다음 작업 선택·시작이 현재 메인 호출 안에서 일어날 수 있다.

이번 창에서 `EndOwned` 48회의 누적 39.08ms는 `Advance` 46.17ms의 **84.65%**였다. `EndOwned` 자체의 추적 self는 0.055ms뿐이므로 비용은 바닐라 작업 종료 쪽에 있다. `Advance`의 나머지 추적 self는 4.665ms이고, 새 Job 발행은 2.206ms, 자리 해제는 0.213ms였다. 국소 계획 `Find`는 이 준비 후 창에서 호출되지 않았다. 따라서 이번 새 지휘 스파이크를 새 스택 후보 탐색만의 문제로 설명할 수 없다.

전체 스케줄러는 한 틱에 최대 2개 분대를 판단하고 **Advance가 반환한 뒤** 1.5ms 예산을 검사한다. 한 분대의 12명 해제만 21ms 수준의 판단을 만들면 이미 예산을 넘긴 뒤다. 인원이 늘면 분대 완료·진입 전환·재시도의 횟수가 늘지만 제한은 여전히 분대 단위라 폰별 비싼 호출 수를 직접 제한하지 못한다.

**추천 1순위:** 완료 상태 전환과 실제 폰 Job 해제를 분리하고, 여러 틱에 걸쳐 소수 인원씩 바닐라로 반환한다. 전역적으로 해제·새 Job 발행 수를 제한하고 마지막 멤버까지 처리될 때까지 필요한 작업 소유권과 입구/자리 안전을 유지한다. `startNewJob:false`만 일괄 적용하면 다음 폰 틱에 같은 다음 행동 검색이 다시 몰릴 수 있으므로 그것만으로 해결했다고 보지 않는다. 한 번의 바닐라 검색 자체가 길면 분산만으로 그 단일 호출의 상한까지 제거되지는 않는다.

## 2. 전체 틱의 큰 지연은 일반 폰·사물 처리에도 있다

이번 전체 틱 최대는 38.204ms, `TickList.Tick` 최대는 37.582ms였다. TickList 누적 5,779.45ms는 전체 틱 누적 경과의 약 86.46%다. 바닐라 IL에서 TickList가 `Thing.DoTick` 등을 실행하는 것을 확인했다. 여기에는 전술 Job을 수행하는 폰과 이미 바닐라로 반환된 폰, 다른 사물의 처리가 포함된다. 이 수치는 순수 바닐라 전투 AI만의 시간이 아니다.

`TryFindAndStartJob`에는 18.433ms의 단일 호출도 있었다. 이 최대는 `EndOwned` 한 호출의 최대 3.068ms보다 크므로 위 분대 반환 경로만이 전부는 아니다. 일반 폰 틱에서의 작업 종료·선택이나 다른 호출 주체도 비용을 만든다. 현재 자료로 특정 폰의 엄폐/적 탐색/작업 선택 중 어느 내부 계산이 원인인지까지는 확정하지 못했다.

기존 204명 원본에서도 New 전체 틱 최대는 일반 접근 152.534ms/공병 99.774ms, Vanilla는 각각 198.081ms/90.547ms였다. 새 엔진을 꺼도 긴 틱이 있어, 사용자 플레이의 모든 스파이크를 새 지휘 서비스 하나로 귀속할 수 없다.

**추천 2순위:** 우선 새 엔진이 동시에 많은 폰의 다음 행동 검색·이동을 유발하는 부분을 줄인다. 이후에도 남는 큰 지연은 `TickList.Tick → Pawn/JobTracker → TryFindAndStartJob/DetermineNextJob`의 소수 경계를 선택해 짧게 확인한다. 이번 단계에서는 모든 폰의 고빈도 메서드를 추가 패치하지 않았다.

## 3. 초기 호출과 실제 길찾기 처리도 별도 후보다

기존 준비 0틱 자료의 전술 `Find`는 호출 최대 약 4.3~6.1ms이며, 단 한 번의 최대 호출이 각 실행의 누적 Find 비용 상당 부분을 차지한다. 초기 JIT·첫 도달 가능성 검사·초기 상태 구축이 후보지만, 기록에 호출 틱이 없어 어느 것이 원인인지 확정하지 않는다. 준비 후 이번 창의 Find 호출 0회를 근거로 첫 계획 문제가 해결됐다고 주장하지 않는다.

기존 `MapPreTick`에도 약 28~55ms의 최대가 있었다. 로컬 바닐라 IL에서 `MapPreTick → PathFinderTick → ForceCompleteScheduledJobs → JobHandle.CompleteAll`을 확인했다. 경로 요청의 실제 예약·처리·완료 대기는 `CreateRequest`와 별개이므로, 요청 생성 메서드가 저렴하다고 실제 길찾기 부하까지 배제해서는 안 된다. 다만 과거 MapPreTick 최대가 이 대기 때문이었는지는 아직 미측정이다. 이번 준비 후 MapPreTick 최대는 0.896ms여서 이 창의 주요 스파이크는 아니었다.

**추천 3순위:** 폰별 이동 시작/전환도 작은 배치로 분산해 경로 요청의 몰림을 줄인다. 필요할 때만 `PathFinderTick/ForceCompleteScheduledJobs`를 추가 선택한다. 이미 바닐라 길찾기가 Unity 작업을 예약하고 완료를 기다리는 구조이므로, 전술 계산을 워커로 옮기기만 하면 이 대기나 바닐라 생각 트리 비용도 사라진다고 보지 않는다.

## 낮은 우선순위와 분석 한계

- 이번 창의 자리 해제 최대는 0.055ms, 조직 Tick 최대는 0.195ms다. 조직 전체를 15틱마다 재평가하고 등록 누락을 300틱마다 한꺼번에 확인하는 구조는 분산 후보지만, 이번 21ms 판단보다 먼저 고칠 근거는 없다.
- 방/지역 갱신 검사 871,412회 중 단일 최대는 0.015ms였다. 이 짧은 창에서 큰 방 재구축 스파이크는 확인되지 않았다. 고빈도 검사 자체를 계측한 오버헤드는 부모 구간에 들어가므로 이번 상세 진단 수치를 정식 CPU 합격 수치와 섞지 않는다.
- 기존 수집기의 느린 호출 기록은 메서드 ID와 시간만 가지며 틱·시작 시각·폰·분대·단계가 없다. 각각의 최대가 같은 틱인지 알 수 없으며 최대값을 더하거나 빼서 특정 틱의 비용을 계산하지 않는다. 코드 호출 관계와 누적 자식 비용으로 분대 반환 병목을 확인한 것이지, 모든 긴 틱의 정확한 호출 트레이스를 얻은 것은 아니다.
- GC, OS 스케줄링/대기, 렌더링 영향은 배제하지 못했다. MapUpdate의 긴 호출은 프레임 비용이며 전체 틱 최대와 합산하지 않는다. 메모리 누수 조사나 새 워커 구조 구현은 이번 범위가 아니다.

결론적으로 **분대 단위 예산 안에서 폰 12~13명의 비싼 전환을 동기 실행하는 구조**를 먼저 바꾸는 것이 새 전술 스파이크를 줄일 가장 직접적인 방법이다. 그 뒤에도 남는 일반 폰 처리·초기 경로 완료 대기를 좁혀 확인한다. 런타임 코드는 수정하지 않았으며 추가 게임 수집은 위 1회로 끝냈다.
