# 대기 분대 실행과 관측 재검증 최적화 결과

2026-10-07. 1순위 명령 조회 캐시 이후, 대기 실행과 관측의 반복 비용을 줄였다. **LOW 400명에서 RunScheduledUnit의 틱당 경과 비용은 Core 기준 68.72%, 개구부 대기 처리는 92.14% 감소했다. 전체 게임 틱 CPU 감소는 이번 시험으로 확인하지 못했다.**

## 적용 내용

기존에는 ReviewAfter를 늘려도 실행 티켓 자체는 10틱마다 재등록됐다. 다음 실행 시각을 실제 상태에 따라 바꿨다. 바닐라 이동·사격·작업 Job은 판단 사이에도 계속 실행된다.

| 상태 | 실제 실행 간격 상한 | 전체 검토 간격 |
|---|---:|---:|
| 조용한 개구부 대기 | 180틱 | 300틱 |
| Hold / Complete / 실행 상태 없음 | 180틱 | 180틱 |
| 접근 중 Assemble | 60틱 | 60틱 |
| 일반 돌파·관측·투척·실내 단계 | 30틱 | 30틱 |
| CrossBreach / 진행 중 반응·회피·연막·지원 수비 | 10틱 | 30틱 |

실행 예약은 전체 검토 시각을 넘기지 않는다. 새 연락 보고와 지원 요청은 해당 분대를 다음 틱에 예약하고 반복 이벤트는 하나로 합친다. 개구부 사용권 해제·소유 분대 제거는 대기 티켓들을 깨운다. 이는 현재 맵의 대기 분대를 대상으로 하는 드문 로컬 이벤트이며, 해당 진입점만 찾는 인덱스까지 추가하지 않았다. 사상자 알림은 기존 즉시 재평가 경로를 유지했다. 이벤트가 누락되어도 주기적 확인으로 복구한다.

개구부 입장 재검증과 사용권 정리는 30→180틱으로 낮췄다. 같은 개구부 대기 명령의 소유자와 최종 목적지가 유지되면 Set을 재발행하지 않는다. 새로운 자리나 다른 반응 명령에서 복귀할 때는 다시 발행한다.

관측은 다음과 같이 변경했다.

- 조용한 대기 관측은 90→180틱, 일반 관측은 20→60틱.
- 후보 상한 32→16명, 관측자 상한 4→2명, 분대 LOS 예산 상한 32회. 지휘자·명시적 개구부 관측자를 먼저 선택하고 나머지는 순환한다.
- 맵별 물리 폰 인덱스는 10→60틱 재사용하며 이동 여유 16→32칸. 폰 수 변경·틱 역행 시 재생성하고, 소실된 폰은 조회 시 제외한다.
- 알려진 적은 공유 ID 인덱스로 조회한다. 매번 전체 맵 폰 목록을 돌며 접촉 ID 사전을 만드는 작업을 없앴다.
- 분대별로 시야 검증을 마친 적 목록을 최대 60틱 재사용한다. 접촉 revision과 이벤트 깨우기는 이를 무효화한다. 사망·다운·디스폰·무기 소실은 재사용 중에도 검사한다.
- 관측 LOS는 같은 시작/끝 칸의 결과를 최대 60틱 재사용한다. 8192개로 제한하고 틱 역행 시 해당 결과를 다시 계산한다. 문 변경 때 전체 LOS 사전을 즉시 지우지 않는다. 물리 구조 revision과 이동용 청크 무효화는 계속 수행한다.

공유 물리 인덱스는 적 지식이 아니다. 새로운 접촉은 관측을 거쳐야 하며, LOW의 개인 기억과 분대 연락 조건은 유지한다. 보고된 적도 최초 목록 구성 시 분대 내 연결된 관측자의 시야 검증을 요구한다. 재사용 기간에는 시야·연막·숨은 적의 반응 판단이 오래된 결과를 사용할 수 있다. 실제 총격은 바닐라 사격 Job이 검증한다. 작업 스레드·통신 전체 프레임 구조·이동 비용 구조는 이번에 변경하지 않았다.

## 좁은 범위 성능 검증

[원본과 CSV](../../Source/Benchmarks/AgentProfiler/Results/2026-10-07-execution-observation/README.md). 기존 프로파일러 coarse 기본 맥락에 다음 **관련 4개 메서드만 추가**했다.

`RunScheduledUnit`, `RefreshContactsCore`, `VisibleArmedEnemies`, `WaitForSharedOpeningCore`.

조건은 LOW 200→400→0명, 동일 seed `hd-perf-20261007`, 지형 SHA `2DCA10EF6A532BA820CA2CFA41B18D21E564655193AC63E429759ED9D0135787`, 준비 600틱, 요청 측정 900틱, 속도 3이다. 프레임 경계로 실제 capture 틱 수는 900~904틱이며 CSV는 capture의 실제 틱 수로 나눈다. 최종 빌드 SHA는 `ef47fca080cb8b9b0bb36c804d8e70dedbe9ed2ac55ac79c6c308adff5b875f5`이다.

Core 100%는 `Verse.GenRadial.NumCellsInRadius(float)` 10,000회 배치의 각 capture 중앙값이다. 400명 기준 배치 시간은 전 0.2765ms, 후 0.2761ms로 비슷하다. 아래 관련 메서드는 **경과 시간**이며 실제 CPU 계측은 DoSingleTick에만 사용했다.

| 400명 메서드 | 호출 수 전→후 | ms/tick 전→후 | Core %/tick 전→후 | Core 기준 감소 |
|---|---:|---:|---:|---:|
| RunScheduledUnit | 3329→247 | 0.50946→0.15911 | 184.25→57.63% | 68.72% |
| RefreshContactsCore | 3329→247 | 0.20063→0.11275 | 72.56→40.84% | 43.72% |
| VisibleArmedEnemies | 1137→258 | 0.00212→0.00049 | 0.77→0.18% | 76.87% |
| WaitForSharedOpeningCore | 1080→247 | 0.18959→0.01488 | 68.57→5.39% | 92.14% |

RunScheduledUnit 안에 관측·대기 호출이 포함되므로 위 값을 더하면 중복이다. 이 부모 기준 약 **0.350ms/tick**을 줄였다. 호출당 비용은 실행 138→580µs, 관측 54→411µs로 증가했다. 빈 체크를 생략한 효과가 크며, 남은 비싼 스캔을 더 빠르게 만든 결과로 해석하면 안 된다. 최대 호출도 실행 4.325→15.987ms, 관측 1.300→15.887ms로 증가했다. 대기 처리는 평균 159→54µs, 최대 4.246→1.770ms로 줄었다. 평균 비용은 좋아졌지만 **한 번의 관측 스캔에서 발생하는 긴 지연은 해결하지 않았다.** 현재 전역 2ms 실행 예산은 이미 시작한 한 메서드를 중단하지 못한다.

400명은 시작 단계가 양쪽 Assemble:37로 같고, 종료는 전 Assemble:36/Breach:1, 후 Assemble:36/EntryWait:1로 다르다. 전후 성공 계획은 37개, 생존은 모두 400명, 이동 기록은 400→399명이다. 후측 미시작 이동 명령은 0건이다. 200명은 시작 단계가 달라 CLI의 정상 짝 비교에서 제외했다. 숫자는 원본·CSV에 보존했지만 개선율 근거로 사용하지 않았다.

전체 DoSingleTick의 실제 CPU는 400명에서 **13.050→14.740ms/tick**, 종료 후 0명에서 1.282→1.892ms/tick으로 높아졌다. 전체 경과 시간도 13.102→14.941ms/tick이다. 이를 외부 환경 때문이라고 단정하거나 패치로 전체 성능이 개선됐다고 주장하지 않는다. 전술 진행·바닐라 작업의 차이와 계측하지 않은 구간이 남아 있으므로 이번 확정 범위는 관련 메서드 호출 감소와 틱당 경과 비용 감소다. Core 보정도 변경된 작업량을 보정하지 못한다.

전후 6개 capture 모두 complete=true, dropped=0, 계측 메서드 예외=0이며 전체 감사도 완료했다. 0명에서는 실행 pending=0, 관련 4개 메서드 호출=0으로 유지된다. 이번 fixture에는 다수의 무장 적이 없어, ID 조회와 적 목록 재사용의 실전 다적 교전 절감률은 확정하지 못했다.

## 기능 검증과 제한

- 빌드 오류·경고 0, 기존 RaidTacticalBindings 전체 검증 통과. 실제 스케줄러 테스트 16개, 새 관측 캐시 테스트 11개를 포함한다.
- TacticalGeometry 검증 1249개 통과.
- 비계측 이동 기능 비교: 변경 전 DLL은 7단계 통과, 최종 DLL 재시험도 7단계 통과. 열린 문·새 구멍·숨은 문 변화·늦은 Security 합류·HC 연막·외벽 개구부·자리 중복 처리를 검사한다.
- **최종 DLL 최초 기능 시험은 1단계 1800틱 제한으로 실패했다.** 한 폰은 `(117,115)`에서 Job·명령·assignment가 사라졌고 나머지는 지정 자리에 도착했다. 변경 전 비교와 최종 재시험에서는 재현하지 못했다. 이전 조사에도 별개의 1단계 실패 기록이 있지만, 이번 실패를 같은 원인이나 최적화와 무관한 문제라고 확정하지 않는다. 실패 원본을 그대로 보관했다.

다음 비용 개선에서는 통신 전체 프레임 갱신을 우선 검토하되, 관측 한 번의 큰 지연에는 스캔 후보 처리의 틱 분할·스냅샷 계산 이전이 추가로 필요하다. 이번 단계는 완료했으며 전체 틱 CPU 개선과 단발성 기능 실패 원인 확인은 후속 과제로 남는다.
