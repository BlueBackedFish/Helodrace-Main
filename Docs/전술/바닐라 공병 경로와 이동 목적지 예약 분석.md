# 바닐라 공병 경로와 이동 목적지 예약 분석

2026-10-04. 설치된 Assembly-CSharp.dll의 JobGiver_AISapper를 직접 역컴파일해 확인하고, 기존 로컬 역컴파일 자료의 LordToil_AssaultColonySappers, LordToil_AssaultColonyBreaching, BreachingGrid, JobDriver_Goto, PawnDestinationReservationManager와 비교했다.

## 이번 한 명씩 이동하는 현상의 코드상 원인

RaidNodeMovement.FollowNodes는 모든 폰에게 GuidanceCells를 중심까지의 거리순으로 정렬해 첫 칸을 선택했다. 개인 자리 점유 조건을 없앤 이전 수정으로 대부분이 같은 중심 칸을 목적지로 받았다.

MapComponent_RaidTacticalOrders.Move는 CanReserve가 false이면 Wait_Combat와 120틱 재시도를 반환한다. JobDriver_Goto는 시작할 때 목적지를 예약한다. 따라서 먼저 작업을 시작한 폰이 중심을 예약하고, 뒤의 폰들은 다른 후보가 있어도 기다렸다. 실제 테스트 로그를 받지 않았으므로 관측된 모든 정체의 단일 원인으로 단정하지는 않지만, 현재 코드에 확실히 존재하는 직렬화 경로다.

## 바닐라 공병(Sapper)

- LordToil_AssaultColonySappers는 공통 sapperDest를 생성하고 적합한 공병들에게 Sapper duty와 그 목표를 준다.
- 나머지는 공병 한 명을 대상으로 Escort duty를 받는다. 원거리 호위 반경은 15~19칸, 근접 호위는 23~26칸이다.
- JobGiver_AISapper는 자신의 현재 위치에서 공통 목표까지 PassAllDestroyableThings 경로를 계산한다. 첫 막는 건물을 찾아 DigUtility.PassBlockerJob으로 처리한다. 막는 건물이 없으면 Goto를 준다.
- 목표 가까이 도달한 판정은 10칸 이내, 같은 방, NoPassClosedDoors 지역 연결을 함께 확인한다.
- 코드에 시간이 지나면 개별 경로를 공통 선으로 전환시키는 별도 단계는 없다. 출발점이 다른 폰이 같은 목적지로 향하고, 호위가 공병을 따라가고, 파괴된 통로를 이후 경로가 활용하면서 경로가 모이는 결과로 해석할 수 있다.

## 별도 브리처(Breaching) 습격

LordToil_AssaultColonyBreaching은 공통 breachStart/breachDest와 BreachingGrid를 만든다. CreateBreachPath는 파괴 가능한 건물을 포함하는 경로를 계산하고, 그 경로를 breachGrid와 walkGrid에 표시한다. 이후 breachRadius만큼 돌파 구역을, 추가 walkMargin만큼 이동 구역을 넓힌다. 즉, 공통 경로는 폭이 있는 구역이다.

벽·문 파괴 비용과 HP 비용, 자연벽 추가 비용, 위험 방 및 Perlin 비용도 사용한다. 이번 시스템에서는 바닐라의 위험 방 평가를 그대로 도입하지 않는다. 확인하지 않은 적과 열린 문을 미리 알고 움직이는 문제를 피하기 위해 기존 관측·진입 제약을 유지한다.

## 이번 적용

- 분대의 지향점과 필수 문·개구부는 공유한다.
- 실제 Goto 목적지는 같은 지향점 후보 구역에서 선택한다.
- 실제 예약 불가능한 칸은 제외하고, 다른 인원의 예정 목적지에는 혼잡 비용을 준다. 현재 위치와의 거리도 약하게 반영한다.
- 예정 목적지는 독점 대기 조건이 아니다. 좁은 구역에서 모든 개인 자리가 확보될 때까지 분대를 멈추지 않는다.
- 작업 생성 직전에 예약이 바뀌면 같은 연결 구역의 대체 목적지를 선택하고 120틱 예약 충돌 대기를 해제한다.
- 비상 회피·최종 스택업에는 이 대체 선택을 적용하지 않는다. 최종 대형은 기존 지정 위치와 안전 검사를 유지한다.
- 이동 후보당 실제 도달성 검사는 최대 24회로 제한한다. 목적지가 유효한 동안 유지해 매 갱신마다 다시 흩어지지 않게 한다.
- 원래 선택한 문, 외벽 진입 제약, 수류탄 안전 대기는 유지한다.

공통 이동 띠를 경로 비용으로 선호하게 만드는 전체 구조 교체는 이번 수정에 포함하지 않았다. 현재는 바닐라가 각 폰 위치에서 임시 목적지까지 실제 경로를 계산하는 방식이다. 단순히 예약 검사를 제거하거나 모든 폰을 동일 타일로 밀어 넣는 방법은 적용하지 않았다.

## 확인할 게임 상황

넓은 야외에서 분대 전원이 함께 출발하는지, 좁은 문을 통과한 뒤 다시 여러 명이 동시에 이동하는지, 여러 분대가 같은 지향점 주변에서 예약을 충돌시키지 않는지 확인한다. 한 칸 통로 자체의 물리적인 줄서기는 가능하다. 자동 테스트는 예약된 중심의 대체 선택, 같은 갱신에서의 목적지 분산, 도달 불가능한 후보, 후보 검사 상한을 검증하며 Unity의 실제 이동 실행은 별도다.
