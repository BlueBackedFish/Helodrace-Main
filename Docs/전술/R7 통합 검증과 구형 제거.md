## 종료 정리 첫 단위

기존에는 `Released` 명령이 맵의 분대 사전과 소유 상태에 남고, 마지막 분대 종료 후 알려진 개구부도 남을 수 있었다. 이제 종료 반환을 마친 명령을 맵/전역 큐에서 제거하고 해당 송수신 메시지와 상호 연락 참조도 정리한다. 마지막 분대가 없어지면 자리/사용권/개구부와 자동 목표 캐시를 비운다. 맵 제거도 전역 큐에서 제거한다. 다른 Lord로 이동한 폰을 원래 명령의 활성 인원으로 취급하지 않는다.

## C4 물리 상태와 폭발 안전 복구

실제 시험에서 저장 시 벽은 살아 있었지만 첫 로드 후 `TargetWall.Spawned=False`, `Destroyed=True`, 개구부 `Walkable=True`로 바뀌었다. 원인은 C4가 `Item`인 상태로 벽 칸에 설치되는 정의였다. 설치된 게임의 `Map.FinalizeLoading`은 비건물을 먼저 생성하고 `GenSpawn.SpawnBuildingAsPossible`은 그 칸의 아이템을 벽이 지울 경우 벽을 생성하지 않고 환불한다. 이후 AI는 기폭 전에 열린 개구부로 해석했다.

설치된 C4를 `Ethereal`로 정의해 벽과 함께 로드되도록 고쳤다. 실제 게임의 Spawn 판정과 현재 XML을 사용하는 독립 회귀 검사에서 기존 Item/벽 충돌을 재현하고 새 정의는 양방향으로 서로 제거하지 않음을 확인했다. 별도 호환용 저장 처리는 추가하지 않았다.

폭발 후 본체는 사라지므로 본체 컴포넌트 참조만 복구하면 안전 대기에서 null 참조가 생긴다. 명령의 폭발 주체와 살아 있는 파편 참조를 본체와 별개로 저장한다. 로드 이후 실제 도화선·파편·해당 개구부의 폭발이 끝나고 안정 시간이 지날 때까지 대기한다. 저장 외에는 새 파편 수집이나 지도 검색을 추가하지 않는다.

- LOW 24명/두 분대: 17틱 음성 제안 1개, 154틱 상태 보고 포함 대기열 2개를 실제 저장/로드. 두 번 모두 메시지·합의·native Job 상태 일치, 정상 틱의 송수신 연결 통과. 분리 중 상태 보고 정지·실내 재접촉/식별·서로 다른 입구/담당 구역을 유지하고 4,804틱에 전원 임무 완료. 실제 전달 31건. [원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/reload-low-communication/audit.json).

## 실제 두 맵의 전역 예산과 맵 제거

`r7-multimap` fixture 28: 실제 별도 월드 타일에 두 번째 맵을 `MapGenerator.GenerateMap`으로 생성하고 각 맵에 완전한 LOW 12인 분대/실제 Assault Lord를 배치했다(총 24명). 동일 게임의 두 맵에서 실제 전술 Job을 각각 12회 발행한 뒤, 120틱에 `Current.Game.DeinitAndRemoveMap`으로 두 번째 맵을 정상 제거한다. 시험 코드가 직접 MapRemoved를 호출하거나 전술 사전을 비우지 않는다.

3,601개의 실제 틱 종료에서 공유 예산을 읽었다. 관측 최댓값은 Job 2/틱, 반환 1, 경로 3, 계획 1, 관측 1, 통신 1로 모든 전역 상한 이내였다. 두 맵이 함께 살아 있던 120틱 동안 서로 다른 맵의 분대 사이에 연락/협력 합의가 유입되지 않았다. 제거 직후 두 번째 맵의 명령/폰 소유/자리/사용권/개구부는 모두 0, 전역 스케줄은 첫 맵의 한 분대만 남았다. 첫 맵의 동일 계획 객체·native Job ID/작업 단계·남은 시간·확보 이력·자리/사용권/소유 개수는 제거 전후 일치했다. 이후 첫 맵의 전원 진입/반환 완료를 실제 1,711틱에 관측했고 일반 진행 집계는 1,714틱에 완료를 기록했다. 그 뒤 종료까지 제거된 맵의 소유/명령이 재생성되지 않았다.

[최종 원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/multimap/audit.json). 두 맵의 인원과 지도/장비 지문을 각각 저장하고 원본 pawn manifest도 분리했다. 첫 수집기는 기능 시험에 통과했으나 두 번째 맵 지문 항목과 개별 manifest 경로가 없었으므로 `multimap-attempt-01`에 초기 증거로 보존한다. 최종 수집기 실행에서 두 manifest의 SHA가 각 지문과 일치하는 것도 확인했다.

## 고정 수비 연결과 실제 저장·공격 전환

신규 엔진은 실제 `LordToil_DefendBase`와 `LordToil_DefendPoint`를 별도 수비 명령으로 등록한다. 적 접촉 전에는 바닐라 duty와 Job을 유지하고 새 대형 이동·방 탐색·돌파 계획을 만들지 않는다. 관측 이후 기존 제한 예산의 엄폐/활 모양 대응을 사용하되 수비 기준점에서 앞으로 진격하지 않는다. 적 소실 후 대응 Job을 전역 틱당 1개 반환 예산으로 종료해 기존 수비 duty로 복귀한다. 고정 수비에서도 안전 구간 TCCC/매딕가방 조건은 허용한다. 비적대 수비가 실제 공격 상태로 바뀔 때 명시 목표가 없으면 명령 소유권을 반납한다.

LOW 24명/두 분대, fixture 29에서 실제 `LordJob_DefendBase`와 `LordJob_DefendPoint`를 사용했다. 첫 360틱 바닐라 수비 유지/신규 Job 0, 먼 적을 실제 노출한 뒤 두 분대 대응, 실제 사격, 적을 물리적으로 숨긴 뒤 수비 복귀를 확인했다. 감지 당시 각 분대의 일부 인원은 자신의 무기 사거리 밖이었다. 모든 무기의 사거리 밖 감지라는 증거로 확대하지 않는다. 순수 수비 첫 시험은 1,099틱, 공격 전환 시험의 수비 복귀는 1,100틱이다. 전진 bound·CQB 계획은 수비 중 0. [수비 원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/defense-baseline/audit.json), [공격 전환 원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/defense-transition/audit.json).

최종 저장 시험에서는 410틱 실제 대응 Job이 실행 중인 상태와 1,100틱 수비 복귀 상태에서 `SaveGame`/`LoadGame`을 각각 실행했다. 두 번 모두 두 명령의 기준점·목표·단계·대응 대형·접촉 이력·native Job ID/Toil/남은 시간·실제 pawn 위치/duty 및 자리/사용권 개수가 일치했다. `r7Reloads=2`, `r7ReloadDefensePreserved=true`, `r7ReloadJobsBound=true`. 2,441틱에 첫 Lord의 바닐라 타이머 그래프가 공격으로 바뀌고 같은 분대 명령이 이름 있는 침대 임무를 진행했다. 4,055틱에 12명 진입 과제를 완료했고, 다른 분대는 기존 수비를 계속 유지했다. [저장 복구 원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/defense-reload/audit.json). 일반 `newFunctionalComplete=false`는 두 분대 모두 공격을 완료해야 하는 기존 집계이며 의도적으로 수비에 남는 분대가 있으므로 변경하지 않는다. 이 시험은 명시 수비/전환/복구 플래그와 실제 명령·Job 데이터로 판단한다.

첫 두 저장 시도는 수비/공격 전환은 완료했지만 저장·복구 횟수가 0이었다. 체크포인트 조건을 완화해도 재현되어 확인한 결과 `ApplyCase`의 수비 처리 조기 반환이 저장 검사보다 앞에 있었다. 저장 검사를 먼저 실행하도록 순서를 고쳤다. `defense-load-attempt-01`/`02` 원본은 미완료 복구 증거로 보존하며 성공 수에 포함하지 않는다. 모든 시험의 raw/hash와 외부 저장 파일 해시를 보존했다. 첫 수비/전환 원본과 최종 저장 시험은 다른 DLL이므로 동일 최종 코드 CPU 자료로 합산하지 않는다.

## 다분대 두 맵과 Returning 재계획의 실제 저장 복구 확장

두 맵 시험의 `Single()`/명령 수 1 제한을 제거했다. 실제 생성한 각 맵의 전체 명령 수를 확인하고, 제거 전 남는 모든 명령의 동일 객체·Plan·실제 Job/Toil·확보 이력과 전체 점유/소유 수를 기록해 실제 `DeinitAndRemoveMap` 직후 비교한다. 남은 모든 명령의 진입 배정 완료를 요구한다. 같은 맵의 연락은 허용하며 실제 맵 간 Channel 반환, 대기 메시지 양 끝, peer/합의 상대의 소속 맵을 검사한다. 이 반사/스냅샷 검사는 격리 기능 fixture에만 있고 일반 플레이의 갱신에는 추가되지 않는다.

`-RetainedReload`는 기존 CQB 네 체크포인트 중 두 번째를 실제 `BeginReturn(..., release:false, replan:true)` 경로로 전환해 저장한다. 확보 셀이나 작업·스케줄러 사전을 만들어 넣지 않는다. 네이티브 로드 직후 Returning/재계획 의도·같은 명령 ID·이력을 확인하고, 실제 반환 작업 이후 같은 이력의 Pending을 관측한 뒤 남은 수류탄/접촉 체크포인트와 전체 방 진행을 마쳐야 한다. 실제 두 번째 저장 파일도 압축 원문/SHA로 보존했다. 앞선 DLL `310ef5...`의 [첫 실제 시험](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/retained-return-load-01/provenance.json)은 4,269틱 전원 완료·세 방/네 저장 복구·위험 진입 0이었다.

최신 감사 DLL `4c9a76329188e8ccfc698c07441a5bc8112719fd023ab3efa9b5ed98ebd55fb9`의 선택 두 사례 큐를 통과했다. **맵당 48명/4분대, 합계 96명/8분대**가 실제 등록됐고 두 맵을 120틱 운영한 뒤 제거한 맵의 정리·남은 네 분대의 객체/작업/이력/계획 보존과 전원 진입을 확인했다. 남은 맵 진입 배정 완료 이벤트는 3,981틱, 전체 Complete 관측은 4,007틱이다. 전역 최대 Jobs 2/Returns 1/Paths 4/Plans 1/Observations 1/Communications 2로 각각 기존 한도를 지켰다. 실제 같은 맵 메시지 송신은 0이어서 다중 맵에서 연락 성공까지 검증했다고 주장하지 않는다. 작업 실패 27회, 위험 진입/예외 로그 0이다.

## 활동·완료·초기 생성 CPU 구간 수집

격리 실행기의 `-CpuWindows`는 CPU 계측을 켠 상태에서 이미 완료된 `DoSingleTick` 호출의 누적 CPU/경과/호출 수와 전체 메인·프로세스 CPU를 시작, 500틱 간격, 최초 검증된 임무 완료, 종료에 기록한다. 미완료 루트 호출 안에서는 값을 읽지 않는다. 다른 Update 경계가 열려 있어도 틱 루트가 닫혔으면 읽을 수 있다. schema 9의 `cpuCheckpoints`와 audit의 `r7CpuCheckpoints`는 같은 원본이며 비교기는 일치·단조 증가·실제 틱/호출 수·종료 합계를 검사한다. 활성/비활성 구간 수집을 같은 비교 그룹으로 섞지 않는다.

`-NoMethodProfile -CpuWindows`에서는 메인·프로세스 CPU만 기록하고 틱 호출 수/CPU/경과는 null이다. 메인 CPU를 틱 루트 CPU로 대신 표시하지 않는다. 최초 임무 완료는 전원 자리 배정·목표/대표 방 확보·식별/접촉 복귀 종료를 확인한 이정표다. 이후 고정 입력이나 협력 만료가 재활성화할 수 있고, 단계/활성 명령 수는 체크포인트의 표본이므로 연속적인 활동 추적이나 영구 유휴 판정으로 해석하지 않는다. 정상/고정 CQB/고정 야전 사례에만 허용하고 저장 복구·다중 맵과 혼합하지 않는다. 최대 128개로 제한하며 일반 플레이에는 이 수집을 켜지 않는다.

`r7ColdMainCpuMs/ProcessCpuMs/WallMs`는 fixture 초기화의 기하 정리·폰/장비 생성·조직 등록 비용이다. Unity/월드 시작과 프로파일러 초기화는 제외한다. 실제 플레이의 습격 생성 총비용이나 첫 호출 JIT 비용으로 표시하지 않는다. Core 대비 값은 경과 시간/Core 기준 배치 중앙값이며 OS CPU 점유율이 아니다. 부모/자식 경과 시간을 합산하지 않는다.

## 최종 CPU 수집 순서와 비계측 대조 준비

[Run-R7Performance.ps1](../../Source/Benchmarks/TacticalEngineAudit/Run-R7Performance.ps1)은 **같은 DLL/정의의 전체 44개 기능 회귀 성공**을 요구한 뒤 기존 반복 실행기로 수집한다. Preview는 게임/파일 생성 없이 계획만 반환한다. 실제 수집 전에 검증한 계획은 다음과 같다. 모든 수집은 정상 그래픽, 준비 0, CpuWindows를 사용한다. 샘플 창은 초기 생성과 별도이며 실제 첫 완료와 후속 구간을 함께 보고한다.

## 비계측 CPU 대조의 읽기 전용 비교

[Compare-R7Unprofiled.py](../../Source/Benchmarks/TacticalEngineAudit/Compare-R7Unprofiled.py)는 기존 `engine-compare`가 요구하는 메서드 capture가 없는 비계측 실행을 별도로 비교한다. Vanilla/New 폴더의 실제 audit/launcher/log에서 네 콘텐츠 SHA·지도/폰/장비·초기 입력·인원/편제·배속·게임/Unity/모드·800×600 정상 그래픽·준비/측정 창을 대조한다. 고정 CQB/야전의 실제 입력 시간표, 격리/환경/구형 제거·안전·실제 이동/진입·신규 완료를 확인한다. OS 메인/프로세스 CPU 누적값과 최종 합계가 일치해야 하고, 비계측 틱 루트 값은 null이어야 한다. 같은 native savedata 인자를 복사한 원본을 여러 반복으로 세지 않는다.

비교는 전체 메인 CPU/틱의 중앙값·범위와 같은 고정 offset의 누적 비용을 보고한다. 실제 틱 루트 CPU/메서드/Core 값은 제공하지 않으며, 단일 실행은 2배 이내라도 반복 대조 통과가 아니다. 고정·완료·종료 경계가 같은 실제 틱에 기록될 수 있으므로 누적값의 단조 증가와 전체 창을 검사한다. 초기 비용은 fixture 초기화로만 표시하고 Unity/월드 부팅 전체 비용으로 해석하지 않는다. 최종 수집 순서·현재 최종 기능 DLL과의 일치·실제 협력 발생·계측 틱 CPU 합격은 matrix journal 및 최종 감사에서 별도로 검사해야 한다.

기존 `899e...` 비계측 신규 한 회의 실제 원본을 읽어 OS 메인 15,375ms/4,000틱을 재확인했다. 잘못된 계측 플래그·가짜 틱 CPU·누적/합계 불일치·그래픽 불일치·진행 없음·야전 입력 누락·중복 native 식별자·혼합 DLL 거절과 1회/3회·2배 경계를 [12개 검사](../../Source/Benchmarks/TacticalEngineAudit/Tests/test_unprofiled_compare.py)로 확인했다. 산술 반복 자료는 명시적으로 합성한 검사 입력이며 실제 CPU 증거로 쓰지 않는다. 이 단위는 **비교기 검증**이고 최신 DLL의 새로운 비계측 N/V 실행이나 R7 CPU 합격이 아니다. 게임 DLL은 변경하지 않았으며 `e4e4...` 전체 44개 회귀는 같은 고정 DLL로 계속 진행한다.

## 최종 CPU 수집의 협력 실행 증거 범위

일반/고정 CPU fixture는 전용 협력 drill이 아니므로 `FinalCooperationDiagnostics`를 호출하지 않는다. 이때 `newMessagesSent/Delivered/AgreementsConfirmed/CooperationStarts=0`은 수집되지 않은 기본값이지 실제 통신/협력 0회라는 뜻이 아니다. 과거 408명 원본에도 합의 agenda·담당 구역·peer 상태 시각이 있었으나 이 카운터들은 0이었다. 최종 판정에서 이 기본값을 성공/실패 횟수로 쓰지 않는다.

[Run-R7Performance.ps1](../../Source/Benchmarks/TacticalEngineAudit/Run-R7Performance.ps1)은 기존 Job 발행·바닐라 경로 요청에 `TacticalCommunications.Send`, `Deliver`, `TacticalCooperationState.CanStart` 세 메서드를 추가 선택한다. 마지막 것은 실제 합의가 Active인 `CooperationReady` 경로에서 호출된다. 신규/바닐라 모두 같은 선택 목록을 쓰며 manifest와 성능 journal/Preview에 남긴다. 비계측 대조는 같은 인자를 기록하지만 메서드 계측을 켜지 않는다. 호출 수는 송수신 **시도**와 합의된 준비 판단의 실행 증거이지 전달 성공·동시 진입 완료 횟수가 아니다. 실제 협력 결과는 최종 agenda/담당 구역/peer 자료와 별도 44개 기능 회귀로 확인하며, 부족하면 해당 CPU 그룹을 협력 완료 증거라고 부르지 않는다.

PowerShell 5 문법과 실행 없는 Preview에서 다섯 추가 선택 대상·전체 24그룹/96회 유지·대표 그룹 세 번의 `Vanilla/New → New/Vanilla → Vanilla/New` 순서를 확인했다. 세 메서드의 실제 본문과 Active 조건은 현재 소스로 확인했으며, 최종 CPU 실행의 capabilities/capture에서 실제 등록·호출을 추가 확인해야 한다. 게임 DLL 해시는 `e4e4...` 그대로이며 현재 전체 기능 큐를 재시작하지 않았다. 이는 수집 구성 보완이고 새로운 CPU 측정/최종 합격은 아니다.

## 최신 DLL 전체 큐의 첫 10개 원본 보존

`hd-r7-final-functional-e4e4-05`의 첫 10개가 정상 그래픽·비계측·실제 3배속에서 통과했다. 해머 회수는 실제 1회/생존 11명 전원 완료 1,830틱, 작동 중 절단기 사망은 회수 1회·절단 재개/생존 11명 완료 1,656틱이다. 설치 전 C4 사망은 회수 완료 2회·설치/기폭·안전 대기 뒤 1,805틱 생존자 완료다. 도화선식 C4 설치 후 점화 전 사망은 실제 작업자 승계 1회/후속 점화·대기 45회·2,136틱 완료다. 점화 후 작업자 사망과 목표 변경은 대기 44회·2,257틱 생존 11명 완료다. `ChargeAction.Detonated`는 여기서 점화/기폭 요청 플래그이며, 도화선의 실제 폭발 완료 시각 자체가 아니다. 모든 사례 위험 진입·예외 로그 0이며 실제 작업 실패는 사례별 0~9회로 원본에 남긴다.

[최신 부분 원본](../../Source/Benchmarks/TacticalEngineAudit/Results/2026-10-09-r7/functional-e4e4-prefix-10/provenance.json)에 41파일의 raw/SHA/압축 전 해시와 전체 큐 journal 스냅샷을 보존했다. ## 후반 29~44번 진단 우선 실행

사용자 요청에 따라 앞부분을 다시 실행하기 전에 아직 전체 큐에서 확인하지 못한 후반 사례를 한 번에 수집한다. 게임 DLL `9050f5f934e58a6b4fc14ec4573bb77c20a56e677cdcd2179517e7eff2344a38`과 세 정의 파일은 변경하지 않았다. 기존 `hd-r7-final-functional-9050-07`의 1~18번은 실제 사례 규격과 원본으로 검증해 모두 통과했다. 큐 부모와 자동 성능 수집 대기만 중단하고, 실행 중이던 18번은 자연 종료까지 보존했다. 이 부분 결과를 전체 44개 통과로 취급하지 않는다.

[Run-R7Functional.ps1](../../Source/Benchmarks/TacticalEngineAudit/Run-R7Functional.ps1)의 `-ContinueOnFailure`는 자연 종료한 사례의 검증 실패를 기록하고 다음 사례로 진행한다. 기본 실행은 기존처럼 첫 실패에서 중단한다. 콘텐츠 변경, 실행 시작 실패, 잔존 게임 프로세스, 관측 기한 초과는 진단 모드에서도 큐를 중단한다. journal은 실패 목록·수집 완료·선택 항목 전체 통과를 각각 기록한다. 수집 완료와 전체 통과는 다르며, 이 모드는 CPU 또는 R7 완료 판정을 하지 않는다.

`hd-r7-diagnostic-tail-9050-02`에서 29번 치료 중단부터 44번 지원 저장/불러오기까지 정확히 16개를 선택해 실제 정상 그래픽·비계측 테스트를 시작했다. PowerShell 5에서 JSON 배열을 추가 `@(...)`로 감싼 선택 오류 때문에 별도 `...-01`에서 1번이 시작됐으나, 부모만 중단하고 게임은 보존했다. 그 실행은 후반 16개 진단 결과에서 제외한다. 올바른 선택은 Preview에서 전체 44개·후반 16개·첫/마지막 이름과 선택 목록 일치까지 확인했다.

[큐 제어 검사](../../Source/Benchmarks/TacticalEngineAudit/Tests/Test-R7FunctionalQueue.ps1)에서 기본 실패 중단, 진단 시 실패 후 계속 실행, 전부 통과한 부분 큐의 범위, 살아 있는 게임 보존, 실행 시작 실패 중단을 확인했다. 이 다섯 검사는 모의 큐 검사이며 게임 기능 통과 증거가 아니다. 후반 전체의 실패 목록을 모은 다음 수정 대상을 정하고, 수정 이후 최종 전체 회귀를 진행한다. 진단 부분 큐에서 자동 CPU 수집은 시작하지 않는다.
