# Security 이동 수정과 공유 돌파 지점 정지 분석

작성일: 2026-10-05. 2단계 이동 수정과 동일 개구부를 선택한 후속 조직의 정지 원인 조사 결과다. 조직 간 협력·진입 순서 조정은 아직 구현하지 않았다.

## 이번에 수정한 이동

### 개인별 접근 제한 통일

기존에는 실제 다음 칸 진입 허용 여부는 개인의 다음 연결을 사용했지만, 경로 비용은 분대 전체의 접근 완료 여부와 전체 `ApproachPath`를 사용했다. 먼저 마지막 연결을 지난 Security도 후행 인원이 접근을 끝낼 때까지 불필요한 문 비용을 받았다. 경로 탐색이 선택한 통로와 실제 이동이 허용하는 통로가 달라질 수도 있었다.

`RaidNodeMovement.ConnectionFor`로 개인의 다음 연결을 구한다. 경로 비용과 실제 칸 이동 판정이 같은 연결의 `AllowedRooms`·`AllowedPortals`를 사용한다. 개인이 마지막 연결을 통과했거나 접근 단계가 끝나면 해당 제한을 해제한다. 회피 때문에 경로 밖 방에 들어간 인원은 현재 방에서 나올 수 있지만, 다른 통로를 지름길로 사용할 수는 없다.

이 변경은 이동점을 밟고 멈추게 하는 새 이동 명령이 아니다. 기존 지향점으로 이동하면서 연결별 안전장치만 일치시킨다.

### 외벽 개구부의 후행 합류

개구부 통과 확인은 실제 폰 위치로 유지한다. 기존 외부 문을 통해 실내 목적지에 도착해도 선택한 개구부를 통과한 것으로 간주하지 않는다.

개구부 안쪽에서 연결된 실내 목표가 확인되면 첫 방에 별도 정지 칸을 확보하지 않고 그 목표로 이동할 수 있게 했다. 실제로 개구부와 바로 안쪽 칸을 벗어나면 임시 합류 상태를 끝내고 정상 명령을 계속한다. 첫 방이 한 칸뿐이면 안쪽 칸 도착으로 전환한다.

목표가 국소 연결 범위 밖이면 기존처럼 첫 방의 합류 칸을 찾는다. 이동 중인 다른 폰이 잠깐 지나가는 것 때문에 목적지를 매번 바꾸지 않으며, 계속 점유되는 목적지는 60틱 간격으로 다시 확인한다. 안전한 실내 목적지가 없으면 개구부 바로 앞에서 대기하는 대신 외부의 빈 대기 칸을 찾는다. 다른 조직의 활성 합류 목적지도 중복 배정 대상에서 제외한다.

### 국소 연결 캐시

| 항목 | 내용 |
| --- | --- |
| 기준 구조 | 습격에 고정된 정적 방 레이아웃 |
| 범위 | 개구부 안쪽 칸 기준 반경 14칸 |
| 형식 | 사방으로 연결되는 `HashSet<IntVec3>` |
| 실시간 확인 | 바닥 통행 가능 여부, 문이 열려 있거나 해당 폰이 열 수 있는지 |
| 새 내부 구멍 | 정적 벽 칸의 서로 반대편이 모두 실내이면 연결 가능 |
| 외부 문 차단 | 문 자체의 방 ID가 양수여도 양쪽이 실내인 통로만 인정 |
| 캐시 키 | 구조 버전, 개구부, 안쪽 칸, 폰 세력 |
| 재확인 | 같은 연결은 60틱마다, 최대 64개 캐시 항목 |
| 경로 비용 갱신 | 연결 집합이 실제로 바뀔 때만 새 연결 버전 사용 |
| 외부 대기 | 개구부 기준 반경 8칸, 바깥쪽의 빈 칸 중 최대 24개 도달 검사 |

연결 집합은 메인 스레드에서 읽어 고정하고, 경로 비용 계산에는 분리된 배열을 넘긴다. 작업 스레드가 실시간 `Map`이나 문을 읽지 않는다. 갱신 시간만 바뀌었다고 같은 내용의 전체 맵 비용 배열을 다시 만들지 않는다.

디버그 실행 보고서의 `ingress`에 `direct`, `waitingOutside`, `searchAfter`를 추가했다. 개인 접근 완료(`memberDone`)와 분대 접근 완료(`unitDone`)도 함께 확인할 수 있다.

## 같은 돌파 지점에서 후속 조직이 멈추는 원인

플레이 로그로 해당 장면을 재현한 결론은 아니며, 아래는 현재 코드에서 확인한 정지 경로다.

1. **같은 후보가 선택되기 쉽다.** `RaidTacticalPlanner.TryFindPlannedBreach`는 거리, 직선 이탈, 노출, 장비, 대형 수용 공간을 평가한다. 다른 조직이 이미 선택한 개구부를 배제하거나 공유 진입 순서를 정하는 항목이 없다. 같은 스폰 위치와 목표라면 같은 개구부가 선택될 가능성이 높다.
2. **후보 검증과 실제 자리 배정의 조건이 다르다.** 돌파 후보를 검증할 때는 빈 `occupied` 집합에서 해당 팀의 스택업이 가능한지 검사한다. 이후 실제 `Assign`은 `OtherFormationCells`로 다른 조직의 대형 예약과 다른 폰의 현재 위치까지 제외한다. 따라서 후보 검증은 성공해도 실제 돌입 인원의 `Position`은 `Invalid`가 될 수 있다. 벽 돌파에서는 이때 일반 집결 칸으로 대신 배정하지 않는다.
3. **선행팀이 진입해도 외부 경계 자리는 남는다.** `FormationAssignments`는 `CrossBreach` 단계의 Entry 예약을 제외하지만 Security·FireSupport 예약은 유지한다. 실제로 해당 칸에 남아 있는 폰도 점유 판정에 걸린다. 선행팀의 돌입 인원이 들어갔다고 대형 공간 전체가 즉시 비는 것은 아니다.
4. **후속팀은 전원 집결 조건에 묶인다.** `AllReady`는 관측 경계 등 일부 예외를 제외하고 지정 칸에 정확히 도착했으며 다른 폰과 겹치지 않은 상태를 요구한다. `Invalid` 자리나 다른 팀이 계속 점유하는 자리가 있으면 `Assemble → Breach`로 넘어가지 못한다.
5. **제한 시간이 지나도 같은 공간을 재시도한다.** 접근 완료 후 720틱이 지나면 `RetargetBlockedStackMembers`가 같은 `SafeStackCells`·`SafeSupportCells`에서 대체 칸을 찾는다. 후보 목록이 비어 있지 않으면 `PhaseStarted`를 갱신한다. 실제 빈 자리가 없으면 이전 배정을 유지하고 120틱 재시도 제한을 걸기 때문에 이 과정이 반복될 수 있다.
6. **이미 열린 벽의 처리까지 도달하지 못한다.** `BreachOpened`로 열린 개구부를 처리하는 주요 전환은 `Breach` 단계에 있다. 후속팀이 집결에서 막히면 선행팀이 벽을 열어도 이 전환에 도달하지 못한다.

이는 조직별 실행 상태가 분리되지 않아서 생긴 문제가 아니라, 물리적으로 공유하는 좁은 공간의 사용 순서가 없는 문제다. 타일 중복을 다시 허용하거나 전원 집결을 무조건 건너뛰면 기존 대형 충돌·폭발 전 진입 문제가 재발할 수 있다.

## 권장 후속 수정

개구부 좌표별로 실제 사용 팀과 대기 팀을 정하고, 후속팀은 같은 스택업 칸에 먼저 진입하지 않게 한다. 인접해서 선행팀이나 열린 개구부를 실제로 확인한 뒤 기존 통로를 재사용하도록 전환하는 방식이 적절하다. LOW의 미관측 정보나 적 기억을 자동 공유하는 기능과는 구분해야 한다.

돌파 후보 검증에도 다른 조직의 대형 예약을 반영하고, 실제 자리 배정 실패는 계획의 준비 실패로 처리한다. 일정 시간 빈 자리가 생기지 않으면 동일 목록 재시도 대신 외부 대기 유지 또는 다른 돌파 후보 선택을 해야 한다. 선행팀 경계 인원은 자신의 임무가 넘어갈 때 예약과 실제 위치를 함께 정리해야 한다.

이번 수정은 개인 접근 제한 불일치와 후행 인원의 첫 방 합류 칸 부족을 완화한다. 공유 스택업 공간 부족과 조직별 진입 순서는 별도 수정이 필요하다.

## 검증과 플레이 확인

- 빌드: 경고 0, 오류 0.
- 전술 기하 검사: 321개 통과. 다음 연결의 경로 비용과 실제 진입 허용 조건, 경로 밖 방 탈출, 실내 연결 범위 제한 포함.
- 게임 클래스 바인딩 검사: 전체 통과. 외벽 합류 상태·저장 46개와 개인 접근·국소 연결 10개 포함.
- 기존 전술 계획, 조직 시스템, XML 검증 통과.

바인딩 검사는 통행 가능 여부를 제공한 작은 맵 구조와 실제 게임 클래스를 사용한다. Unity의 실제 경로 탐색, 생성된 여러 분대의 움직임, 좁은 통로 혼잡은 플레이에서 추가 확인해야 한다.

플레이에서는 후행 Security가 기존 외부 문으로 돌아가지 않는지, 첫 방을 지나는 동안 개구부 안쪽에 멈추지 않는지, 실내 자리가 없으면 바깥에서 대기하는지 확인한다. 같은 개구부를 고른 후속팀이 멈추면 단계가 `Assemble`인지, `unitDone=True`인지, 배정 칸이 `Invalid`인지, 선행팀 Security가 해당 칸을 점유하는지 함께 기록하면 위 정지 경로를 구분할 수 있다.
