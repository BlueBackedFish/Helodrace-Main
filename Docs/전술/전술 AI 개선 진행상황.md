# 전술 AI 개선 진행상황

기준: 2026-10-03. [바닐라 전투 구조와 전술 AI 개선안](바닐라%20전투%20구조와%20전술%20AI%20개선안.md)을 바탕으로 진행한 코드 변경과 검증 범위다.

## 구현한 내용

### 1. 작업 전환 진단

개발자 전술 창의 `Trace tactical job changes`를 켜면 조직 폰의 작업 시작·종료, 명령 변경, 도달 실패 대기, 후발 합류를 기록한다. 위치, 실행 단계, 이전·새 작업, 목적지, 명령 주체, 종료 조건, 바쁜 자세 및 취소 요청을 확인할 수 있다.

기록은 기본적으로 꺼져 있고 게임 저장에 포함하지 않는다. 맵별 최대 128개 사건을 보관하며 선택 조직의 최근 24개를 표시한다. 같은 명령을 유지하는 매 틱을 로그로 쌓지는 않는다.

커밋: `55dba249`. 코드: [RaidTacticalTrace.cs](../../Source/Helodrace/Core/RaidTacticalTrace.cs).

### 2. 전술 명령의 소유권과 저장

- 이동·대기·지역 교전을 폰별 지속 명령으로 관리한다. 집단 실행기는 명령을 갱신하고 전용 `HD_RaidTacticalControl`의 작업 선택 노드가 바닐라 `Goto`, `Wait_Combat`, 전투 작업을 실행한다.
- 해당 폰의 일반 Lord duty 작업 선택을 전용 노드로 연결한다. 기존 Lord 자체는 유지하므로 집단의 후퇴·해산 판단은 계속 동작한다. 전술 제어 대상에서 빠지면 원래 duty 처리가 재개된다.
- 제어 중에는 Lord의 상시 duty 작업이 별도 명령을 발행하지 않는다. 상시 트리의 폭발 회피 등 다른 긴급 판단은 유지한다.
- 같은 목적지와 이동 속도이면 기존 경로를 유지한다. 목적지가 바뀌면 바닐라의 기본 `Goto` 연속 작업 판정 때문에 변경이 무시되지 않도록 처리한다.
- 장비 작업, 의료 작업, 납치·제압 상호작용, 플레이어 강제 작업과 긴급 작업은 우선 보호한다. 조준·연사·쿨다운이 끝난 뒤 보류된 명령을 적용한다.
- 새 이동·교전 명령이 보류 중이면 전투 대기의 다음 자동 사격을 잠시 막는다. 현재 사격을 계속 취소하지 않고도 연속 사격이 이동 명령을 무한히 지연시키는 상황을 방지한다.
- 이동 실패 시 잠시 대기한 뒤 재시도한다. 작업이 끝나도 기존 일반 습격 AI가 임의의 목적지를 고르는 대신 남은 전술 명령을 다시 선택한다.
- 확정 배치·접근 경로·돌파 셀·선택 전술을 실행 상태와 함께 저장한다. 폰별 명령도 저장하고 로드 후 적용을 재확인한다.
- 뒤늦게 합류한 인원은 현재 계획의 비어 있는 안전 후보에 경계 인원으로 합류한다. 진행 중인 진입 순서를 재번호하거나 이미 들어간 인원을 회수하지 않는다. 사용 가능한 후보가 없으면 현 위치에서 대기한다.

### 3. 스택업·지원·개구부 통과

- 스택업 대기는 원본의 정지 전투 작업을 사용한다. 실제 교전 중에는 사격 방향을 유지하고 평상시에 담당 경계 방향을 바라본다.
- 개구부 안쪽 목적지는 문턱에서 벗어난 셀로 고른다. 다른 폰의 예약·실제 점유와 이전 통과자의 목적지를 확인한다.
- 안쪽에 유효한 자리가 없으면 진입을 보류하고 간격을 두고 다시 찾는다. 한 칸 공간은 한 명만 진입하고 나머지는 외부 경계를 맡긴다.
- 진입 대형과 지원 효과가 준비되면 진입 인원이 함께 각자의 실내 자리로 이동한다. 각자의 단방향 통과 상태와 목적지는 유지하고, 문턱의 통행과 충돌은 바닐라 이동이 처리한다.
- 수류탄 발사를 실행기에 통지하고 해당 투사체를 추적한다. 투척 준비, 살아 있는 투사체, 활성 폭발 피해 처리와 효과 정리 시간이 모두 끝날 때까지 돌입을 보류한다.
- 탄종의 폭발·파편 범위와 투척 오차, 현재 아군 위치·LOS를 확인한다. 실제 발사 시에도 아군이 위험 영역으로 이동했는지 다시 검사한다.
- 지원 사용·발사 대기·실패·생략 상태를 개발자 보고에 표시한다.
- 진입 전 대형이 준비되지 않았으면 시간 제한만으로 돌입하지 않는다.
- 투척자는 발사 직후 대형 복귀 명령을 받으며, 진입 전에는 개구부 안쪽에 있는 상태를 대형 준비 완료로 인정하지 않는다.
- 실내 엄폐가 없으면 개구부 쪽 벽에서 1~3칸 깊이의 옆자리를 선호한다. 전방 엄폐가 실제로 있는 경우만 최대 6칸 깊이까지 후보로 허용한다.
- 통과 후 같은 실내 배치를 교전 중심으로 사용하며 활동 반경을 3칸으로 제한한다. 방 목표 근처나 먼 경계 지점으로 다시 전진하는 명령을 발행하지 않는다.
- 공격 후 대열 복귀는 같은 초기 방 구분과 현재 가시성을 가진 아군을 기준으로 한다. 벽 너머 다른 방의 아군에게 직선 거리만으로 붙으려 하지 않는다.

커밋: `115d1b39`, `824a7856`. 코드: [공격 실행](../../Source/Helodrace/Core/RaidTacticalExecution.cs), [수류탄 발사](../../Source/Helodrace/ModernWar/InventoryGrenadeSystem.cs).

### 4. 목표점과 넓은 이동 영역

정확한 경유지로 복귀시키던 `CorridorReturn`을 제거했다. 폰에는 최종 이동점을 주고 원본 경로 탐색기에 공통 이동 영역의 추가 비용을 전달한다. 접근 경로 주변에서는 비용을 낮추고 멀리 벗어난 셀에는 추가 비용을 부여한다.

외벽 바깥에서 준비하는 단계에는 초기 구조 스냅샷의 실내 공간을 통과 불가로 처리한다. 다른 열린 입구를 통해 실내를 우회한 뒤 외부 작업점에 도착하는 경로를 막기 위한 제약이다. 이미 실내에서 시작한 폰은 그 초기 방에서 나올 수 있으며, 후속 실내 방 돌파에는 외부 접근 제한을 적용하지 않는다.

교전 위치를 찾아 이동할 때는 활동 반경, 수비 추격 한계, 초기 방 경계를 실제 경로에도 적용한다. 활동 영역 밖으로 밀린 폰은 중심으로 복귀할 수 있다. 단순 영역 밖 비용과 실내 진입 금지를 구분한다.

커밋: `51c43289`, `5a16b49d`. 코드: [RaidMovementArea.cs](../../Source/Helodrace/Core/RaidMovementArea.cs).

### 5. 야전·수비 연결

야전에서는 기존 접근·우회·연막·야전 수류탄 분기를 유지하면서 도착 후 지역 교전 명령을 사용한다. 특정 중심 주변에서 바닐라 표적·엄폐·사격선 선택을 사용하고, 원본 locus 검색 사각형의 문제를 피하기 위해 후보 validator로 활동 영역을 제한한다. 모든 인원에게 동시에 계속 새로운 엄폐 이동을 강제하지 않는다.

야전 위협 스냅샷, 야전 투척 표적, 외부 지원 표적과 반격 표적은 현재 관측 조건을 확인한다. 계획의 적 스냅샷은 분대원에게 40칸 이내이며 LOS가 있는 적으로 제한한다. 별도의 마지막 관측 기억 시스템은 아직 추가하지 않았다. 구조 캐시에 적의 실시간 위치를 저장하지 않는다.

수비는 기존 `Defend` 또는 `DefendBase` duty를 가진 비플레이어 조직 인원도 실행 대상으로 포함한다. 원래 Lord의 중심점 또는 duty 위치를 수비 목표로 사용하며 이름 있는 침대로 공격 목표를 바꾸지 않는다. 경계·화력지원 인원과 대응조를 분리한다.

- 경계 인원은 배치 주변의 작은 활동 범위에서 엄폐와 사격 위치를 선택한다.
- 화력지원 인원은 조금 넓은 범위를 사용한다.
- 관측된 위협에 대응하는 인원은 수비 중심 주변 25칸 안에서 이동·교전한다.
- 대응 대상이 사라지면 원래 배치 주변 명령으로 복귀한다.
- 근접 추격 대상이 허용 영역을 벗어나면 작업을 중단한다.
- 원래 수비 duty가 공격·후퇴 등으로 바뀌면 이전 수비 계획을 계속 반환하지 않는다.

독립 수비 연결은 위 두 duty와 기존 조직 등록을 기준으로 한다. 모든 종류의 NPC·플레이어 수비 명령에 적용하는 범용 시스템은 아니다. 야전의 화력조·기동조 교대 전진 전체 시퀀스나 마지막 관측 위치에 따른 수색은 별도 확장 대상이다.

커밋: `5a16b49d`.

## 캐시와 성능

- 기존 맵 구조 캐시와 조직별 초기 방 스냅샷은 그대로 사용한다.
- 실행 중인 확정 계획을 저장하며 일반 계획 갱신과 분리한다.
- 원본 비동기 경로 요청에는 수정하지 않는 비용 배열을 제공한다. 접근 계획과 교전 중심·반경에 따라 만든 배열을 재사용한다.
- 비동기 작업이 이전 배열을 읽을 수 있으므로 원본 경로 탐색기가 모든 작업을 완료하고 종료한 뒤 배열을 해제한다. 배열 캐시는 저장하지 않는다.
- 비용 배열은 셀당 2바이트이며 계획·활동 영역 종류가 많아지면 맵 수명 동안 메모리 사용이 늘 수 있다. 개발자 창에서 요청 수, 캐시 그리드 수, 누적 생성 시간을 확인한다.
- 여러 조직의 배경 계획을 같은 틱에 모두 새로 만들지 않는다. 단일 큰 계획의 틱 분할은 구현하지 않았으며, 스터터링 해소 여부는 실제 계측이 필요하다.

## 검증 결과

- 최종 모드 빌드: 경고 0, 오류 0.
- 대형 연결·전술 판단·통과·명령 정책: 69개 검증 통과.
- 조직·편성 및 실제 XML 검증: 1,365개 검증 통과.
- 설치된 원본 DLL의 대상 메서드·인자·비공개 필드 연결: 10개 검사 통과.
- 새 duty XML 파싱 및 문서 링크·diff 형식 확인.

원본 연결 검사는 리플렉션으로 Harmony 대상과 인자 연결을 확인하는 검사다. Unity/Mono 안에서 패치를 실행하거나 맵을 움직이는 테스트와 다르다. 위 결과만으로 실제 게임의 왕복, 스터터링 또는 모든 오류가 해결되었다고 확정하지 않는다.

재검증 명령:

```powershell
dotnet build Source/Helodrace/Helodrace.csproj --no-restore -p:IntermediateOutputPath=obj/RaidTacticalOrders/ -p:UseSharedCompilation=false
dotnet run --project Source/Tests/RaidTacticalPlanning/RaidTacticalPlanning.Tests.csproj --no-restore
dotnet run --project Source/Tests/RaidTacticalBindings/RaidTacticalBindings.Tests.csproj --no-restore
dotnet run --project Source/Tests/SquadSystem/SquadSystem.Tests.csproj --no-restore -- .
```

원본 연결 검사는 먼저 최신 모드 DLL을 빌드해야 한다. 로컬 패키지 캐시가 필요한 환경에서는 설치된 패키지 경로를 지정해 restore한 뒤 실행한다.
