# 03. 그룹 이동·개인 경로·접촉

## Lord의 집단 명령은 무엇인가

맵의 LordManager가 활성 Lord들을 틱한다. 각 Lord는 LordJob tick → 현재 LordToil tick → tick 신호의 상태 전환 검사 → ticksInToil 증가 순으로 처리한다. Memo·피해·표적 획득·인원 상실 등은 별도의 신호를 보낸다. 현재 Toil이 source인 Transition만 검사하고 먼저 활성화된 전환 하나를 적용한다. Transition의 trigger 목록은 각자 활성화 여부를 검사하며 하나가 통과하면 전환한다. 모든 trigger가 동시에 참이어야 하는 AND 목록이 아니다. [LordManagerTick](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/LordManager.cs:48>), [LordTick](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/Lord.cs:593>), [Transition.CheckSignal](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/Transition.cs:88>)

전환은 pre actions → GotoToil → post actions다. GotoToil은 이전 Toil cleanup, 새 Toil Init, 관련 trigger 초기화, UpdateAllDuties를 실행한다. **Duty를 바꾼다고 모든 개인 Job이 무조건 즉시 끝나는 것은 아니다.** 해당 전환에 EndAllJobs 같은 action이 있어야 명시적 집단 중단이 일어난다. [GotoToil](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/Lord.cs:547>), [Transition.Execute](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/Transition.cs:138>), [EndAllJobs](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/TransitionAction_EndAllJobs.cs:1>)

## 집단 Travel의 실제 이동

LordToil_Travel은 전원에게 같은 dest를 focus로 주는 TravelOrLeave Duty를 만든다. 개인 `JobGiver_GotoTravelDestination`은 기본 exactCell=false일 때 목적지 주변 6칸의 closewalk 셀로 Goto를 만들고, `nextMoveOrderIsWait` 토글에 따라 30~80틱 Wait_Wander도 번갈아 만든다. exactCell·wanderOnArrival·jobDef 등의 설정이 이 패턴을 바꿀 수 있다. 이 대기는 경로 알고리즘이 아니라 **이동 JobGiver의 동작**이다. [LordToil_Travel](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/LordToil_Travel.cs:1>), [GotoTravelDestination](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/JobGiver_GotoTravelDestination.cs:1>)

도착 판정은 205 global ticks 간격에 **소유 폰 전원**이 dest 10칸 이내이고 ClosestTouch 도달 가능인지 확인한다. 참이면 TravelArrived memo를 보낸다. 여기에는 75% 도착 quorum이나 일정 대형의 개인 슬롯 배정이 없다. 확장 Toil의 AllArrivedCheckRadius override는 별개다.

각 Goto의 Driver는 목표 셀을 예약하고 Goto Toil에서 `pather.StartPath`를 호출한다. **공통 목적지를 받은 각 폰이 독립적인 경로 요청을 만든다.** 여러 경로 계산의 grid를 공유하는 것은 가능하지만 모든 폰에게 같은 경로 노드열을 복사하는 기본 Travel 규칙은 아니다. [JobDriver_Goto](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/JobDriver_Goto.cs:10>), [Toils_Goto.GotoCell](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Toils_Goto.cs:55>)

## 이동 중 적을 만나면 누가 멈추는가

아래 경로들을 분리해야 한다.

| 상태 | 반응을 만드는 코드 | 실제 효과 |
|---|---|---|
| 일반 Travel Lord의 폰이 피해를 입음 | Trigger_PawnHarmed → DefendPoint 전환 | 랜덤 소유 폰 위치를 방어점으로 정하고 EndAllJobs. 이후 각 폰이 Defend 트리에서 교전/필요/배회 선택 |
| Travel Lord가 적을 봄 | acquired-target 신호는 존재하지만 이 그래프에 해당 전환 없음 | 단순 발견만으로 전원이 방어 전환한다는 일반 Travel 규칙은 없음 |
| Assault/Defend 전투 Duty의 Goto가 만료/종료/override됨 | 해당 ThinkTree의 AIFightEnemy | 그 폰이 표적과 사격점을 다시 고름. 타 폰 전원 정지는 별도 그래프가 필요 |
| 플레이어 비징집 폰 | constant ConfigurableHostilityResponse | 강제 작업 등 조건을 제외하고 가까운 적 공격/도주/무시 |
| 징집 Goto | Orders/강제 명령 및 Job 실행 | Goto 자체는 원거리 자동 사격 루프를 가지고 있지 않음. 도착 뒤 Wait_Combat이 현재 자리 사격 |
| 근접 위협/막힌 경로 | ReactToCloseMeleeThreat 또는 PathFollower blocking 대응 | 개인 근접 공격·작업 종료. 일반 원거리 엄폐 대응과 다름 |

LordJob_Travel의 방어 전환은 PawnHarmed이며, 피해 없이 1200틱이 지나면 Travel로 돌아간다. “적을 보면 바로 전원이 멈춤”이 아니다. PawnHarmed에는 ExternalViolence 피해, 폭력적 인원 상실(다운·죽음·포로), 체포 시도도 들어간다. [Travel graph](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/LordJob_Travel.cs:17>), [SetDefendLocalGroup](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/TransitionAction_SetDefendLocalGroup.cs:1>), [Trigger_PawnHarmed](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/Trigger_PawnHarmed.cs:1>)

방어 전환 후 Duty.focus는 공통 방어점, 기본 반경 28(종류별 override 가능)이다. 개인 엄폐점은 AIDefendPoint가 고른다. 일렬 대형/호 대형/화력조 협력/최후방까지 동시 도착을 강제하는 범용 구조는 여기에 없다. [DefendPoint](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI.Group/LordToil_DefendPoint.cs:1>)

## Escort/FollowClose가 경로를 닮게 만드는 방식

Follower는 followee에게 도달 가능하고 충분히 멀면 FollowClose Job을 받는다. Driver는 이동 중 30틱 hash 조건으로 거리를 재검사한다. 시작에는 followRadius×1.2, 이미 followee로 이동 중이면 followRadius를 써 왕복을 줄인다. 가까우면 단순 거리 외에 인접/LOS도 본다. [AIFollowPawn](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/JobGiver_AIFollowPawn.cs:1>), [FollowClose](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/JobDriver_FollowClose.cs:1>)

followee가 아직 목적지까지 움직이고 있다면 그 폰의 LastPassableCellInPath 근처를 목적지로 삼을 수 있다. 이때 속도를 followee와 맞춰 더 빠른 폰이 앞서 달리는 것을 줄인다. 먼 follower는 followee의 현재 Thing 위치를 Touch로 추적한다. 따라서 뒤 인원들이 비슷한 방향으로 모이지만, 전원이 한 공유 경로·한 개인 슬롯을 따르는 방식은 아니다.

## PathFollower는 적 탐색기가 아니다

StartPath는 path mode를 해결하고 도달 가능성을 빠르게 확인한다. 같은 목적지/모드의 진행 경로면 재시작하지 않을 수 있고, 중간 이동 진행량을 유지할 수 있는 조건도 있다. 새 목적지는 per-pawn PathRequest가 된다. [StartPath](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_PathFollower.cs:154>)

PatherTick은 중복 점유 복구 → FullBodyBusy면 대기 → 도착 → 경로 결과 수령 → 필요 시 새 요청 → 다음 칸 충돌 → 이동 비용 지불/다음 칸 진입 순으로 진행한다. 이 루프에는 원거리 적을 관측하고 엄폐점을 고르는 일반 분기가 없다. 적 대응은 주로 위 계층의 Job/트리에 있다. [PatherTick](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_PathFollower.cs:217>)

재경로 검사는 hash 30 조건에서 다음 상황을 확인한다.

- 목표 무효/맵 변경, 경로 없음·노드 소진.
- 가까운 목표가 경로 끝에서 더 이상 즉시 도달 가능하지 않음.
- region heuristic 경로를 75노드 소비함.
- 움직이는 Thing 목표의 좌표가 거리별 허용치보다 크게 바뀜(먼 목표 10칸, 가까워지면 5/3/2/0.5칸).
- 앞쪽 최대 20노드의 비보행·폰 충돌·KnownDanger·열 수 없는 비적대 문·금지 문·대각선 막힘.

[NeedNewPath](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_PathFollower.cs:881>)

이때 KnownDangerAt은 해당 칸의 edifice가 그 폰에게 dangerous인지 보는 함수다. **모든 적 사거리로 만든 위협 맵 또는 킬존 판정이 아니다.** [KnownDangerAt](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/PawnUtility.cs:619>)

## 문·막힘·움직임 비용

닫힌 문을 열 수 있으면 manual open을 시작하고 문이 다 열릴 때까지 cooldown stance로 기다린다. 적대 건물 또는 canBashDoors 조건의 막힌 건물에는 AttackMelee expiry300을 시작할 수 있다. 이것은 일반 이동의 blocker bash이며 공병/브리처의 계획된 장애물 선택과 다르다. [TryEnterNextPathCell](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_PathFollower.cs:586>)

적 폰이 앞 칸을 막고 180틱 움직이지 못했거나 lastBlocker가 생긴 경우, 공격 가능한 폰은 1회 AttackMelee·expiry300을 시작하고 그렇지 않으면 이동 작업을 실패시킨다. 친군 막힘은 우회/대기, 중복 점유 복구 등의 경로를 사용한다. [blocking 대응](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_PathFollower.cs:317>)

칸 이동 비용은 cardinal/diagonal TicksPerMove + 지형/건물 비용, terrain tag 속도 보정 후 450 상한을 적용한다. Amble은 ×3·최소60, Walk는 ×2·최소50, Jog는 ×1, Sprint는 ×0.75 반올림이다. stagger와 flying은 틱당 비용 지불을 조절한다. `Sprint`가 별도의 전술 경로를 만드는 것은 아니다. ## 예약과 물리적 겹침은 다르다

DestinationReservation은 선정하는 JobGiver가 CanReserve를 확인할 때 중복 위치를 줄이는 협약이다. **Reserve 자체는 모든 중복을 거절하지 않는다.** faction별 목록, claimant/job/obsolete 상태를 관리하며 Job 종료·새 경로·새 예약에서 정리된다. NPC CanReserve는 비적대 세력도 확인하고, player 쪽은 자기 faction을 확인한다. [PawnDestinationReservationManager](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/PawnDestinationReservationManager.cs:1>)

실제 충돌은 PawnUtility와 PathFollower가 별도로 결정한다. 다운/사망/자체 정지·최근 가까운 적 여부·종류의 collidesWithPawns·심리적 비가시·몸 크기 등의 조건이 있다. 비적대 폰 충돌은 양쪽 Job/Def/Driver의 collideWithPawns 상태도 본다. AttackStatic/AttackMelee는 해당 JobDef 값을 켜지만 일반 Goto와 Wait_Combat에는 같은 명시 설정이 없다. 다만 **Wait Driver는 자동 근접/원거리 공격을 시도하는 분기에서 Driver.collideWithPawns=true로 바꾸고, 다음 공격 검사 시작에는 false로 돌린다.** 일반 Goto도 개별 Job에서 플래그를 켤 수 있다. 그러므로 **바닐라 예약을 호출했다는 이유만으로 항상 한 칸 한 명이 보장되지는 않는다.** [충돌 규칙](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/PawnUtility.cs:482>), [JobDefs](</C:/Program Files (x86)/Steam/steamapps/common/RimWorld/Data/Core/Defs/JobDefs/Jobs_Misc.xml:143>), [Wait Driver](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/JobDriver_Wait.cs:96>)

## 1.6의 경로 계산은 이미 Job System을 사용한다

일반 이동은 PathRequest를 workQueue에 넣는다. PathFinderTick은 이전 scheduled jobs의 완료를 기다려 결과를 전달하고, 현재 요청을 검증해 모은 뒤 MapData를 수집하고 grid jobs와 path jobs를 스케줄한다. 같은 MapGridRequest는 grid 결과를 재사용한다. 여러 batch로 나누며 batch 안의 path jobs는 scratch를 공유하므로 dependency로 직렬화한다. [PathFinderTick](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/PathFinder.cs:282>), [ScheduleBatchedPathJobs](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/PathFinder.cs:360>)

순수 NativeArray 기반 PathFinderJob과 grid 계산 외에, 문/폰/provider를 다루는 ManagedJob 단계도 있다. 따라서 “경로 탐색 전체가 Unity 객체 접근 없이 순수 워커 계산”이라고 요약하지 않는다. 결과 수집은 CompleteAll 대기점을 갖는다. [ParameterizeDoorBlockedJob](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/PathFinder.cs:594>), [ForceCompleteScheduledJobs](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/PathFinder.cs:441>)
