# 06. 회피·도주·플레이어 명령

## 폭발 회피는 위험 통보에서 시작한다

일반 constant tree의 FleePotentialExplosion은 맵의 모든 수류탄을 스캔하지 않는다. `mindState.knownExploder` 한 개를 사용한다. intelligence>=2, exploder spawned, 이동/기어가기 가능, playerForced 현재/예정 작업 없음, 폭발물9칸 이내 조건에서 직접 flee 목적지를 찾고 Sprint Goto를 반환한다. [FleePotentialExplosion](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/JobGiver_FleePotentialExplosion.cs:1>)

knownExploder를 주는 `Notify_DangerousExploderAboutToExplode`는 intelligence>=2이며 **비징집**일 때만 기록하고 즉시 CheckForJobOverride한다. HumanlikeConstant 쪽에도 비징집/깨어 있음/비화재/비정신 상태 gate가 있다. 즉 “징집시킨 플레이어 폰도 항상 이 바닐라 코드로 수류탄을 피함”은 성립하지 않는다. [MindState 통보](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse.AI/Pawn_MindState.cs:716>)

GenExplosion.NotifyNearbyPawnsOfDangerousExplosive는 기본4.5칸 주변을 검사한다. instigator Pawn에는 별도 통보하며, 다른 폰은 intelligence·onlyFaction·ExternalViolence 조건을 통과해야 한다. passability가 impassable인 폭발물은 인접 room들을, 나머지는 자기 room을 기준으로 한다. 폰의 room이 null 또는1칸이면 통보 예외가 있고, 일반 room이면 폭발물의 겹치는 room과 LOS가 필요하다. [GenExplosion 통보](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/GenExplosion.cs:146>)

호출자를 보면 큰 차이가 드러난다.

| 폭발 계열 | 통보 시점 | 세력 범위 |
|---|---|---|
| Projectile_Explosive | 착탄 후 explosionDelay가 있을 때 | `onlyFaction=launcher.Faction` |
| CompExplosive | wick 시작 시 | onlyFaction=null, 즉 세력 필터 없음 |
| 지연 없는 Projectile_Explosive | impact에서 곧바로 Explode | 같은 지연 회피 통보 절차를 거치지 않음 |

[Projectile_Explosive.Impact](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/Verse/Projectile_Explosive.cs:27>), [CompExplosive.StartWick](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/CompExplosive.cs:212>)

**따라서 일반 지연 발사체의 통보는 발사자 측 아군 회피에 가깝다. 적이 던진 수류탄을 상대 세력이 발견해 회피한다는 범용 감지기는 아니다.** 특수 projectile/능력/모드가 이 함수를 다르게 호출하는 경우는 구분해야 한다.9칸은 회피 JobGiver 거리이며 최초 주변 통보4.5와 같은 값이 아니다.

## 직접 폭발 회피 목적지

## 징집 상태는 Job 선택을 바꾼다

Pawn_DraftController.Drafted 변경은 priority work/queue를 정리하고, 현재 player-interruptible 작업을 종료하며, FireAtWill을 기본true로 돌린다. 비징집으로 돌아가면 destination reservation을 해제한다. voluntarily joinable Lord에서는 빠질 수 있고, master를 따르는 동물에도 상태 변화를 알린다. 메카/아기 운반/카랴반 등의 예외도 있다. [Pawn_DraftController](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/Pawn_DraftController.cs:19>)

FireAtWill=false는 warmup을 soft cancel하지만 모든 강제 공격 Job이나 발사 중 burst까지 동일하게 끄는 범용 취소 버튼은 아니다. Wait_Combat의 자동 원거리 선택이 해당 플래그를 확인한다. Orders는 idle drafted 폰에게 무기한 Wait_Combat을 준다. 징집 자동 사격의 엄폐 이동 부재는 플레이어가 위치를 지휘하도록 만든 선택이다.

## 플레이어 이동 명령의 위치 선택

단일 DraftedMove는 클릭 주변 standable 셀을 찾고 BestOrderedGotoDestNear를 거쳐 Goto를 주문한다. 목적지가 같거나 이미 도착했으면 작업 재시작을 줄인다. reachable/메카 command range/exit map 등을 확인한다. 이 Goto에 자동 원거리 반응을 삽입하지 않는다. [DraftedMove](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/FloatMenuOptionProvider_DraftedMove.cs:1>)

BestOrderedGotoDestNear는 root 자체가 유효하면 **바로 root**를 쓴다. 아니면 가까운 radial 후보에서 surrounding cover score를 사용하고, 첫8칸 이상을 본 뒤 유효 후보가 있으면 끝낸다. 필요하면30칸까지 넓힌다. 이 엄폐는 적 방향의 CastPositionFinder와 달리 주변 총 cover score다. **클릭한 칸이 이미 유효할 때 더 좋은 엄폐로 자동 보정하지 않는다.** [BestOrderedGotoDestNear](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/RCellFinder.cs:75>)

여러 폰을 선택하면 MultiPawnGotoController가 드래그 선 start→end에 각 폰의 root를 보간하고, 이미 배정된 dests와 command range를 validator로 제외한다. interaction 중10틱 또는 마우스 변화에서 재계산하고 최종 확정 때 폰별 Goto를 발행한다. 이는 입력 시 위치 배정이며 NPC Lord의 일반 그룹 이동과 다르다. 배정 후에는 개인 PathFollower를 사용한다. [MultiPawnGotoController](</C:/Users/Public/Documents/ESTsoft/CreatorTemp/vanilla-combat-4871-20261014/RimWorld/MultiPawnGotoController.cs:104>)

## 장면을 분석할 때 확인할 순서

1. Pawn의 main/constant ThinkTree, LordJob/현재 LordToil/Duty를 확인한다.
2. 현재 JobDef/driver/toil/expiry/checkOverride/collideWithPawns/playerForced를 확인한다.
3. stance가 warmup/cooldown/stunned인지, pather가 요청 대기/이동/충돌/도착 상태인지 구분한다.
4. 표적 획득·피해·exploder 알림이 실제로 발생했는지와 그래프에 해당 trigger가 있는지 확인한다.
5. CanSee/CanHit/LOS/명중/friendly-fire 각각의 함수와 flag를 확인한다.

그룹이 멈춘 장면을 개인 Job의 자동 사격만으로, 개인이 멈춘 장면을 Lord의 집단 전환만으로 설명하지 않는다.
