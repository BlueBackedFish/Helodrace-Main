# 3순위: 통신 프레임 분산 갱신과 장비 캐시

2026-10-07. CPU·틱 지연 최우선 계획의 3순위를 적용했다. 분대마다 통신 상태를 따로 갱신하고, 장비 목록과 연결 그래프를 더 오래 재사용한다.

## 적용 내용

- 전체 분대를 20틱마다 재구축하던 방식을 분대별 기한 큐로 교체했다. 한 틱에 최대 2분대, 분대 사이에서 0.5ms의 소프트 예산을 검사한다. 하나의 프레임 계산 자체를 중단하지는 않는다.
- 조직 목록 확인은 180틱, 개별 프레임 확인은 120틱, 그래프 수명은 300틱이다. 4칸 이내 이동이나 관련 없는 구조 변경은 기존 그래프를 유지한다.
- 방탄복에 실제 장착된 무전기 목록은 최대 600틱 재사용한다. 태블릿은 사용하지 않는다. 무전기 작동 여부는 연결 계산 시 확인하며, 실제 패킷 전달 때 장착 여부·네트워크·거리·작동 상태를 다시 검사한다.
- 전달과 ACK 처리는 유지한다. LOW 분대 사이의 접촉 전달은 현재 거리·LOS·연막을 검사한다. 개인 보고와 원장 정리는 20틱마다 순환하는 최대 2분대만 처리한다.
- 사상자 이벤트는 해당 분대 프레임을 무효화하고 다음 틱 갱신을 요청한다. 조직 해산과 맵 제거 때 예약·프레임·장비 캐시를 제거한다. 습격 종료 후에는 목록 확인 기한까지 휴면한다.

장비 변경의 새 연결 탐지는 최대 600틱 늦을 수 있고, 작은 이동에 의한 내부 지휘 연결은 오래된 결과를 사용할 수 있다. 전달 직전 검증은 제거하지 않았다. 작은 그래프를 워커로 옮기는 대신 갱신 횟수와 반복 장비 탐색을 줄였다.

## 관련 메서드 성능 검증

기존 프로파일러에 `RefreshFrames`, `ProcessTick`, `RaidCommunicationPolicy.Delays`만 추가했다. 기본 coarse 대상은 틱과 컴포넌트 맥락 확인용이다. 동일 시드·맵·600틱 준비·900틱 수집으로 HIGH 208/403명과 LOW 400명을 비교하고 각각 0명으로 정리했다. 모든 캡처는 완료, 계측 예외와 dropped sample은 0이다.

Core 100%는 `GenRadial.NumCellsInRadius(float)` 10,000회 배치의 7회 측정 중앙값이다. 아래 비율은 각 캡처의 Core 값으로 정규화한 틱당 비용이다. 메서드는 Stopwatch 경과 시간이며, 실제 스레드 CPU 시간은 `DoSingleTick`에서만 수집한다.

| 대상 | 이전 ms/틱 → 이후 | Core 대비 이전 → 이후 | 정규화 감소 |
|---|---:|---:|---:|
| HIGH 403, RefreshFrames | 0.3280 → 0.0547 | 120.71% → 20.21% | 83.3% |
| LOW 400, RefreshFrames | 0.1463 → 0.0437 | 53.94% → 15.65% | 71.0% |
| HIGH 403, 통신 선택 범위 합집합 | 0.3417 → 0.1089 | 125.77% → 40.21% | 68.0% |
| LOW 400, 통신 선택 범위 합집합 | 0.1649 → 0.0561 | 60.82% → 20.11% | 66.9% |
| LOW 400, Delays | 0.0494 → 0.0119 | 18.22% → 4.26% | 76.6% |

`ProcessTick`에서 프레임 작업을 분리했기 때문에 부모/자식 inclusive 비용을 단순 합산하거나 ProcessTick 하나만 비교하지 않는다. 합집합은 선택된 통신 메서드들의 trackedSelf 합계이며, 계측하지 않은 하위 호출 비용도 포함한다. Delays는 RefreshFrames에 포함되는 호출이 있으므로 표의 행끼리도 더하지 않는다.

HIGH 403의 RefreshFrames 최대 호출 지연은 9.64→1.32ms, LOW 400은 5.91→0.69ms였다. 호출 수는 HIGH 45→948, LOW 53→945로 늘었다. 새 호출의 대부분은 기한 큐 확인이며, 전체 재구축 호출과 같은 작업량이 아니다. HIGH 208의 합집합은 0.1822→0.1056ms/틱이다. HIGH 208→403에서 이후 RefreshFrames는 0.0284→0.0547ms/틱으로 증가한다.

습격 종료 후 0명 시험에서는 RefreshFrames가 45회에서 5회로 줄었다. 통신 합집합은 HIGH 0.001184→0.000355ms/틱, LOW 0.001049→0.000270ms/틱이다. 목록 확인 때문에 완전한 0비용은 아니다.

## 전체 틱과 검증 한계

전체 메인 틱의 실제 CPU 시간은 HIGH 403에서 23.18→17.91ms/틱, LOW 400에서 14.83→12.59ms/틱이었다. 통신에서 직접 관찰한 절약은 각각 약 0.23/0.11ms/틱이므로, 전체 틱 개선을 전부 이 변경의 효과로 해석할 수 없다.

HIGH의 시작·종료 단계 분포는 같지만 이동한 인원이 각각 1명 적었다. LOW는 이전 400명, 이후 398명이 이동했고 종료 단계가 Support에서 EntryWait로 달랐다. HIGH 403의 전달 검증은 이전 0회, 이후 720회로 늘어 통신 트래픽도 같지 않다. 모두 생존했으나 행동이 완전히 동일한 시험은 아니다. 단일 전후 수집이며 반복 시험의 통계적 보장은 하지 않는다.

빌드와 실제 게임 클래스 바인딩 검증을 통과했다. 통신 통합 39개 및 스케줄링 6개 검사에서 연결 유효기간·작은 이동 재사용·무전기 제거·사상자·현재 벽에 의한 음성 차단·한 틱 작업 상한·해산과 맵 제거 정리를 확인했다.
