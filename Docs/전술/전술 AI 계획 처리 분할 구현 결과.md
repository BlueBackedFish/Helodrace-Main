# 전술 AI 계획 처리 분할 구현 결과

작업: 2026-10-06. [구조 개편 검토](전술%20AI%20구조%20개편%20검토.md)의 B 계획 서비스에 해당한다. 이전에는 첫 계획만 순서를 제한하고, 다음 방·정체 복구·진입점 복구는 한 번의 호출에서 전체 계획을 생성했다. 이제 운영 코드의 모든 계획 생성이 공통 요청 서비스를 사용한다.

## 요청과 실행

`MapComponent_RaidPlanningService`는 분대별로 요청 하나를 보관한다. 요청에는 용도, 목표, 기준이 된 확정 계획, 구성·장비 서명, 조직의 고정 구조 버전, 계산 중인 계획, 중간 계산 상태가 들어간다. 같은 요청을 다시 조회하면 기존 계산을 이어서 사용하며 처음부터 다시 시작하지 않는다.

`GameComponent_RaidPlanScheduler`는 모든 맵의 요청을 한 대기열에서 번갈아 처리한다. 게임 전체 프레임당 3ms 또는 최대 64개 계산 조각을 처리하고 남은 요청을 다음 프레임으로 넘긴다. 일시정지 중에는 계산하지 않는다. 맵마다 3ms를 따로 주거나 분대마다 새 스레드를 만드는 방식이 아니다. Pawn·Map·LOS·예약 조회는 메인 스레드에 남아 있다.

| 계산 | 분할 지점 |
| --- | --- |
| 입력 수집 | 구성원, 무장/관측 적, 목표, 국소 지도 등 주요 수집 구간 사이 |
| 돌파 후보 | 구조 후보 하나마다, 상세 후보 하나마다, 스택 검증 인원마다 |
| 경로 | 최대 32개 frontier 작업 후 양보. frontier·거리·이전 칸을 유지 |
| 경로 복원 | 최대 32개 칸마다 양보 |
| 우회 | 각 후보와 두 경로 탐색 사이 |
| 자리 배정 | 부상자·진입자·지원자 한 명마다 |
| 이동 지향점 준비 | 노드 하나와 연결 구간 하나마다 |

48개 구조 후보, 8개 상세 후보, 계획 전체의 4096개 경로 작업 한도는 유지한다. 프레임이 바뀌어도 작업 한도를 새로 지급하지 않는다. 더 좋은 후보를 끝까지 비교하지 않고 첫 유효 돌파를 사용한다. 이름 있는 침대나 명시적인 목표가 있으면 사용하지 않을 야전 fallback 지점을 추가 탐색하지 않는다.

3ms는 다음 조각의 실행을 허가하는 기준이다. 바닐라 `CanReach` 한 번, 지역 지도 갱신, 대형 후보 목록 생성, GC 등은 중간에 끊을 수 없어 조각이 이를 넘길 수 있다. 이를 엄격한 최대 시간으로 표현하지 않는다. 개발자 보고와 감사 결과에 실제 조각 최대 시간을 기록한다.

## 결과 채택과 안전

- 첫 계획이 준비되지 않았거나 낡아서 폐기되면 안전한 대기 소유권을 유지한다. 잠깐 일반 습격 AI로 돌아가 다른 입구를 따라가지 않는다.
- 다음 방과 정체 복구 계산 중에는 기존 확정 명령을 유지한다. 다음 방 목표도 계산 중에 다시 고르지 않는다.
- 이미 점유한 방을 다시 돌파하거나 관측한 진입점이 막힌 경우에는 잘못된 공병 작업을 중단하고 제자리 대기하며 대체 계획을 기다린다. 실제 C4·투척물 안전 대기를 우회하지 않는다.
- 결과는 구성·지휘·무기·착용 장비·수류탄·점화기·C4, 구조 버전, 기준 계획, 살아 있는 담당자, 현재 방 구역, 진입·정지 칸을 재검증한 뒤 채택한다. 단순 한 칸 이동은 요청 서명에 포함하지 않는다.
- 피해 재평가는 해당 분대 요청을 취소하고 기존의 확정 돌파·통과 기록을 보존한다. 맵 제거와 조직 정리도 중간 계산을 해제한다.
- 계산 중 계획은 실행 상태에 공개하지 않는다. 실행 단계와 Job 변경은 완료된 결과를 게임 틱에서 조회한 뒤 수행한다. 개발자 새로고침도 요청으로 처리하며 즉시 전체 계획을 계산하지 않는다.
- 관측한 적 위치와 사거리는 양보 전에 값으로 복사한다. 기다리는 동안 적 Pawn이 시야 밖으로 이동해도 새 위치를 몰래 반영하지 않는다. 확정 계획이 교체되면 이전 계산에 고정했던 다음 방·재확인 목표도 해제한다.

계산 중 iterator와 대기열은 저장하지 않는 파생 자료다. 저장되는 확정 계획·단계·선택 통로·접촉 기억을 바탕으로 로드 후 필요한 요청을 다시 발행한다. 실제 저장/로드 중 진행 시험은 별도 통합 검증 범위로 남아 있다.

구형 동기 `MakePlan`, 맵별 계획 입장 예산, 첫 계획 전용 별도 대기열을 제거했다. 정기 실행에서 이동 노드를 동기로 다시 준비하는 호출도 제거했다. 완료되지 않은 계획을 바닐라에 넘기는 별도 fallback은 추가하지 않았다.

## 검증과 측정 해석

- 모드 빌드: 오류·경고 0개.
- 지도·이동·공정 대기열 자동 검증: 940개 통과. 다른 맵의 요청에 차례 양보, 중복 제출, 취소, 일시정지/예산 소진, 조각 수 제한 포함.
- 실제 설치 게임 클래스: 경로 frontier 중단·재개·우회·공통 한도 5개 검증과 요청 보존·피해 취소·세대 교체·낡은 결과 거절·첫 대기 소유권·맵 제거 검증 통과. 기존 Security·대형·투척·관측·통신·저장 자료 검증도 통과.
- 기존 전술 정책 자동 검증 통과.

`Planning` CPU는 이제 한 계획 전체가 아니라 계산 조각 표본이다. 변경 전 계획 p95와 변경 후 조각 p95를 같은 종류의 값으로 비교하면 안 된다. 합계와 완료 요청 수를 함께 본다. `BreachSearch`·`RouteSearch`는 하위 포함 구간이며 합산하지 않는다.

계획 계산을 Update에서 처리하므로 `GameTick` 비용만 줄었다고 총 CPU가 줄었다고 판단하지 않는다. 별도로 기록한 계획 CPU와 TPS/FPS도 함께 확인한다. 준비 구간까지 포함한 CPU 합계·최대값과, 측정 구간의 TPS/FPS를 구분한다. 분위수는 최근 최대 2048개 표본이다. 계획 서비스 통계는 게임 전체에서 시나리오를 넘겨 누적된다.

## 400명 반복 시험

LOW 400명·37개 분대가 같은 개구부를 공유하는 조건이다. 준비 300틱, 측정 600틱이며 같은 게임에서 `1배속 → 3배속 → 3배속 → 1배속 → 1배속 → 3배속` 순서로 실행했다. 대부분은 개구부 대기 상태라 여러 방의 동시 교전 성능을 의미하지 않는다.

| 항목 | 이전 C 시험 | B 반복 시험 |
| --- | --- | --- |
| 1배속 TPS | 30.938, 1회 | 46.542 / 41.493 / 39.248 |
| 1배속 FPS | 15.469 | 23.503 / 20.746 / 19.624 |
| 3배속 TPS | 33.892, 1회 | 48.506 / 45.570 / 38.278 |
| 3배속 FPS | 12.766 | 14.875 / 15.114 / 14.561 |
| 성공 계획 | 각 37개 | 매 시험 37개, 실패·한도 소진 0개 |
| 시험 종료 시 미완료 계산 | 이전에는 미기록 | 매 시험 0개 |
| 실제 계산 조각 최대 | 기존 표본은 전체 계획 | 첫 시험 11.626ms, 이후 시험 Planning 최대 2.140~4.139ms |

조각 처리 한도 3ms를 넘는 호출은 남아 있다. 첫 시험에서 큰 조각이 있었으며 서비스 누적 최대는 이후에도 11.626ms를 표시한다. 전체 틱 최대도 168.674~246.886ms, 실행 최대는 149.732~183.048ms여서 실행 측의 순간 지연은 별도로 줄여야 한다.

이전 C는 배속별 1회이고 실행 순서·준비 상태가 다르다. 반복 B 결과가 더 높은 TPS를 보였지만 개선율이나 수용 인원을 보장하지 않는다. 이 반복 버전 이후 마지막으로 관측 위치 복사와 확정 계획 교체 시 이전 요청 목표 해제를 추가했다. 최종 DLL 검증 결과는 아래에 별도로 기록한다. 원자료와 DLL별 구분은 [측정 JSON](전술%20AI%20계획%20처리%20분할%20측정.json)에 있다.

## B 단계 시험 DLL 확인

B 단계 DLL SHA-256: `F3438E75B67A021F0B29E36608E3F91F3308BBE9CD9E67C343E0499E8168B5CF`. 설치 게임 DLL과 일치함을 확인한 뒤 독립 테스트 환경에서 실행했다.

Security 실게임 회귀 5개가 모두 통과했다. 각 단계 11명이며 알려진 문, 관측한 새 개구부, 숨은 반대편 문 개폐, 경계 해제 뒤 합류, HC 연막 통과를 확인했다. 완료까지 각각 436 / 480 / 495 / 276 / 445틱이었다. 최종 버전 빌드 및 자동 검증도 통과했고, 이 시험 로그에 계획 처리 예외나 새로운 전술 관련 스택 오류는 없었다.

최종 DLL의 400명 재확인에서는 1배속 TPS/FPS 30.389/15.195, 3배속 31.763/11.997로 이전 반복 버전보다 낮게 나왔다. 각 37개 계획 성공, 400명 생존, 실패·미완료 계산 0개이며 계획 조각 최대는 첫 시험 9.472ms, 다음 시험 1.721ms였다. 전체 틱 최대는 223.295/260.274ms다. 초기 상태와 진행 인원에 따라 결과 차이가 크므로 이번 변경의 안정적인 TPS 향상을 주장하지 않는다. 실제 게임의 실행 갱신 비용과 프레임 전체 비용을 다음 단계에서 더 줄여야 한다.

50명 지속 시험은 준비 300틱·측정 6000틱·3배속이다. TPS 179.302, FPS 56.590이며 50명 전원 생존·이동했다. 분대 계획 5개가 유효하고 종료 단계는 SecureRoom 2 / ClearRoom 1 / Assemble 2였다. 계산 조각 2035개, 완료 요청 33개, 낡은 결과 폐기 18개, 미완료 계산 0개로 후속 방 진행이 유지됐다.

| --- | --- | --- |
| Planning 합계 / 최대 ms | 150.5 / 전체 계획 82.988 | 193.7 / 조각 9.202 |
| Execution 합계 / 최대 ms | 1814.5 / 156.165 | 1291.9 / 78.096 |

실행 비용과 최대 틱 시간이 낮게 나왔지만 전체 틱 합계와 계획 합계는 증가했다. 단발 지속 시험의 부하·진행 단계 차이도 있어 CPU 총량 감소로 단정하지 않는다. Goto 시작 지연은 p50/p95/p99 = 0/1/150틱, 최대 671틱으로 일부 요청의 긴 지연이 남아 있다. 현재 지표는 시작된 Goto만 기록하며 미시작 요청의 대기 나이를 따로 집계하는 기능은 다음 실행 개선에서 필요하다.

이 지속 시험에는 별도 통신 오류가 25회 발생했다. 64개 보고 기억이 가득 찬 상태에서 오래된 수신 보고를 즉시 제거해 놓고 `ProcessTick`이 해당 보고를 다시 `First`로 찾는 문제다. 따라서 이 지속 시험 수치를 오류 없는 성능 자료로 취급하지 않는다. 보고 수신 결과를 실제 보관 여부와 일치시키는 수정과 재시험을 아래 후속 수정에서 진행했다.

## 통신 용량 오류 후속 수정

`RaidReportLedger.Receive`는 이제 수신한 복사본이 실제 기억에 남았을 때만 성공을 반환한다. 더 새로운 64개 보고에 밀려 들어온 보고 자신이 제거됐다면 전술 정보에 적용하거나 보관 목록에서 다시 찾지 않는다. 통신 자체의 ACK는 정상 완료해 같은 낡은 보고를 계속 재전송하지 않게 한다. 최신 보고 우선·기억 용량·LOW 접촉·High 장비와 지연 규칙은 유지한다.

용량이 가득 찬 상태의 오래된 보고 수신, 실제 전달 틱에서 정보 미적용, 후속 ACK와 대기열 해제를 검증했다. 통신 통합 검증은 기존 24개와 신규 3개를 포함해 27개가 통과했다. 수정 DLL SHA-256은 `270E724DDCA4F39359ADA14B90DA99408729C5EA6A1C4AF04CF67CC28B7D128E`이다.

수정 DLL의 50명·6000틱·3배속 재시험에서는 TPS 178.075, FPS 56.411, 생존 50명, 이동 47명이었다. 5개 계획 성공, SecureRoom 3 / Breach 1 / Assemble 1, 미완료 계산과 Native 준비 각각 0개다. 로그의 통신 예외와 계획 처리 예외는 재발하지 않았다. 계획 조각 최대 9.196ms, 실행 최대 65.542ms, 전체 틱 최대 68.739ms이며 Goto 시작 지연 p50/p95/p99 = 0/60/120틱, 최대 193틱이다. 이 역시 단발 시험이므로 앞선 시험과의 비율을 일반적인 개선율로 쓰지 않는다.

## 남은 범위

단일 바닐라 검증과 지역 지도/대형 후보 생성의 큰 조각, 실행 쪽의 관측·위험 반응·예약·Native 이동 배열 준비 비용은 남아 있다. 모든 실행 갱신을 분산하는 큐와 역할 작업·명령 소유권 통합은 다음 개편 범위다. 다수 맵·여러 독립 진입점·High 편제·진행 중 저장/로드·교전 중 장비 교체는 실제 게임에서 추가 검증해야 한다.
