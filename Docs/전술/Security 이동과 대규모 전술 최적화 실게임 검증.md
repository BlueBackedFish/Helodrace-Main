# Security 이동과 대규모 전술 최적화 실게임 검증

작성: 2026-10-05. 기존 [원인 분석 및 계획](Security%20이동%20정지%20원인과%20대규모%20전술%20최적화%20검토.md)의 구현·검증 후속 기록.

## 확인한 정지 원인과 수정

Security에는 돌입 인원과 다른 이동 요구가 생긴다. 접촉 경계 명령으로 자리를 지키게 해 놓고 전체 노드 집결에는 참여시키는 충돌, 이전 방에서 합류할 때 문 자체의 방 번호나 파괴된 벽칸의 방 번호 0을 금지하는 충돌이 있었다. 현재 방의 경계 자리로 갈 폰에게 돌입조의 다음 방 노드를 먼저 요구하는 경우도 있었다.

접근과 준비 완료가 같은 참여 집합을 사용하고, 후방 인원은 알려진 실내 연결부만 이용하는 개인 합류 구간을 만든다. 모든 문이나 외부 바닥을 일괄 허용하지 않는다. 다른 인원이 접근을 끝낸 뒤 경계가 해제되는 경우에도 해당 폰의 마지막 합류 구간만 재개한다. 먼저 도착한 인원의 진행은 유지한다.

“집결” 말풍선은 계획 단계 변경 알림이다. 실제 Goto가 시작되었다는 뜻은 아니다. 개발자 표시에서 요청 목적지·적용 목적지·명령 소유자·실제 Job·차단 이유·지속 틱·실제 Goto 시작 지연을 확인할 수 있다. 개구부 작업을 먼저 하는 분대가 있으면 후속 분대는 명시적인 `OpeningQueue` 상태로 대기한다.

400명 시험에서는 최초 계획을 주로 30틱마다 한 건씩 처리하여 일부 분대가 900틱 시험 종료까지 계획을 받지 못하는 별도 병목도 발견했다. 최초 계획 FIFO를 프레임마다 처리하고, 대기 중인 폰은 전술 소유권을 유지한 채 현 위치를 지킨다. 최신 구조 수집 중 이전 Completed를 새 습격의 고정 구조로 잡던 문제도 수정했다.

## 적용한 최적화와 선택

| 변경 | 현재 방식 | 실제 한계 |
| --- | --- | --- |
| 반복 조회 | 조직 뷰/ID 재사용, 폰 배정·개인 진행 사전, 즉시 대응 분대 ID 사전 | 구성원 상태는 살아 있는 객체에서 읽으며 전체 전투 AI를 캐시하지 않음 |
| 대형 | 맵당 틱별 칸→배정 인덱스, 겹치는 개구부 작업 구역 FIFO | 실제 칸 점유는 최신 ThingGrid로 확인. 대기열은 병렬 진입 경로 분배를 대신하지 않음 |
| 이동 비용 배열 | 실제 허용 조건으로 중복 합치기, 실제 대기자 우선 FIFO, 해당 폰만 완료 통지 | 바닐라 customizer API가 맵 전체 배열을 요구함 |
| 수명·메모리 | 요청 참조와 Native 읽기 종료를 따로 추적, 안전한 유휴 LRU 회수, 일반 준비 64MiB·128항목 목표 | 긴급 회피는 잠시 예산을 넘을 수 있음. 바닐라 경로 배열/관리 힙 전체의 상한이 아님 |
| 물리 지도 | 16×16 청크, 건물·문·지형 변화 이벤트, 120틱 안전 폴링 | 캐시의 물리 변화와 분대가 아는 변화는 분리 |
| 적 관측 | 공간 후보 인덱스, 같은 틱 LOS 재사용, 맵당 10틱/2048 시도와 FIFO 최소 32 | LOW 접촉/HIGH 무전 정보 공유 규칙을 우회하지 않음. 연막은 매 틱 현재 상태 확인 |
| 국소 CQB 지도 | 4개 배열을 두 묶음으로 재사용하고 이전 결과와 비교한 뒤 교체 | 메인 스레드 소유 버퍼이며 워커가 참조하는 입력 풀은 아님 |
| 계획 비용 | 예비 점수 순으로 검사, 완전히 유효한 후보 3개를 찾으면 가장 좋은 결과 채택 | 실패한 후보가 많으면 나머지 후보도 검사. 전체 후보에서 최적임을 보장하지 않음 |
| 계획 예산 | 프레임당 3ms/최대 2건 입장, FIFO, 단일 틱 최초 계획 1건 | 실행 중인 한 계획을 강제로 쪼개거나 중단하지 않아 한 번의 계획은 3ms를 넘을 수 있음 |
| 워커 | 불변 값 작업 최대 2개, 정적 구조 작업 최대 1개 | Map/Pawn/Thing 접근은 메인 스레드. 4개 성능은 바닐라 Jobs 경쟁까지 검증한 결과가 아님 |

합성 600×600 배열 64건 비교에서 워커 1/2/4개는 약 179/89/49ms였다. 이는 Unity/Mono/바닐라 경로 탐색이 없는 값 계산 측정이다. 따라서 기본은 2개로 정했다. 자세한 원자료는 [값 기반 측정](Security%20이동%20최적화%20후%20값%20기반%20측정.json)에 있다.

## 실제 이동 회귀 시험

`-hdRaidMovementAuditFunctional`을 명시한 별도 quicktest에서 11명 모두 Security인 집결 임무를 제공했다. 지정한 출발/목표 방과 알려진 연결부를 고정하고, 실제 전술 실행·명령·Unity PathFinder·Pawn_PathFollower로 이동시켰다. 적이 없는 이동 시험이며 자연 발생 전투 전체를 재현한 결과는 아니다.

| 상황 | 결과 | 도착까지 게임 틱 |
| --- | --- | ---: |
| 이전 방 → 알려진 열린 문 → 목표 방 | 11명 도착 | 401 |
| 고정 구조의 벽이 파괴된 새 개구부 | 11명 도착 | 482 |
| 시야 밖 반대편 문을 30틱마다 개폐 | 같은 계획 유지, 해당 문 사용 없이 11명 도착 | 524 |
| 10명 접근 완료 뒤 이전 방의 경계 인원 해제 | 경계 해제·개인 합류 완료 | 235 |
| 이미 알려진 개구부에 HC 연막 유지 | 11명 도착 | 434 |

이 값은 해당 배치의 이동 완료 시간이며 명령 처리 지연 자체가 아니다. 속도·충돌·한 칸짜리 연결부 통과 시간도 포함한다. Unity 프레임 사이에 시작·완료된 짧은 Job은 현재 Job 폴링만으로 셀 수 없어 실제 위치 변화와 StartJob 진단도 함께 확인했다. [회귀 원자료](Security%20이동%20실게임%20회귀%20결과.json).

전술 분대의 계획 수는 50/100/200/400명 각각 5/10/19/37이며, 모든 조건에서 실패 계획 0건, 측정 종료 시 이동 배열 준비 대기 0건이었다. 실제 배열 대기자의 최대 나이는 1프레임이었다. 누적 배열 생성 28건/재사용 4947건, Native 배열 최고 사용량은 3,500,000 bytes(약 3.34MiB)였다.

400명 1배 조건의 계획 CPU p50/p95/p99는 10.538/15.223/19.408ms, 실행은 14.525/55.168/95.437ms였다. 3배 실행 프레임 최고값은 112.338ms였다. 평균 TPS와 별개로 순간 스파이크가 남으며 **400명을 충분히 감당하는 상태라고 보기는 어렵다**. 1배의 200명까지는 약 60TPS지만 FPS 저하도 확인된다.

이동 시작 지연의 400명 p95/p99는 0/0틱이고 최댓값은 1배 181틱/3배 206틱이었다. 시작한 Move만의 분포이므로 아직 시작하지 않은 대기는 포함하지 않는다. 종료 시 400명 중 389명은 같은 작업 구역의 `OpeningQueue` 대기였고 11명만 앞선 작업을 진행했다. 이 900틱 시험의 TPS를 400명이 동시에 실내 CQB를 수행하는 경우로 확대 해석하면 안 된다.

3배의 0명 조건도 앞선 400명 제거 후 139TPS로 나왔고, 50/100명의 상대 결과가 일관되게 증가하지도 않았다. 한 실행 순서의 정리/GC·행동 차이와 시간 변동이 포함되어 있다. 재실행 순서를 바꾸고 반복 수를 늘리기 전에는 개선율이나 엄격한 수용 인원 상한으로 사용하지 않는다.

250×250 quicktest 맵, 콘크리트 평지, 외벽·내벽·문·이름 있는 침대를 생성했다. 같은 장비의 바닐라 공병과 LOW 조직 전술 AI를 비교한다. 11인 분대와 마지막 잔여 인원으로 스트레스 단위를 만들었으며 잔여 단위에도 돌파 도구를 제공한다. 이는 실제 습격 생성기 편제 검증과 별개의 시험이다. 침대 주인은 시험 중 사망하지 않게 보호한다.

각 조건은 300틱 준비 후 600틱 동안 FPS/TPS를 측정한다. CPU/GC/Goto 통계는 준비 시간을 포함하는 900틱 누적이다. 단계별 CPU에는 서로 포함되는 항목이 있어 합계로 더하지 않는다. `worst execution/frame`은 전술 실행의 프레임별 누적 최댓값이며 렌더·바닐라 AI를 포함하는 전체 프레임 시간은 아니다. 배열/메모리 지표는 동일 맵의 여러 조건에 걸친 누적/최고값이므로 바닐라 행에 남은 메모리를 바닐라가 생성한 것으로 해석하지 않는다.

앞선 탐색 시험은 Superfast를 “3”으로 표기했지만, 실제 바닐라 `TickManager`의 Superfast는 6배 또는 12배다. 최종 비교는 Normal/Fast를 명시해 1배/3배를 맞춘다. 탐색 시험의 결과를 최종 표에 혼용하지 않는다.

벤치마크는 동일 PC의 특정 배치·한 번의 실행이다. 전술 AI와 바닐라는 실제 행동이 다르므로 TPS 차이를 특정 최적화 하나의 개선율로 환산할 수 없다. 개구부 FIFO가 긴 대기를 만들 수 있으며, 모든 분대가 계획을 받은 것과 모든 방을 클리어한 것도 구분한다.

## 장시간 진입 검증과 진단 보정

300틱 준비＋6000틱 표본의 별도 50명 장시간 시험에서는 5분대 중 `ClearRoom` 2개, `SecureRoom` 1개, `CrossBreach` 1개, `Assemble` 1개로 진행했다. 후속 분대가 영구 정지하는 대신 차례로 작업 구역을 사용하고 진입하는 것을 확인했다. 종료 시 배열 준비 대기 0, 최고 2건, 최대 대기 1프레임, Native 최고 3.22MiB였고, 전술 예외는 없었다. 모든 방 클리어가 끝난 결과는 아니다. [장시간 원자료](Security%20공유%20개구부%20장시간%20검증.json).

이 시험의 실행 p50/p95/p99는 2.024/11.034/25.760ms, 프레임 최고값은 174.184ms였고, 계획 한 번의 최댓값은 96.891ms였다. 여기서도 프레임 입장 예산의 한계를 확인했다. 종료 스냅샷에는 이미 준비가 끝난 `GridPreparing` 사유가 일부 남아 있었다. 이후 준비 완료 통지에서 그 사유를 해제하고, 보호 작업이나 자세 작업 때문에 재개하지 못하면 `ProtectedJob`/`Busy`로 표시하도록 수정했다. 성능·네이티브 회귀 원자료는 이 표시 보정 전 DLL(`8b3768bd`)의 결과이며, 표시 보정은 빌드·게임 클래스 검증을 별도로 통과했다.

## 더 공격적인 최적화의 적용 가능성

남은 우선 후보는 계획 후보 검사 자체를 여러 프레임으로 나누는 상태 머신, 국소 재계획을 변경 청크에 구독시키는 방식, 공유 개구부의 대기 자리 조회를 지속 인덱스로 바꾸는 것이다. 특히 3ms 입장 예산만으로는 첫 계획의 큰 스파이크를 없앨 수 없다.

장기적으로 방/연결부 그래프가 다음 지향점과 합류 연결부를 제공하고, 바닐라 Goto에 짧은 구간을 맡기는 방식을 검토할 수 있다. 전체 배열을 제거하면서 기존 물리 이동 차단만 유지하면 금지된 경로를 선택했다가 실제 이동이 멈추는 충돌이 다시 생긴다. 경로 선택과 물리 허용을 함께 바꿔야 한다.

Jobs/Burst 이전은 값 계산이 주된 병목인지를 먼저 확인해야 한다. 현재 줄인 것은 중복 작업·조회·할당·대기 의존성이고, 게임 객체 접근을 워커로 옮기지는 않았다. 폰마다 Task를 무제한 생성하거나 GPU 경로 탐색을 적용하는 것은 이번 범위에 포함하지 않는다.

## 재실행

게임을 종료한 상태에서 아래 스크립트를 실행한다. DLL/PDB만 설치 모드에 복사하며, 새 감사 폴더에 독립 설정·저장 데이터·로그를 만든다. 기존 플레이 세션은 재사용하지 않는다. 감사 게임은 완료/오류 시 자신만 종료한다.

```powershell
./Source/Benchmarks/RaidMovementAudit/Run-GameAudit.ps1
./Source/Benchmarks/RaidMovementAudit/Run-GameAudit.ps1 -Cases 16 -Functional
```

생산 빌드 경고 0/오류 0, 지형·값 작업 933개, 게임 클래스 바인딩 전체(Security 40개), 전술 정책 전체, 편제 2180개, XML 395개를 통과했다. Unity 실게임 시험은 위의 별도 결과로 확인한다.
