# 스파이크 원인 분해 도구

2026-10-08. 프로파일러 schema 8. [기존 틱 추적](틱%20스파이크%20프로파일러%20확장.md)에서 남아 있던 욕구 트래커 내부와 초기 호출 여부를 구분하기 위한 확장이다. 전술 판단·이동·바닐라 AI 동작은 바꾸지 않는다.

## 추가 기능

- `needs-spikes`: 욕구 트래커와 구체적인 NeedInterval 구현을 수집한다. 현재 설치 게임 기준 추가 18개, 기본 경계 포함 전체 70개다.
- `jobs-spikes`: 작업 판단·전투 행동·사격 위치 탐색과 관련 직접 호출 한 단계. 추가 22개, 기본 경계와 중복 제거 후 전체 71개다.
- `path-spikes`: 경로 시작·갱신·요청·완료 대기와 관련 직접 호출 한 단계. 추가 28개, 전체 77개다. 워커 실행 시간 자체는 수집하지 않는다.
- 추적 시 메서드별 초기 8회 호출의 시점·문맥·경과 시간과 메서드별 진입 순번을 보존한다. 빠른 호출, 느린 틱 보존 순위, 상세 기록 512개 제한, 폰 필터와 독립적이다. 추적 비활성 시 추가 배열을 만들지 않는다.
- CLI `initial CAPTURE [METHOD_TEXT]`로 초기 표본과 이후 전체 호출 평균을 함께 본다. `spikes`/`pawn`에도 진입 순번이 나오며 `hotspots`에는 호출당 평균과 틱당 호출 수가 추가된다.
- `hotspots`의 `excludedMethods`에서 메서드별 다른 스레드 호출/중첩 깊이 초과를 구분한다. 불완전 수집의 비교 거부 규칙은 유지한다.

등록 때만 IL/Reflection을 사용하며, 전체 호출 그래프·getter·Unity 워커를 자동 계측하지 않는다. 모든 대상은 기존 128개 상한 안에 있어야 한다. Core 기준 배치 메서드는 자동 확장에서도 제외한다. 수집 중에는 미리 할당한 배열에 값만 쓰고 파일/JSON 생성은 종료 후 수행한다.

초기 작업 프리셋 시험에서 제외 호출 252건으로 불완전 캡처가 나왔다. 정상 비교 자료로 쓰지 않았다. 직접 호출 확장을 같은 클래스·Verse.AI·JobGiver로 좁혀 공용 보조 함수 계측을 줄였고, 누락 이유별 카운터를 추가했다. 실패 자료는 별도로 보존하며 이 시점에 카운터가 없었으므로 252건의 이유를 확정하지 않는다.

## 해석

초기 표본은 **수집 시작 이후의 메서드 전체 최초 8회**다. 폰별 최초 호출이나 게임 시작 이후 최초 호출이 아니다. JIT/콜드 캐시 원인으로 단정하지 않는다. 이후 평균은 초기 표본을 뺀 모든 완료 호출을 사용하지만 이후 최대 표시는 보존된 긴 호출/느린 틱에 한정한다. 없으면 null이다.

기존과 동일하게 개별 메서드 값은 경과 시간이다. 실제 CPU는 루트 틱/전체 메인 창 Windows 계수와 함께 판단한다. Core 고정 배치 대비 비율은 CPU 점유율이 아니다. 프리셋·추적 스키마·폰 필터가 다른 실행을 전후 성능 비교로 묶지 않는다.

## 약식 검증

게임/CLI 빌드, 초기 호출의 재귀·진입 순서·예외·중단 후 배출·버퍼 제한, JSON 왕복, 초기 표본 제외 평균/Core 비율, 선택 메서드/0틱/기록 부재 처리를 검사했다. 실제 게임 어셈블리에서 세 프리셋의 구체적 메서드·폰 문맥 연결·128개 상한과 Core 기준 제외를 확인했다.

욕구 프리셋은 실제 LOW 60명/5분대, 외벽 돌파, 준비 120틱·측정 180틱으로 한 번 수집했다. 등록 70개, 초기 기록 320개, 보존 틱 8개, capture/audit complete=true, dropped/계측 예외/상세 기록 잘림 0이다. 전체 임무 완료 시험이 아니며 기능 완료 값 false를 그대로 보존했다. 실제 캡처에서 CLI 조회·같은 조건 비교·다른 조건 거부 검사도 통과했다.

이 실행의 `Need_Mood.NeedInterval` 최대는 19.2225ms, 그 아래 선택된 `Need_Seeker.NeedInterval` 최대는 18.4876ms였다. 초기 8회 기분 호출 최대는 0.8900ms이고 19.2225ms 호출은 이후 기록에 남았다. 긴 욕구 처리의 범위를 기분/Seeker 계산까지 좁혔고, 메서드 전체의 최초 수집 호출만으로 설명할 수 없는 사례를 확인했다. 특정 생각 계산·GC·JIT·폰별 초기화 중 무엇이 원인인지는 이 자료만으로 확정하지 않는다. 바닐라 수정이나 CPU 개선률을 주장하는 결과도 아니다.

최종 작업·경로 프리셋은 각각 LOW 24명/2분대, 준비 0·측정 180틱으로 한 번 재검증했다. 등록 71/77개, 초기 기록 360/464개, capture/audit complete=true, dropped/계측 예외/상세 잘림 모두 0이다. 경로 시험은 실제 StartPath 30회, CreateRequest의 각 오버로드 31회, ForceCompleteScheduledJobs 181회를 수집했다. 최종 DLL 지문과 원본 지문이 일치하고 CLI 검사를 통과했다. 첫 경로 버전의 상세 기록 잘림 47,218건도 따로 보존했다.
