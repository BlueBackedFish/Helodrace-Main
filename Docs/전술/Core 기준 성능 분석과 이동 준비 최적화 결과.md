# Core 기준 성능 분석과 이동 준비 최적화 결과

2026-10-07. [다음 최적화 계획](에이전트%20프로파일러%20구현%20결과와%20다음%20최적화%20계획.md)의 1번 작업을 진행했다.

## 성능 분석 기준

Core `Verse.GenRadial.NumCellsInRadius(float)`를 반지름 `8+(i%16)`으로 10,000회 실행한 고정 배치가 기준이다. 지도·폰·전술 진행·난수를 읽지 않는다. 준비 호출로 초기 JIT 비용을 제외하고 수집 시작/종료와 약 1초마다 측정한다. 기준 샘플은 대상 메서드 집계에서 제외하며 기준 메서드를 별도로 Harmony 계측하는 선택은 금지한다.

100%는 이 고정 배치 한 번의 비용이다. CPU 점유율이 아니다.

- 호출당 기준 비율: `(메서드 누적 경과 시간 / 호출 수) / Core 배치 중앙값 × 100`.
- 틱당 기준 비율: `(메서드 누적 경과 시간 / 게임 틱 수) / Core 배치 중앙값 × 100`.
- 전후 비교: 틱당 기준 비율의 전후 값과 퍼센트포인트 차이. 실제 ms/tick도 함께 기록한다.

원본 수집 JSON에 기준 입력·반복 수·모든 샘플·기존 Harmony 패치 소유자와 메서드별 두 비율을 기록한다. CLI는 중앙값과 비율을 표시하고 같은 기준인지 검증한다. 기준이 없거나 입력/횟수/패치가 다르면 비교를 거부한다. 기존 기준 없는 파일에서 비율을 임의로 만들지 않는다. 틱이 없는 수집은 틱당 값이 null이다.

공통적인 CPU 속도 변화는 이 비율로 줄일 수 있다. GC, 서로 다른 메모리 접근 특성, 스케줄링 간섭과 전술 진행 차이는 남는다. 원래 시간과 호출 수, 게임 진행 결과도 함께 보며 비율만으로 모든 환경 차이를 제거했다고 주장하지 않는다. 실제 스레드 CPU는 기존처럼 전체 게임 틱에만 별도로 기록한다.

## 이동 준비 처리 변경

빈 준비 큐는 OldestWaitAge/ServiceOrder/배열화를 수행하지 않는다. 캐시 한도·메모리 한도 때문에 필요한 Trim은 별도로 유지한다. 준비된 캐시를 무조건 해제하지 않았으며 네이티브 lease 및 PathFinder의 해제 소유권은 변경하지 않았다.

작업이 있는 큐는 같은 프레임의 Tick/Update를 한 번의 준비 패스로 합친다. 중복 요청은 패스를 다시 열지 않는다. 새로운 준비 작업이 들어오면 같은 프레임에도 다시 처리할 수 있다. 미완료 worker는 다음 프레임에 계속 확인한다. Clear 후의 새 습격은 이전 프레임 상태를 이어받지 않는다.

`Select`는 제거된 컴포넌트와 order-null을 관측/수류탄 준비 검사보다 먼저 반환한다. 감사 결과에는 측정 구간의 실제 `preparationServicePasses`를 추가했다.

## 실제 게임 수집

경량 계측, OS CPU 조회 비활성, LOW, 3배속, 50명→100명→종료 후 0명, 준비 120틱, 측정 약 1,200틱. [원본 수집·감사·CLI 비교 결과](../../Source/Benchmarks/AgentProfiler/Results/2026-10-07/)를 보존했다.

| Pump 구간 | 이전 ms/tick | 이후 ms/tick | 이전 Core 기준 %/tick | 이후 Core 기준 %/tick |
|---|---:|---:|---:|---:|
| 50명 | 0.012343 | 0.006947 | 4.506% | 2.553% |
| 100명 | 0.014003 | 0.002778 | 5.125% | 0.999% |
| 종료 후 0명 | 0.007743 | 0.000452 | 2.838% | 0.166% |

종료 후의 기준 비율 감소는 약 94.1%다. **Pump 자체의 감소**이며 전체 게임 CPU가 94% 줄었다는 뜻이 아니다. 50/100명 구간은 전술 진행이 완전히 같지 않으므로 반복 검증 없이 개선율을 일반화하지 않는다.

종료 후에도 가벼운 컴포넌트 호출은 1,600회 남았지만 실제 준비 서비스 패스는 0이었다. 구간 중 남은 네이티브 캐시는 정상적으로 유지됐다. 활성 50/100명 구간의 서비스 패스는 6/4회였고 준비 완료 통지와 다음 습격의 새 작업도 발생했다. 누적 peakWaitFrames는 1프레임이었다.

모든 전후 감사 실행은 complete로 종료했다. 이후 50/100명은 전원 생존·이동했다. 이전 50명은 40명이 이동했다. 이 진행 차이를 성능 최적화의 부수적인 AI 개선으로 단정하지 않는다. 이후 50명 감사에 관측 작업 중인 대기 이동 1건도 남아 있으므로 security의 모든 정지 현상이 해결됐다고 해석하지 않는다.

## 검증과 후속

- 수집기 단위 시험: 재귀/예외/종료/JSON 및 Core 중앙값·공통 속도 변화·잘못된 기준 검증.
- CLI: 동일 수집 비교, 서로 다른 기준/대상 거부, 틱 없는 수집 처리 검증.
- 순수 전술 시험: 1,179개 검사 통과. 프레임 중복 제한·동일 프레임 새 요청·완료 통지·새 습격 초기화를 포함한다.
- 실제 게임 클래스 기반 연결/전술 검증 통과. native 기능 감사의 개구부 통과·늦은 Security 합류·연막·외벽 추종·겹친 자리 처리 등 7단계가 모두 통과했다. 원본 기능 감사 결과도 함께 보존했다.

다음 작업은 기존 계획의 2번인 통신 재계산 축소다. 이번 변경에서 통신 접촉/중계 규칙을 변경하지 않았다. 이후 비교도 동일 Core 기준과 동일한 계측 대상·전술 조건을 사용한다.
