## 다음 작업 순서

### 1. 빈 이동 처리의 상시 비용 제거

`Pump`에 pending=0 빠른 반환을 넣는다. 캐시 한도/메모리 한도 때문에 필요한 Trim은 별도로 유지한다. `Select`는 removed/order-null 확인을 관측·투척 준비 검사보다 먼저 수행한다. 활성 준비 작업의 프레임당 중복 Pump도 줄이되 같은 프레임에 새 요청이 들어오는 경우와 준비 완료 통지 지연을 고려한다.

완료 기준: 종료 후 준비 큐 순회/배열화가 발생하지 않고, 새 습격 시작·준비 완료 통지·동일 개구부 진입이 유지된다. 네이티브 경로 판독 lease 및 PathFinder 소유권은 그대로 지킨다. cache memory 숫자가 0이 되는 것을 성공 기준으로 삼지 않는다.

### 2. 통신 재계산 축소

먼저 LOW의 불필요한 장비 무전기 열거/RadioTo 검사와 디버그 상태 문자열 재생성을 줄인다. 활성 분대 목록을 맵의 실행 티켓/로스터에서 얻고 매 프레임 전체 조직을 다시 열거하지 않도록 한다.

이후 구성원·대장·위치·장비/무전 상태가 변할 때 연결을 갱신하고, 짧은 유효기간 동안 기존 간선과 CommandDelays를 재사용한다. 문/벽 및 연막 변화에 대한 유효기간이나 버전 검증도 필요하다. 위치만 같다고 LOS가 계속 유효하다고 가정하지 않는다. 프레임의 갱신과 보고 전달 시점의 최종 접촉/장비 검증을 분리한다.

정확한 모든 간선 재계산이 여전히 크면 직접 대장 연결을 우선하고 제한된 중계 홉/틱별 간선 예산으로 단순화한다. 기존 정보를 계산 도중 불완전하게 공개하지 않는다. LOW의 접촉 없는 분대 간 공유 금지, 전달 지연/ACK/중단, High의 실제 방탄복 무전 파츠와 blackout 조건을 유지한다. 태블릿을 도입하지 않는다.

완료 기준: 동일 상세 대상에서 간선/LOS/연막 호출 수가 감소하고, 동일 경량 대상의 RefreshFrames ms/tick이 감소한다. 접촉 단절·무전 장비 손실·대장 사망·연막 차단의 기존 검증을 통과한다.

### 3. 실행 반응 및 큰 단일 호출 축소

RunScheduledUnit, RefreshContactsCore, EmergencyReactions, RespondToFire, RespondToCqbContacts, FollowNodes, RetargetBlockedStackMembers, TryStartBreach 등을 소수씩 추가 계측한다. 평상시 10틱 반응 검사를 더 싼 사건/위험 변경 플래그와 느린 전체 검토로 분리할 후보를 찾는다. 사망·다운·폭발 같은 확실한 긴급 사건의 우선 처리는 유지한다.

UpdateStep의 큰 작업은 하위 호출이 실제 원인인지 먼저 확인하고, 필요하면 검색/계획을 여러 틱에 나눠 처리한다. 이번 수집에서는 실행 스케줄러 queue budgetStops=0이었으므로 이미 설정된 2ms 예산을 무조건 낮추는 것보다 한 단위의 큰 호출을 제한하는 편이 적절하다.

완료 기준: 준비를 충분히 거친 동일 전술 단계에서 반복 측정하고, 누적 시간뿐 아니라 긴 호출/게임 틱 p95·p99가 개선된다. security 집결 및 개구부 통과 시험은 별도로 수행한다. 폰이 멈춰서 CPU가 줄어든 결과는 성공으로 보지 않는다.

### 4. 재현성과 도구 확장

동일 지도 seed/전술 단계/준비 조건을 고정한 반복 실행과 결과 집계를 추가한다. 이후 200/400명 및 High 무전 편제를 확대한다. 현재 TPS 대조군은 50명 176.612, 100명 157.260이고 경량 수집은 176.896/166.099였다. 수집 실행이 더 빠른 구간도 있으므로 이 자료로 정확한 계측 오버헤드 %나 성능 개선을 주장할 수 없다. 2%/5% 비용 목표는 아직 입증되지 않았다.

호출별 지연 분포와 한정된 긴 호출 기록, 여러 스레드 지원, 독립 모드/MCP 래퍼는 실제 필요에 따라 추가한다. 네이티브 Mono 샘플러는 초기 로딩/ABI 검증이 필요한 별도 연구다. 현재 통신 및 빈 큐 비용은 메인 스레드의 반복 작업이어서 곧바로 다른 스레드에 보내는 것보다 재계산과 호출 자체를 없애는 방향이 우선이다.
