# 스택업·진입 위치 계산 틱 스파이크 분석

2026-10-12. 단일 방 돌파를 실제 게임에서 두 번 측정했다. **스택업과 진입 자리의 여러 후보를 한 틱에서 계산하는 구조는 확인됐지만, 큰 지연에는 최초 전술 판단·자리 배정 비용과 바닐라 폰/경로 처리도 함께 포함된다.** 전술 알고리즘은 수정하지 않았다.

## 측정 조건과 유효성

- 현재 New 엔진, LOW 12명/1분대, 외벽이 닫힌 하나의 39×35칸 방, 이름 있는 침대 목표, 해머 돌파.
- 같은 시드·DLL·지도·폰 지문으로 새 프로세스 2회. 준비 0틱, 수집 1800틱, 3배속. 스택업/진입 생성 메서드와 바닐라 틱·작업·경로 경계를 선택 계측했다.
- 두 capture 모두 complete=true, dropped=0, 메서드 예외 0. 12명 전원 진입·자리 도착, 실제 구조에 맞는 계획·연결 스택·고유 자리 검사 통과. 잘못된 안전 대기 전 진입·작업 실패 0.
- 목표 폰은 시험 중 피해를 받지 않아 진입 후 계속 사격하며 종료 단계는 Enter다(39/38회 사격). 전체 방 확보나 습격 완료를 검증한 시험은 아니다.
- 첫 시도는 수집 시작 전 격리 검사의 오류로 중단됐다. 최근 Prefix+Postfix가 있는 같은 클래스가 후크 2개로 집계되는데 기대값은 클래스 1개였기 때문이다. 실제 설치 클래스 집합을 비교하도록 **시험 도구만 수정**했다. 실패 원본은 별도 보존하고 성능 수치에서 제외했다.

## 같은 계획 생성 틱의 비용

아래 값은 **경과 시간 ms**다. 개별 메서드의 실제 CPU 시간은 아니다. 부모/자식 행은 중복되므로 합산하지 않는다.

| 메서드/구간 | 호출 수 1회차/2회차 | 1회차 합계 | 2회차 합계 | 1회차 단일 최대 | 2회차 단일 최대 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 계획 생성 틱 전체 `DoSingleTick` | 1/1 | 55.980 | 60.527 | 55.980 | 60.527 |
| `AdvanceCore` — 해당 틱 판단 | 1/1 | 29.358 | 30.766 | 29.358 | 30.766 |
| `TacticalLocalPlanner.Find` | 1/1 | 13.036 | 13.297 | 13.036 | 13.297 |
| `ClassifyStructure` | 9/9 | 3.443 | 3.468 | 1.879 | 1.780 |
| `BuildStack` | 7/7 | 3.763 | 4.052 | 2.967 | 3.291 |
| `BuildPositions` | 7/7 | 1.636 | 1.733 | 1.494 | 1.610 |
| `AllocateEntry` | 1/1 | 3.250 | 3.275 | 3.250 | 3.275 |

두 실행 모두 수집 틱 3에 이 작업들이 몰렸다. `Find`와 그 바깥의 `AllocateEntry`는 직접 중첩되지 않아 합계 16.286/16.571ms이며, 해당 전술 판단의 55.5%/53.9%다. `BuildStack`+`BuildPositions`는 5.398/5.785ms, 판단의 18.4%/18.8%다. **자리 플러드필만 줄여서 전체 29~31ms를 모두 없앨 수는 없다.**

Core `GenRadial.NumCellsInRadius` 10,000회 배치 중앙값은 0.2807/0.2718ms다. `Find` 한 번은 그 기준의 **4,644%/4,892%**, `AllocateEntry`는 **1,158%/1,205%**다. 평균 틱으로 나누면 `Find`는 2.579%/2.718%에 불과해 초기 스파이크가 평균값에 가려진다. 이 비율은 CPU 점유율이 아니다.

계획 틱의 실제 메인 스레드 CPU 계수는 두 번 모두 46.875ms였다. Windows의 거친 시간 해상도를 가진 루트 CPU이며 이 값을 하위 메서드별로 나눠 귀속하지 않는다. 계획 틱 GC 0/1/2 컬렉션은 모두 0이었다. 객체 할당 비용까지 없다는 뜻은 아니다.

## 코드에서 확인한 원인

1. [Find](../../Source/Helodrace/Tactics/TacticalLocalPlan.cs)은 최대 8개 외벽 후보를 순회하며 **후보마다 스택업과 진입 공간을 모두 만든 뒤** 점수 정렬과 최종 도달 검사로 선택한다. 이 시험에서는 7개 후보가 실제로 두 계산을 모두 실행했다. 선택하지 않은 6개 후보의 자리는 버려진다.
2. [AdvanceCore](../../Source/Helodrace/Tactics/TacticalCommands.cs)는 `Find` 직후 진입 순서와 `AllocateEntry`까지 같은 호출에서 처리한다. [작업 예산](../../Source/Helodrace/Tactics/TacticalWorkBudget.cs)의 1.5ms 제한은 허가/사후 회계다. 긴 `Find`나 플러드필을 중간에 중단하지 않으므로 틱당 계획 1개여도 스파이크가 가능하다.
3. [StackFormation](../../Source/Helodrace/Tactics/TacticalStackFormation.cs)은 연결된 양쪽 대형과 LOS→축→무필터 완화를 위해 탐색한다. 각 후보에 별도 상태/시야 배열·힙·리스트가 생기며, 연결 부분 탐색은 필요한 자리 수를 얻은 뒤에도 해당 부분을 계속 탐색한다. [EntryFootprint](../../Source/Helodrace/Tactics/TacticalEntryFootprint.cs)은 별도 배열/힙으로 안쪽 공간을 다시 계산한다. 동일한 틱에서 이 비용이 후보 수만큼 반복된다.
4. 최초 비용이 크다. `BuildStack` 첫 호출은 2.967/3.291ms지만 같은 계획 안의 나머지 6개 평균은 **0.133/0.127ms**다. `BuildPositions` 첫 호출은 1.494/1.610ms, 나머지 평균은 **0.024/0.020ms**다. 첫 호출 준비·JIT·캐시 영향이 의심되지만 JIT를 직접 계측하지 않았고 정확한 내역은 확정하지 않는다. 큰 최초 값을 반복 비용으로 보지 않는다.
5. `AdvanceCore`에서 계측한 자식을 뺀 잔여 경과 시간도 해당 틱에 **13.072/14.195ms**다. 내부의 미계측 판단·설정·진입 순서·계측 비용 등이 포함된다. 이 잔여 시간을 모두 위치 계산이라고 분류할 근거는 없다.

LOS는 계획 틱에서 대표 오버로드 609회, 합계 0.143/0.136ms였다. 이 장면에서는 LOS 자체가 주범이라는 근거가 없다. 가구 제거 시뮬레이션 `TryPrepareFurniture`는 0회여서 복잡한 가구/복도 상황은 이번 시험 범위 밖이다.

## 다른 스파이크와 구분

1회차의 계획 틱에는 바닐라 `TickList.Tick` 24.494ms가 겹쳤고, 2회차에는 `PathFinderTick` 25.957ms가 겹쳤다. 이들은 전술 자리 생성 메서드의 자식이 아니다. 2회차 전체 최대는 틱 2의 **80.871ms**로, 계획 생성보다 먼저 발생했으며 바닐라 폰 처리 지연이 컸다. 경로 처리 값도 워커 계산·동기화 대기를 분리해 측정한 것은 아니다.

따라서 스택업 시점의 체감 스파이크는 한 원인으로 묶지 않는다. 전술 계획 일괄 계산을 분산해도 바닐라 초기 폰/경로 스파이크는 남을 수 있다. 고비용 메서드 대부분이 수집 초반이라 두 새 프로세스만으로 반복 CQB/대규모 분대에서의 비용 증가율을 확정하지 않는다.

## 추천 수정 순서

| 우선 | 방향 | 줄일 대상·제약 |
| --- | --- | --- |
| 1 | 저렴한 형상/거리로 후보를 먼저 정렬하고 선택 후보만 대형 계산. 실패하면 다음 후보를 후속 틱에서 처리 | 선택되지 않은 후보의 스택/진입 계산 제거. 이번 장면의 추가 6개 따뜻한 후보 비용은 약 0.94/0.88ms라 이것만으로 초기 30ms가 사라지지는 않음 |
| 1 | 후보 탐색→스택업→진입 공간→개인 배정을 지속 상태로 나누고 단계/후보 사이에 양보 | `Find`+배정 16.3~16.6ms가 같은 틱에 몰리는 현상 완화. 개별 단계의 최초 호출은 여전히 예산을 넘을 수 있어 단계 내부 작업 상한도 필요 |
| 2 | 최초 호출 준비를 별도로 줄이거나 분산. 순수 대형 계산 준비/자료구조 재사용, 배정의 LINQ·컬렉션 생성 단순화 검토 | 첫 플러드필과 배정의 차이가 크지만 실제 절감률은 미검증. 맵을 읽는 경로/AI 함수를 무작정 사전 실행하지 않음 |
| 2 | 다음 원인 확인 시 `AdvanceCore`의 미계측 준비 판단과 바닐라 폰/경로 경계를 좁혀 수집 | 잔여 13~14ms와 별도 25ms급 스파이크 구분. 기존 2명 작업·4회 경로 허가 제한만으로 바닐라 내부 지연을 선점할 수는 없음 |
| 3 | 연결 부분 탐색을 필요한 인원 수에서 조기 종료하고 단순 배열 큐/재사용 버퍼 적용 | 따뜻한 대형 계산은 이미 작음. 후보 분산/최초 비용보다 후순위. 작은 방·양쪽 연결·고유 자리 규칙을 유지해야 함 |

이번 단계는 진단 결과이며 위 전술 최적화를 구현하지 않았다. 기존의 큰 정적 맵 캐시나 워커 구조를 먼저 추가할 근거는 없다. 이 시험의 따뜻한 자리 계산 규모에서는 스냅샷/스레드 작업 큐 비용보다 후보·단계 분산이 단순하고 직접적이다. 전체 전술 AI 또는 바닐라 대비 2배 기준에 대한 합격 판정도 하지 않는다.
