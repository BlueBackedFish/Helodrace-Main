# 텍스트 검사 규칙

Helodrace의 모든 게임 텍스트(아이템, 연구, 건물, 제작법, 직업·보고 문구, 시스템 안내, 툴팁, 설정 화면)를 작성하고 검사할 때 이 문서를 따른다. 연구 배치·통합·분리 판단은 [연구 배치·구성 검수 규칙](ResearchContentReviewRules.md)을 따른다.

## 1. 원문과 번역의 위치

원문은 영어, 번역은 한국어다. 새 텍스트를 처음 추가할 때부터 이 구조로 작성한다.

| 텍스트 | 영어 원문 | 한국어 번역 |
|---|---|---|
| Def의 `label`, `description`, `reportString`, `jobString` 등 | `Defs/**/*.xml`의 해당 필드 | `Languages/Korean (한국어)/DefInjected/<DefType>/` |
| 코드·UI 문자열 | `Languages/English/Keyed/` | `Languages/Korean (한국어)/Keyed/` (같은 키) |

- C# 코드에 표시용 문자열을 직접 쓰지 않는다. Keyed 키를 만들고 `Translate()`로 조회한다.
- Patches로 추가·교체하는 텍스트도 영어로 작성하고 한국어는 DefInjected에 둔다.
- 영어 원문과 한국어 번역은 같은 작업에서 함께 추가·수정·삭제한다. 한쪽만 바꾸지 않는다.

### 언어 결함의 처리

| 상태 | 처리 |
|---|---|
| 영어 원문만 있고 한국어 번역이 없음 | 영어 원문을 한국어로 번역해 DefInjected/Keyed에 추가한다. |
| 원문(Defs·English Keyed·C# 문자열)이 한국어임 | 영어 원문을 작성해 원래 자리를 교체하고, 기존 한국어 문장은 한국어 번역 위치로 옮긴다. |
| 원문이 한국어이고 같은 키의 한국어 번역도 이미 있음 | 둘을 비교한다. 같으면 원문만 영어로 바꾼다. 다르면 어느 쪽을 남길지 기록하고 임의로 덮어쓰지 않는다. |

- 한국어 원문을 번역 위치로 옮길 때 문장은 그대로 옮긴다. 문체·내용 수정은 아래 검사 기준에 따라 별도로 판정한다.
- 영어 원문을 새로 쓸 때와 한국어로 번역할 때 모두 아래 검사 기준을 적용한다. 직역보다 의미와 정보를 맞춘다.
- 고유명사·장비명·연구명은 기존 번역의 표기를 따른다. 같은 대상을 파일마다 다르게 옮기지 않는다.
- 수치, 서식 인자(`{0}`, `{PAWN_label}` 등), 리치 텍스트 태그, 줄바꿈 기호는 원문과 번역에서 일치시킨다.
- 결함 검사는 `Defs`, `Patches`, `Languages/English`, `Source`(표시 문자열)에서 한글을 찾고, 영어 원문 키마다 한국어 번역이 있는지 대조한다. XML 주석과 코드 주석은 제외한다.

## 2. 검사 범위와 판정

- 한국어를 기준으로 문제를 판정하고, 확정한 수정 방향을 영어 원문에도 적용한다.
- 검수만 요청받은 경우 게임 정의나 번역을 수정하지 않는다. 원문, 문제 구간, 이유, 보존할 정보, 개선 방향, 출처와 사용자 검수 의견을 기록한다. 수정은 적용 단계에서 한다.
- `PawnKindDef`와 군용 태블릿은 제외한다. 인용문 때문에 길어진 설명은 길이 검사에서 제외한다.
- 기능 툴팁·계약서·상태 설명은 수치와 사용법이 필요한 자리다. 아이템 설명과 같은 잣대로 삭제 대상으로 삼지 않는다.
- 특정 단어가 있거나 문장이 매끄럽다는 이유로 AI 문체라고 단정하지 않는다. 자동 탐지는 후보 추출이며 최종 판정은 문맥을 대조한다.

## 3. 설명문 검사 항목

### A. 현실 명칭 잔존 (최우선)

- 이미 가상 명칭으로 치환된 회사·브랜드·제품·모델·인물·조직·상표의 현실 이름이 설명에 남아 있으면 지적한다.
  예: 이름은 `디펜테크 IIIA 클래스 방패`인데 설명에 `Intruder G2`가 남은 경우.
- 실제 가상명 치환 근거가 있을 때만 지적한다. 일반 군 제식명, 기술명, 탄약 규격, 구경, 산업 표준, 세계관에서도 그대로 쓰는 일반 명칭은 자동 치환하지 않는다.
- 아이템과 제작법의 명칭도 교차 확인한다.

### B. 불필요하게 긴 설명

같은 의미 반복, 장단점의 과도한 나열, 다른 장비와의 세세한 비교, 스탯에서 확인 가능한 정보의 반복, 당연한 작동 원리 설명, 외형·성능·사용법·장단점·메커니즘을 한 문단에 모두 담은 설명.

### C. 메타적 게임 메커니즘 설명

세계관 속 물건이 아니라 게임 시스템을 직접 설명하는 문장. 예: `착용하면 이동속도가 10% 감소합니다.`, `적이 3칸 이내에 있으면 효과가 발동합니다.` 필요한 조작·효과 정보는 정보 창의 운용 정보 같은 별도 도움말로 옮기는 방향을 기록한다. `좁은 방패라 측면을 넓게 가리지는 못한다.`처럼 물건의 특성을 자연스럽게 묘사하는 문장은 허용한다.

### D. 카탈로그식·AI식 구조

`A 덕분에 B하지만 C는 낮습니다`, `~하도록 설계되었습니다`, `~에 적합합니다`, `뛰어난 X와 우수한 Y를 제공합니다`, 장점→단점→용도 순의 정형 구조, 홍보문 같은 수식 과다. 표현 하나만으로 판정하지 않고 패턴이 반복되거나 사족이 많을 때만 판정한다.

### E. 불필요한 사용법 설명

이름이나 외형만으로 용도가 분명한데 사용법을 풀어 쓴 문장. 그 정보가 물건의 핵심 정체성이면 남긴다.

### F. 정보 밀도 부족

문장 수에 비해 새로운 정보가 적은 설명. 예: 3~4문장이지만 내용이 `경량 방패 / IIIA급 / 관측창` 세 가지뿐인 경우.

### G. 내용 오류

설명의 장비명·해금 목록을 실제 XML·코드와 대조한다. 오래된 목록, 없는 장비, 이름과 기능이 다른 설명은 문체 문제와 별도의 내용 오류로 기록한다.

## 4. 판정 등급과 수정 원칙

| 등급 | 기준 |
|---|---|
| 유지 | 짧고 자연스럽고 세계관과 일관됨 |
| 경미한 수정 | 한두 표현이나 고유명사만 고치면 됨 |
| 재작성 권장 | 사족, 메타성, 현실 명칭, 과도한 비교 등이 여러 개 있음 |
| 강한 재작성 필요 | 대부분이 메타적이거나 현실 명칭이 다수여서 새로 쓰는 편이 나음 |

삭제 우선순위:

1. 게임 메커니즘을 직접 설명하는 문장
2. 이미 가상화된 대상의 현실 고유명사
3. 스탯에서 확인 가능한 수치 성능
4. 불필요한 다른 장비와의 비교
5. 같은 뜻의 반복
6. 지나치게 카탈로그식인 용도 설명

- 무조건 짧게 줄이지 않는다. 기술 원리, 물건의 정체성, 실제 용도, 역사, 제조사 설정, 독특한 설계 특징은 보존한다. 자연스러운 비교나 짧은 기술 설명을 일괄 삭제하지 않는다.
- 길다는 이유만으로 재작성 판정하지 않는다.
- 재작성하면서 새 설정을 창작하지 않는다.

## 5. 현실 명칭 ↔ 가상 명칭 대응

A 항목을 판정하려면 먼저 언어 파일 전체의 명칭 체계를 파악한다. 설명문 검수부터 시작하지 않는다.

- 아이템명, 모델 번호, 제식명, 같은 접두사·제조사 표기, 설명 속 인물·설계자, 같은 제품군, 브랜드와 모회사, 원설계사와 생산사, 라이선스 생산, 회사명 변경·인수합병을 교차검증한다. 남아 있는 현실 모델명은 식별 앵커로 쓴다.
- 아이템 하나만으로 매핑을 확정하지 않는다. 서로 다른 제품 2개 이상에서 같은 방향의 증거가 나올 때만 높은 신뢰도를 준다.
- 신뢰도는 `확정`(독립적인 강한 증거 다수), `유력`(복수 증거 일치, 대안 일부 남음), `가능성 있음`(단서 부족), `보류`(후보 복수·증거 충돌) 중 하나로 쓴다. 근거가 부족하면 `보류`로 남긴다.
- 회사, 브랜드, 제품, 제품군, 설계자, 생산사, 개발사, 라이선스 생산사를 구분한다. 서로 다른 회사를 편의상 하나로 합치지 않는다.
- 같은 가상 명칭의 여러 표기(`W&M`, `W & M`)는 대표 표기 하나를 정하고 나머지를 비고에 남긴다. 이름이 비슷하다는 이유만으로 합치지 않는다.
- 이름 느낌, 같은 첫 글자, 같은 국가·시대만으로 연결하지 않는다. 설계사와 제조사, 현재 상표권자와 역사적 원제조사를 혼동하지 않는다. 설명문의 일반적인 수사를 고유명사 치환으로 오인하지 않는다.

## 6. 연구 이름

- 등록된 모든 연구의 한국어·영어 이름과 기술 내용, 인접 계보의 제목을 함께 대조한다.
- 주된 제목 방식은 기술의 이미지·성과·역사적 의미를 짧게 표현하는 방식이다. 예: `병 속의 번개`, `공기에서 빵을`, `천분의 일 인치를 향하여`, `사격과 기동`.
- `시대/등급 + 장비 종류` 같은 분류명, 사전 표제어, 내부 작업용 제목이 이 제목군과 어긋나는지 검사한다.
- `시너지`처럼 홍보 문구로 읽히는 말, 번역투, 어색한 단계 표현, 의미가 불분명한 조어, 띄어쓰기를 확인한다.
- 기술명을 직접 쓴다는 이유만으로 오류로 판정하지 않는다. `기계공학 입문` 같은 계통 시작점이나 `수치제어` 같은 정확한 기술명은 역할을 고려해 유지 또는 검토로 구분한다.
- 제목이 해금 대상이나 기술 범위를 잘못 암시하면 문체보다 의미 정확성을 우선한다. 개명 예시는 검수용 제안이며 자동 적용하지 않는다.

## 7. 검수 결과 기록 형식

재작성 필요 텍스트는 `경미한 수정` 이상만 기록한다.

| ID | 대상 | 원문 | 판정 | 문제 유형 | 문제 구간 | 현실 고유명사 | 삭제 가능 내용 | 보존할 핵심 정보 | 재작성 방향 |
|---|---|---|---|---|---|---|---|---|---|

- 문제 유형: `언어 위치 오류`, `번역 누락`, `현실 고유명사 잔존`, `과도한 사족`, `내용 반복`, `메타 설명`, `과도한 성능 비교`, `카탈로그식 문체`, `AI식 정형 문체`, `불필요한 사용법`, `내용 오류`, `설정 불일치`, `기타`. 여러 개면 `;`로 구분한다.
- 문제 구간은 핵심 부분만 짧게 인용한다.
- 재작성 방향에는 완성 문장 대신 고치는 방법만 적는다. 예: `Intruder G2 언급 삭제. 성능 비교 삭제. 경량 방패와 관측창 특징만 1~2문장으로 압축.`
- 현실 명칭 잔존은 `대상 / 남은 현실 명칭 / 대응 가상 명칭 / 매핑 신뢰도 / 수정 필요 여부 / 비고` 표로 따로 정리한다.
- 셀 하나에 여러 매핑이나 대상을 합치지 않는다.

## 8. 확인된 예외

- 대출·계약서, 상태 설명, 운용 정보처럼 수치와 사용법이 필요한 텍스트는 C·E 항목 적용에서 제외한다.
- `HelodLowHeavyArtillery`, `HelodSniperRifle`, `HelodLessLethalChemical`은 이름·설명을 보존한다. 저격 연구의 M1C 문구도 유지한다. 기준본은 [exclusions.json](Data/TextContent/exclusions.json)이다.
- 추모 연구의 인용문은 보존한다.
